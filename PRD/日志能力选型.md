
## 1. 文档目的

本指南用于帮助开发 Agent 根据不同项目的：

- 技术栈
- 应用类型
- 部署环境
- 团队规模
- 日志体量
- 隐私与合规要求
- 运维能力
- 成本预算

选择合适的日志方案并完成落地。

日志方案不能只按“哪个产品功能最多”来选择。首先需要区分：

1. **日志生成库**
2. **日志采集与传输层**
3. **日志存储和查询平台**
4. **错误监控与可观测性平台**

这些组件位于不同层级，通常可以组合使用，并不一定互相替代。

---

# 2. 日志系统的基本分层

一套完整的日志链路通常是：

```
应用业务代码
    ↓
日志生成库
    ↓
采集器或传输组件
    ↓
日志存储与分析平台
    ↓
查询、告警、图表和问题排查
```

例如：

```
应用代码
    ↓
Pino
    ↓
OpenTelemetry Collector
    ↓
Better Stack / Loki / 其他后端
```

或者：

```
应用代码
    ↓
Sentry SDK
    ↓
Sentry
```

因此，不能简单地把 Pino、OpenTelemetry、Sentry、Better Stack 和 Loki 当成完全同类的产品。

---

# 3. 五种主要方案的定位

## 3.1 Sentry

### 定位

Sentry 是以**应用错误诊断**为核心的可观测性平台。

它可以统一处理：

- 未捕获异常
- 错误聚合
- 堆栈信息
- 结构化日志
- 分布式追踪
- 性能问题
- 用户会话回放
- 告警

Sentry 可以把错误、日志、追踪和会话回放关联在一起，适合分析“用户遇到了什么问题，以及问题是怎样发生的”。citeturn875368search2turn875368search12turn147811search0

### 最适合的场景

- Web 应用
- 移动应用
- 桌面应用
- API 服务
- SaaS 产品
- 面向最终用户的软件
- 需要快速定位线上错误的项目
- 缺少专职运维人员的中小型团队

### 优点

- 接入速度通常较快
- 错误会自动聚合为问题，而不是只显示大量原始日志
- 可以查看完整堆栈和上下文
- 可以将前端、后端、请求链路和用户操作关联起来
- 自带查询、告警和问题管理界面
- 不需要自行开发日志管理后台

### 缺点

- 使用方式容易与 Sentry SDK 和数据模型形成一定绑定
- 数据量较大时需要关注套餐、采样和保留周期
- 如果需求主要是存储海量服务器原始日志，Sentry 未必是最合适的唯一平台
- 不同语言和框架支持的具体功能可能不同，接入前需要检查对应 SDK

### 选择原则

当项目最关心的是：

> 应用为什么报错、哪个用户受到了影响、错误发生前后经历了什么

优先考虑 Sentry。

---

## 3.2 Better Stack

### 定位

Better Stack 是以**集中式日志管理和日志查询**为核心的托管平台。

应用、服务器或基础设施可以把日志发送到 Better Stack，然后通过统一界面进行：

- 实时日志查看
- 全文搜索
- 字段筛选
- 日志查询
- 图表分析
- 告警
- 日志、指标和追踪关联

Better Stack 支持通过现成集成或 HTTP 接口接收日志；HTTP 接口可接收 JSON、NDJSON 或 MessagePack 数据，因此即使某种语言没有专用 SDK，也可以完成接入。citeturn147811search2turn147811search4turn147811search36

### 最适合的场景

- 后端服务
- API 服务
- 容器和服务器
- 定时任务
- 数据处理任务
- 多个服务集中查看日志
- 需要实时 Live Tail 的场景
- 主要目标是搜索原始日志，而不是错误聚合

### 优点

- 日志导入方式灵活
- 适合集中收集不同来源的日志
- 搜索和实时查看体验较完整
- 不要求所有应用使用同一种日志库
- 可以较快形成统一日志控制台
- 无须自行维护日志数据库和查询集群

### 缺点

- 属于外部托管平台，需要考虑费用和数据上传
- 日志量越大，越需要配置采样、过滤和保留周期
- 与专门的错误监控平台相比，其核心价值更偏向日志搜索和运维分析
- 前端应用不能随意嵌入具备私密写入权限的日志令牌

### 选择原则

当项目最关心的是：

> 把不同服务的日志集中起来，实时查看并快速搜索

优先考虑 Better Stack。

---

## 3.3 OpenTelemetry

### 定位

OpenTelemetry，简称 **OTel**，不是日志查看平台，也不是日志数据库。

它是一套厂商中立的：

- API
- SDK
- 数据标准
- 自动埋点组件
- 数据采集器
- 数据处理和导出机制

OpenTelemetry 可以统一处理三类可观测性数据：

- Logs：日志
- Traces：调用链
- Metrics：指标

OpenTelemetry Collector 可以接收、处理、补充和导出这些数据，再发送到一个或多个开源或商业后端。citeturn147811search6turn147811search16turn147811search17

### 最适合的场景

- 微服务系统
- 分布式系统
- 多语言项目
- 多个服务需要统一追踪
- 希望避免绑定某一家平台
- 未来可能更换日志或监控供应商
- 需要同时处理日志、指标和调用链
- Kubernetes 或复杂云环境

### 优点

- 厂商中立
- 可以统一不同语言和服务的遥测数据
- 后端可以替换
- 可以同时发送到多个平台
- Collector 可以统一执行过滤、脱敏、采样、补充字段和路由
- 适合逐步建设完整的可观测性体系

### 缺点

- 它本身不提供最终的日志查询界面和长期存储
- 仍然需要连接 Sentry、Loki、Better Stack 或其他后端
- 配置和部署复杂度高于直接接入某个 SaaS SDK
- 对简单的单体应用可能属于过度设计
- 不同语言的 SDK、自动埋点能力和日志支持程度可能存在差异

### 选择原则

当项目最关心的是：

> 建立统一标准，并允许未来自由更换或组合日志平台

优先考虑 OpenTelemetry。

需要注意：

> 选择 OpenTelemetry，不等于已经完成日志系统建设。它解决的是采集、规范化和传输问题，最终仍需选择存储和查询后端。

## 3.4 Grafana Loki

### 定位

Grafana Loki 是一个开源日志聚合和存储系统。

它通常与以下组件搭配：

```
Grafana
Loki
Grafana Alloy 或 OpenTelemetry Collector
对象存储或本地存储
```

Loki 的设计重点是通过标签建立日志流索引，而不是为每条日志正文建立完整全文索引。该方式可以降低索引规模和部分存储成本。citeturn147811search7turn147811search33turn987096search13

### 最适合的场景

- 必须自托管日志数据
- 对数据位置有明确要求
- 已经使用 Grafana 生态
- Kubernetes 或容器环境
- 日志量较大
- 团队具备服务器和存储运维能力
- 希望避免完全依赖商业 SaaS

### 优点

- 开源
- 可以自行部署
- 数据和保留策略可控
- 适合与 Grafana 仪表盘、指标和告警体系集成
- 可以使用对象存储承载大量日志
- 适合基础设施和服务端日志

### 缺点

- 需要自行维护部署、升级、备份、容量和安全
- 通常还需要 Grafana、采集器和存储系统
- Loki 本身不包含完整身份验证层，自托管时需要额外配置认证代理或其他安全措施。citeturn147811search26turn987096search11
- 查询方式和标签设计需要学习
- 标签设计错误可能造成大量日志流和严重性能问题

### Loki 标签规则

Loki 的标签应当使用值数量有限、长期稳定的字段，例如：

```
environment
service
application
namespace
cluster
log_level
```

不要把以下高基数字段直接设置为索引标签：

```
request_id
trace_id
user_id
order_id
timestamp
ip_address
```

这些字段可能产生大量唯一值，导致日志流数量急剧上升。高基数字段应放在日志正文或结构化元数据中。citeturn987096search0turn987096search1turn987096search5

### 选择原则

当项目最关心的是：

> 日志数据自主可控，并愿意承担部署和运维成本

优先考虑 Grafana Loki。

## 3.5 Pino

### 定位

Pino 是 Node.js 生态中的结构化日志生成库。

它负责在应用中产生日志，例如：

```
{
  "level": 30,
  "time": 1784390400000,
  "service": "api",
  "event": "user_login",
  "user_id": "anonymous-id"
}
```

Pino 本身不是：

- 云端日志平台
- 日志数据库
- 日志控制台
- 错误监控服务
- 长期日志存储系统

Pino 将额外处理、格式化和传输机制称为 Transport。官方建议把发送、告警、格式化等日志处理工作放到独立进程或工作线程中，避免阻塞 Node.js 主事件循环。citeturn147811search10

### 最适合的场景

- Node.js 后端
- JavaScript 或 TypeScript 服务端
- 需要输出结构化 JSON 日志
- 对日志性能比较敏感
- 希望将日志发送到不同后端

### 优点

- 适合生成机器可解析的结构化日志
- 性能开销相对可控
- 可以通过 Transport 输出到不同目的地
- 便于与 Better Stack、Loki、OpenTelemetry 等组合
- 适合作为 Node.js 项目的底层 Logger

### 缺点

- 只解决应用内日志生成问题
- 没有完整的远程查询和可视化后台
- 不负责长期存储
- 不负责完整的错误聚合和问题管理
- 主要面向 Node.js，不是跨语言通用方案

### 选择原则

当项目使用 Node.js，并需要一个本地结构化日志库时，可以选择 Pino。

但必须同时决定：

> Pino 产生的日志最终发送到哪里。

对于非 Node.js 项目，应当选择对应语言成熟的结构化日志库，而不是强行使用 Pino。

# 4. 五种方案的关系

| 方案          | 所属层级           | 主要职责                         | 是否提供查询后台 | 是否负责长期存储 |
| ------------- | ------------------ | -------------------------------- | ---------------- | ---------------- |
| Pino          | 日志生成库         | 在 Node.js 应用中生成结构化日志  | 否               | 否               |
| OpenTelemetry | 采集与传输标准     | 采集、处理和导出日志、指标、追踪 | 否               | 否               |
| Sentry        | 可观测性平台       | 错误、日志、追踪、性能和回放     | 是               | 是               |
| Better Stack  | 日志与可观测性平台 | 集中收集、搜索、分析和告警       | 是               | 是               |
| Grafana Loki  | 日志存储后端       | 聚合、存储和查询日志             | 需配合 Grafana   | 是               |

不能进行以下错误比较：

```
Pino 和 Sentry 二选一
OpenTelemetry 和 Loki 二选一
Pino 和 OpenTelemetry 二选一
```

因为它们可能处于不同层级。

正确的组合可以是：

```
Pino + Sentry
Pino + Better Stack
Pino + OpenTelemetry + Loki
语言原生日志库 + OpenTelemetry + 商业平台
应用 SDK + Sentry
Grafana Alloy + Loki + Grafana
```

# 5. 推荐组合模式

## 模式一：快速错误监控

```
应用
  ↓
Sentry SDK
  ↓
Sentry
```

适合：

- 中小型应用
- MVP
- Web、移动端或桌面端产品
- 主要关注线上异常
- 不希望维护日志基础设施

特点：

- 部署简单
- 错误定位效率高
- 维护成本低
- 平台依赖相对明显

---

## 模式二：集中式日志平台

```
应用日志库
  ↓
Better Stack
```

适合：

- 多个后端服务
- 服务器、容器和定时任务
- 需要集中搜索日志
- 需要实时查看日志流
- 不希望自建日志系统

特点：

- 搜索和集中管理方便
- 日志来源兼容性强
- 需要控制日志量和托管费用

---

## 模式三：厂商中立的可观测性架构

```
应用日志库或 OpenTelemetry SDK
  ↓
OpenTelemetry Collector
  ↓
Sentry / Better Stack / Loki / 其他后端
```

适合：

- 中大型项目
- 多语言服务
- 微服务
- 未来可能更换供应商
- 需要日志、追踪和指标统一

特点：

- 扩展性强
- 后端可替换
- 配置和维护复杂度较高

---

## 模式四：完全自托管

```
应用日志库
  ↓
Grafana Alloy 或 OpenTelemetry Collector
  ↓
Grafana Loki
  ↓
Grafana
```

适合：

- 数据不能发送给第三方
- 需要自主管理存储
- 日志量较大
- 已有 Grafana 或 Kubernetes 环境
- 团队具备运维能力

特点：

- 控制权高
- 基础设施和运维成本高
- 需要自行处理鉴权、备份和扩容

---

## 模式五：Node.js 结构化日志

```
Node.js 应用
  ↓
Pino
  ↓
Transport 或 Collector
  ↓
目标日志平台
```

适合：

- Node.js 后端
- TypeScript 服务
- 需要高质量 JSON 日志
- 后续可能更换日志平台

Pino 只负责第一段，不应被视为完整日志系统。

---

# 6. Codex 选型决策流程

Codex 在接入日志系统前，应当依次完成以下判断。

## 第一步：判断主要目标

### 目标是快速发现和定位应用错误

选择：

```
Sentry
```

### 目标是集中收集和搜索服务器日志

选择：

```
Better Stack
```

### 目标是建立厂商中立的数据采集标准

选择：

```
OpenTelemetry
```

然后再选择一个存储后端。

### 目标是自托管并掌控日志数据

选择：

```
Grafana Loki + Grafana
```

### 项目是 Node.js，需要本地结构化日志库

选择：

```
Pino
```

然后连接 Sentry、Better Stack、Loki 或 OpenTelemetry。

---

## 第二步：判断项目规模

### 简单单体应用

优先：

```
语言原生日志库 + Sentry
```

或：

```
语言原生日志库 + Better Stack
```

一般不需要先部署 OpenTelemetry Collector 和 Loki 集群。

### 多服务项目

优先考虑：

```
统一日志规范
+ OpenTelemetry
+ 集中式日志后端
```

### 大规模容器或 Kubernetes 项目

优先考虑：

```
OpenTelemetry Collector 或 Grafana Alloy
+ Loki 或商业可观测性平台
```

---

## 第三步：判断运维能力

### 没有专职运维人员

优先使用：

```
Sentry
Better Stack
其他托管平台
```

### 有成熟运维团队

可以考虑：

```
OpenTelemetry
Grafana Loki
Grafana
对象存储
自建告警系统
```

不要仅因为开源软件无需许可证费用，就认定自托管成本更低。

自托管仍然需要承担：

- 服务器
- 存储
- 网络
- 备份
- 升级
- 安全
- 扩容
- 故障恢复
- 人力维护

---

## 第四步：判断数据要求

### 日志允许上传第三方服务

可以选择托管平台。

### 日志包含敏感数据或受数据地域限制

需要：

- 优先考虑自托管
- 评估供应商的数据区域
- 配置日志脱敏
- 控制数据保留周期
- 禁止上传不必要的用户数据
- 评估合规协议

---

## 第五步：判断是否需要 OpenTelemetry

满足以下任意多项时，应考虑引入 OpenTelemetry：

- 存在多个服务
- 存在多种编程语言
- 需要分布式追踪
- 需要统一日志、指标和调用链
- 未来可能更换平台
- 需要同时输出到多个后端
- 需要在采集层统一脱敏、采样和路由

只有一个简单应用，且短期只需要错误监控时，不必为了“架构完整”强行引入 OpenTelemetry。

---

# 7. 通用默认推荐

在没有特殊限制时，可以采用以下默认规则：

|                                    |                          |
| ---------------------------------- | ------------------------ |
| 项目情况                           | 默认优先方案             |
| 小型应用，需要快速上线错误监控     | Sentry                   |
| 后端或服务器日志较多，需要集中搜索 | Better Stack             |
| 多语言、微服务、分布式系统         | OpenTelemetry + 日志后端 |
| 必须自托管或数据不能出域           | Grafana Loki + Grafana   |
| Node.js 项目需要本地 Logger        | Pino                     |
| Node.js 小型应用                   | Pino + Sentry            |
| Node.js 日志密集型服务             | Pino + Better Stack      |
| Node.js 自托管环境                 | Pino + Collector + Loki  |
| 已经拥有成熟可观测性平台           | 接入现有平台，不重复建设 |

# 8. 所有项目都应遵守的日志规范

无论最终使用哪个平台，业务代码都不应到处直接依赖具体供应商 SDK。

建议提供统一日志接口：

```
logger.debug()
logger.info()
logger.warn()
logger.error()
logger.fatal()
```

业务代码调用统一 Logger，再由适配器决定输出到哪里：

```
业务代码
    ↓
统一 Logger 接口
    ↓
Console Adapter
Sentry Adapter
OpenTelemetry Adapter
Better Stack Adapter
Loki Adapter
```

这样做的目的包括：

- 降低供应商绑定
- 统一日志字段
- 统一脱敏
- 便于测试
- 便于替换平台
- 避免业务模块直接依赖多个 SDK

---

# 9. 日志格式要求

生产环境优先使用结构化日志，不要只输出无法解析的自然语言字符串。

推荐格式：

```
{
  "timestamp": "2026-07-18T12:00:00.000Z",
  "level": "error",
  "service": "example-service",
  "environment": "production",
  "version": "1.4.0",
  "event": "payment_request_failed",
  "message": "Payment request failed",
  "request_id": "request-id",
  "trace_id": "trace-id",
  "duration_ms": 832,
  "error_code": "PAYMENT_TIMEOUT"
}
```

推荐公共字段：

```
timestamp
level
message
event
service
environment
version
request_id
trace_id
feature
operation
duration_ms
error_code
```

根据实际需求选择：

```
anonymous_user_id
session_id
http_method
http_route
status_code
dependency
retry_count
```

---

# 10. 日志级别规范

## debug

用于开发和临时诊断。

例如：

```
缓存读取结果
内部变量状态
详细执行分支
```

生产环境通常关闭或采样。

## info

用于记录正常的重要业务事件。

例如：

```
服务启动
任务完成
用户完成关键流程
配置加载成功
```

## warn

用于记录尚未导致失败，但需要关注的异常状态。

例如：

```
发生重试
使用降级方案
配置缺失但使用默认值
响应时间接近阈值
```

## error

用于记录操作失败或需要处理的异常。

例如：

```
请求失败
数据库操作失败
第三方服务调用失败
未捕获异常
```

## fatal

用于记录导致进程无法继续运行的严重故障。

例如：

```
关键配置完全缺失
数据库初始化失败
进程即将退出
```

---

# 11. 安全和隐私要求

任何日志方案都必须默认过滤：

```
密码
API Key
Access Token
Refresh Token
Cookie
Authorization Header
银行卡信息
身份证件信息
完整手机号
完整邮箱地址
私密请求体
数据库连接字符串
用户上传的私密内容
```

禁止：

```
logger.info("token", token)
logger.error(JSON.stringify(request.headers))
logger.debug(userPassword)
```

应当在统一日志层实现：

- 字段白名单
- 敏感字段屏蔽
- 正则脱敏
- 请求体大小限制
- 错误对象清洗
- 用户标识匿名化
- 环境变量过滤

前端代码中不得嵌入具有私密管理权限或无限制写入权限的服务令牌。

---

# 12. 性能和成本控制

日志系统应当配置：

- 日志级别
- 采样率
- 批量发送
- 异步发送
- 缓冲区上限
- 超时
- 重试上限
- 数据保留周期
- 单条日志大小限制
- 高频事件限流

禁止在高频循环中无条件写入大量日志：

```
每一帧写日志
每一个字符输入写日志
每一个数据库行写日志
每一次轮询写完整响应
```

对于高频成功事件，可以：

- 采样
- 聚合为指标
- 只记录失败
- 记录统计结果
- 调低到 debug 级别

日志系统出现故障时，不应导致核心业务一起崩溃。

# 13. 错误做法

## 错误一：只使用 console.log

问题：

- 字段不统一
- 难以搜索
- 难以远程查看
- 无法稳定关联请求
- 容易泄露敏感信息
- 难以建立告警

## 错误二：业务代码直接绑定平台

例如：

```
每个业务模块直接调用 Sentry
每个模块自行发送 Better Stack HTTP 请求
每个模块自行构造 Loki 数据
```

问题：

- 难以更换平台
- 日志格式不一致
- 脱敏规则分散
- 测试困难

## 错误三：同时接入多个平台但不定义职责

例如：

```
同一条错误同时发送到三个平台
不同平台字段完全不同
不知道哪个平台是主要数据源
```

应当明确：

```
错误监控由谁负责
原始日志由谁负责
调用链由谁负责
告警由谁负责
长期存储由谁负责
```

## 错误四：为了“高级”直接引入完整可观测性架构

对于简单项目，直接部署：

```
OpenTelemetry Collector
Loki
Grafana
Prometheus
Tempo
对象存储
告警系统
```

可能造成明显的过度设计。

## 错误五：把日志当成数据库

日志不应成为核心业务数据的唯一存储位置。

订单、用户、任务结果等业务事实，仍应存储在正式数据库中。

# 14. Codex 最终输出要求

Codex 为具体项目选择日志方案时，必须输出以下内容：

```
1. 项目技术栈
2. 应用类型
3. 部署环境
4. 主要日志需求
5. 日志量预估
6. 数据隐私要求
7. 团队运维能力
8. 选择的日志生成库
9. 选择的采集或传输方式
10. 选择的存储和查询平台
11. 是否需要 OpenTelemetry
12. 选择该方案的理由
13. 未选择其他方案的理由
14. 日志字段规范
15. 脱敏规则
16. 采样和保留策略
17. 故障降级策略
18. 接入目录和代码位置
19. 本地与生产环境差异
20. 验证和测试方法
```

不得只根据开发语言直接决定方案。

例如：

```
Node.js 项目不代表一定使用 Sentry
使用 Pino 不代表已经拥有日志平台
使用 OpenTelemetry 不代表已经拥有日志存储
使用 Loki 不代表已经完成采集和可视化
```

# 15. 最终决策总结

## 选择 Sentry

当核心需求是：

```
快速定位应用错误
关联用户、请求、堆栈和操作过程
```

## 选择 Better Stack

当核心需求是：

```
集中收集不同服务的日志
实时查看和快速搜索原始日志
```

## 选择 OpenTelemetry

当核心需求是：

```
统一采集标准
降低供应商绑定
连接多个可观测性后端
```

## 选择 Grafana Loki

当核心需求是：

```
自托管
大规模日志存储
数据自主可控
```

## 选择 Pino

当核心需求是：

```
在 Node.js 应用内部生成高质量结构化日志
```

Pino 需要与日志平台组合使用。

最终应根据项目实际约束选择，而不是固定要求所有项目使用同一套方案。
