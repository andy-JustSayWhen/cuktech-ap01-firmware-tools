# `0x0040d4..0x0040df` 文件系统重启同步通知节点

返回总账：[`AP01 原厂固件逐字节与逐指令通读总账`](../原厂固件逐字节与逐指令通读总账.md)

## 1. 覆盖结论

本段连续覆盖 12 字节，是一个优先级为 0 的重启通知节点。它在系统启动时插入全局重启
通知链；系统重启或断电时，节点回调遍历所有任务的文件描述符并同步尚未写入底层存储的
文件内容。系统仅停机时，回调不执行文件同步。

| 项目 | 值 |
| --- | --- |
| 文件范围 | `0x0040d4..0x0040df` |
| 复制后的运行内存范围 | `0x62fc35c0..0x62fc35cb` |
| 原厂结构 | `struct notifier_block`（保存通知回调、后继节点和优先级的结构），共 12 字节 |
| 用途 | 文件系统重启同步通知节点 |
| 未解释字节 | 0 |

本文是该通知节点初值、注册方式和回调能力边界的唯一事实原文；后续文档只引用本路径。
原厂二进制没有保留本静态对象的符号名，因此本文按已证实用途命名，不虚构源码变量名。

## 2. 十二字节逐字段读取

原始字节为：

```text
b8 b4 03 a0  00 00 00 00  00 00 00 00
```

按原厂通知节点的三个连续 32 位字段解释如下：

| 文件偏移 | 结构内偏移 | 长度 | 小端值 | 字段与初始状态 |
| --- | ---: | ---: | --- | --- |
| `0x0040d4..0x0040d7` | `+0x00` | 4 | `0xa003b4b8` | `notifier_call`：文件系统重启同步回调 |
| `0x0040d8..0x0040db` | `+0x04` | 4 | `0x00000000` | `next = 0`：注册前没有后继节点 |
| `0x0040dc..0x0040df` | `+0x08` | 4 | `0x00000000` | `priority = 0`：通知优先级为 0 |

公开系统的同类结构也按“回调、后继、优先级”排列，见
[`notifier.h`](https://github.com/apache/nuttx/blob/c4f641991ae5a3edda9ddbfa5a7d3e76e8ae87e5/include/nuttx/notifier.h)。
固件注册代码分别读取本段 `+0x08`、写入 `+0x04`，通知代码分别读取 `+0x00`、`+0x04`，
从二进制侧逐字段验证了这三个字段的归属，而不是只按相似结构猜测。

## 3. 启动注册链路

系统启动函数 `0xa0029050..0xa0029074` 执行以下实际顺序：

1. 关闭机器中断并保存原状态；
2. 以 `gp`（保存全局数据起点的寄存器）加 256 取得本段运行地址 `0x62fc35c0`；
3. 读取本节点 `+0x08` 的优先级；
4. 从 `0x62fc6c00` 取得全局通知链首节点，按优先级从高到低寻找插入点；
5. 把原插入点写入本节点 `+0x04`，再把本节点写入链首或前一节点；
6. 恢复机器中断状态。

固件采用的全局链和注册行为与公开系统中的 `g_reboot_notifier_list` 及注册函数一致，见
[`reboot_notifier.c`](https://github.com/apache/nuttx/blob/c4f641991ae5a3edda9ddbfa5a7d3e76e8ae87e5/sched/misc/reboot_notifier.c)。

## 4. 通知分发与动作值

原厂通知分发函数 `0xa00264d6..0xa002651c` 从 `0x62fc6c00` 读取链首。对每个节点，它先保存
`+0x04` 后继地址，再以“当前节点、动作值、附加数据”三个参数调用 `+0x00` 回调，然后继续
访问已保存的后继节点。链为空时直接返回。

两个实际调用点给出动作值：

| 调用点 | 动作值 | 已证实含义 |
| --- | ---: | --- |
| `0xa0056e1c..0xa0056e1e` | 1 | 系统重启 |
| `0xa002aa60..0xa002aa64` | 2 | 系统停机 |

公开系统把动作值 1、2、3 分别规定为重启、停机、断电，见
[`reboot_notifier.h`](https://github.com/apache/nuttx/blob/c4f641991ae5a3edda9ddbfa5a7d3e76e8ae87e5/include/nuttx/reboot_notifier.h)。
本节点回调 `0xa003b4b8..0xa003b4e2` 清除动作值的第 1 位后与 1 比较，因此：

- 动作值 1：执行同步；
- 动作值 2：不执行同步；
- 动作值 3：执行同步。

原厂当前可达调用点已经直接覆盖重启和停机；回调本身明确兼容断电动作，但本段调查没有
发现直接传入动作值 3 的固件调用点，故不宣称本机界面存在单独的断电入口。

## 5. 文件同步回调闭合

动作值符合条件时，`0xa003b4c8..0xa003b4d2` 把 `0xa0027ffc` 作为任务遍历回调，调用
`0xa00265ae`。后者在保护任务表的临界区内逐项读取任务控制块，并对每个非空任务调用该回调。

任务回调 `0xa0027ffc..0xa002806e` 的控制流是：

1. 从任务控制块取得任务组；任务组为空时返回；
2. 确认任务组文件表有效，并为遍历期间增加引用；
3. 按文件表行数循环，每行固定检查 6 个文件描述符；
4. 对每个存在的文件对象增加临时引用；
5. 调用 `0xa0025888`：普通文件走操作表中的同步入口，挂载点文件走对应的文件系统同步入口；
6. 调用 `0xa0027d54` 释放文件对象临时引用；
7. 全部行处理完成后，调用 `0xa0027cc0` 释放任务组文件表引用。

公开系统的 `task_fssync` 和 `sync` 也采用“遍历所有任务、逐文件描述符同步”的同一职责，见
[`fs_files.c`](https://github.com/apache/nuttx/blob/c4f641991ae5a3edda9ddbfa5a7d3e76e8ae87e5/fs/inode/fs_files.c)。
固件的任务组布局和每行文件数来自本固件配置，因此本文以固件指令中的实际值 6 为准。

## 6. 能力边界

本节点只负责在重启和断电通知阶段发起文件内容同步。它不负责触发重启、不等待存储器物理
掉电、不关闭文件描述符，也不处理动作值 2 的单纯停机。回调统一返回 0，因此它不会阻止
通知链中的后续节点继续执行。
