# `0x0049f4..0x004a83` 显示帧缓冲设备对象

返回总账：[`AP01 原厂固件逐字节与逐指令通读总账`](../原厂固件逐字节与逐指令通读总账.md)

## 1. 覆盖结论

本段连续覆盖 144 字节，是原厂屏幕的显示帧缓冲设备对象。它提供屏幕和画面内存参数，
保存上层注册对象、传输同步量、后台工作项、显示中断引脚、初始化标志和动态画面内存地址。

| 项目 | 值 |
| --- | --- |
| 文件范围 | `0x0049f4..0x004a83` |
| 复制后的运行内存范围 | `0x62fc3ee0..0x62fc3f6f` |
| 可见分辨率 | 320 × 240 |
| 虚拟画面高度 | 480，即两幅 240 行画面 |
| 每行字节数 | 640 |
| 每个像素 | 16 位 |
| 颜色布局 | `RGB565`（每个像素用 16 位，红、绿、蓝分别占 5、6、5 位） |
| 动态画面内存长度 | `0x4b000`，即 307,200 字节 |
| 显示中断引脚 | 23 |
| 注册路径 | `/dev/fb0` |
| 连续覆盖字节 | 144 |

`0x004a80..0x004a83` 的四个零字节是本对象 `+0x8c` 的动态画面内存地址初值。
下一份非零记录从 `0x004a84` 开始，因此本段边界没有吞入下一个对象。

各行长度合计 144 字节。`+0x5c..+0x67` 和 `+0x84..+0x88` 已完整保存原始边界和零值，
但没有有效指令或原厂私有头文件证明其名称，因此明确保留未定。

函数表和两份参数结构的字段顺序，由原厂采用版本
[`fb.h`](https://github.com/apache/nuttx/blob/271f76590f22/include/nuttx/video/fb.h#L488-L522)
与同文件的
[函数表定义](https://github.com/apache/nuttx/blob/271f76590f22/include/nuttx/video/fb.h#L689-L850)
核准。当前配置未编入颜色表、硬件光标、局部更新、垂直同步和叠加层的可选入口，
因此函数表恰好是 11 个四字节槽，即 44 字节。24 字节后台工作项的结构定义只引用
[物理旋钮底层输入对象](00498c-0049f3-物理旋钮底层输入对象.md)第 2 节，本文不重复定义。

## 3. 两个参数函数的逐指令结果

`0xa013394e..0xa01339ca` 依次：

1. 校验设备对象和输出地址均非空；
2. 写出格式编号 11、横向 320、纵向 240、一个颜色平面；
3. 把完整 8 字节返回值复制到对象 `+0x2c` 的副本；
4. 返回成功。

格式编号 11 与官方同版头文件的
[`RGB16_565`](https://github.com/apache/nuttx/blob/271f76590f22/include/nuttx/video/fb.h#L62-L68)
相等，与本段每像素 16 位的直接证据一致。

`0xa01339cc..0xa0133a5e` 依次：

1. 校验设备对象、输出地址和画面编号地址；
2. 从运行地址 `0x62fc3f6c`，即对象 `+0x8c`，取画面内存起点；
3. 写出长度 `0x4b000`、每行 640 字节、显示编号 0、每像素 16 位、虚拟尺寸 320 × 480，
   横向与纵向偏移保持为 0；
4. 把完整 28 字节返回值复制到对象 `+0x34` 的副本；
5. 返回成功。

`320 × 240 × 2 = 153,600` 字节，`307,200` 正好容纳两幅完整画面；这与虚拟高度
480 和后方依据纵向偏移选择待发画面的指令相互印证。

## 4. 启动申请、中断和注册

`0xa0056062..0xa00567a2` 对本对象的直接处理顺序是：

1. 读取 `+0x89`，若已初始化则拒绝重复执行；
2. 读取 `+0x8c`，若动态画面内存地址已非空则拒绝重复申请；
3. 从系统内存池取得一段 32 字节对齐且长度为 307,200 字节的连续区域，把起点写入 `+0x8c`；
4. 把画面内存末尾地址提供给后方显示传输状态；
5. 把 `+0x80` 的引脚 23 设为输入，配置中断条件 10，登记入口 `0xa0134a84`
   并把本对象地址作为回调参数；
6. 完成硬件初始化后把 `+0x89` 置 1；
7. 申请上层显示字符设备对象，通过 `+0x00` 取屏幕整体参数，按平面数建立队列，
   生成并注册 `/dev/fb0`；
8. 注册成功后把上层对象地址写入 `+0x28`，供中断和后台发送路径使用。

上层通用注册流程可与同版官方
[`fb.c`](https://github.com/apache/nuttx/blob/271f76590f22/drivers/video/fb.c)
对照；原厂镜像内又保留了私有源码路径 `lcd/fb_dev.c`，因此本文仅用通用源码核准公开结构和注册语义，
不用它替代原厂私有显示发送实现。

## 5. 画面队列与传输闭环

1. 引脚 23 的中断入口 `0xa0134a84..0xa0134b0e` 通过对象 `+0x28` 检查待发画面记录数；
2. 有待发记录时，它使用对象 `+0x68` 的 24 字节工作项，把后台入口
   `0xa0134b10` 和本对象地址排入工作队列；
3. 后台入口 `0xa0134b10..0xa0134cf0` 取出一条 28 字节画面记录，尝试取得
   `+0x50` 的同步量，再用对象 `+0x34` 中的画面起点、每行字节数和记录中的纵向偏移
   算出本次发送起点；
4. 该入口完成显示传输参数设置并启动硬件传输，然后把同步量计数明确重置为 0；
5. 传输完成入口 `0xa0134d02` 向同一同步量归还一次，再从上层队列移除已发送的
   28 字节画面记录，形成“取待发画面→发送→完成后移除”的闭环。

这条闭环中，同步量初值 1 表示可以开始一次传输；后台入口取得后为 0，完成入口归还后回到 1。
固件中的尝试取得、重置和归还三个实际函数都只读写 `+0x50..+0x5b`，这也是不把后续
`+0x5c..+0x67` 猜成传输同步量字段的直接理由。

## 6. 能力边界

本段证明显示设备的静态对象布局、画面内存参数、启动申请、设备注册、中断排队和完成归还链路。
它不证明屏幕面板的具体型号，也不把后方尚未连续通读的显示寄存器配置、图形库或页面绘制代码登记为已掌握。
镜像内没有可用的原厂私有对象定义，两段无访问证据的零值区域仍保留未定。
