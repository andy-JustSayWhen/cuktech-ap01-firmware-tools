## 2. 默认协商组表

`0x005fd4..0x005fe5` 是九个 16 位值组成的 `ssl_preset_default_groups`（默认协商组表）；
`0x005fe6..0x005fe7` 是为下一张 4 字节对齐对象保留的两个零填充字节。

| 顺序 | 原始编号 | 原厂组名 | 直白含义 |
| ---: | ---: | --- | --- |
| 0 | 29 | X25519 | 使用 25519 曲线完成临时密钥协商 |
| 1 | 23 | secp256r1 | 使用 256 位标准椭圆曲线 |
| 2 | 24 | secp384r1 | 使用 384 位标准椭圆曲线 |
| 3 | 30 | X448 | 使用 448 曲线完成临时密钥协商 |
| 4 | 25 | secp521r1 | 使用 521 位标准椭圆曲线 |
| 5 | 26 | brainpoolP256r1 | 使用 256 位 Brainpool 曲线 |
| 6 | 27 | brainpoolP384r1 | 使用 384 位 Brainpool 曲线 |
| 7 | 28 | brainpoolP512r1 | 使用 512 位 Brainpool 曲线 |

源码中的 IANA（负责统一分配网络编号的国际登记机构）编号顺序和当前镜像完全相同，也表明
原厂编译时没有把五个有限域组加入本表。

## 3. 两张默认签名算法表

两张表都由十个 16 位值组成，末项 0 是结束标记。每个非零编号的高字节表示摘要算法，低
字节表示签名算法或完整签名方案；精确组合如下。

| 文件偏移 | 原厂表名 | 逐项编号 |
| --- | --- | --- |
| `0x005fe8..0x005ffb` | `ssl_preset_default_sig_algs` | `0x0403, 0x0503, 0x0603, 0x0806, 0x0805, 0x0804, 0x0601, 0x0501, 0x0401, 0` |
| `0x005ffc..0x00600f` | `ssl_tls12_preset_default_sig_algs` | `0x0603, 0x0806, 0x0601, 0x0503, 0x0805, 0x0501, 0x0403, 0x0804, 0x0401, 0` |

编号语义按原厂源码为：

- `0x0403/0x0503/0x0603`：椭圆曲线签名分别配合 256、384、512 位安全散列；
- `0x0804/0x0805/0x0806`：带随机盐填充的 RSA（用一对公开和私有密钥签名的算法）分别配合
  256、384、512 位安全散列；
- `0x0401/0x0501/0x0601`：传统填充的 RSA 分别配合 256、384、512 位安全散列；
- `0`：结束标记。

两张表包含相同的九种非零组合，但优先顺序不同：通用表先列三个椭圆曲线组合；仅使用
传输层安全协议 1.2 版本的表则按 512、384、256 位摘要强度分组排列。

## 4. 原厂配置分支

安全通信默认配置入口 `0xa018cc50` 的直接指令关系是：

1. `0xa018ccdc` 把四个版本字节设为 `3, 3, 3, 3`；
2. `0xa018ccf8` 读取这四字节并与 `0x03030303` 比较；
3. 四字节相等时，`0xa018cd82..0xa018cd8a` 选择仅适用于 1.2 版本的第二张签名算法表；
4. 不相等时，`0xa018cd0c..0xa018cd14` 选择通用签名算法表；
5. 两条分支随后都把默认协商组表写入配置对象内偏移 132，并把签名算法表写入偏移 124。

芯片厂同版本源码的配置结构把这两个位置对应的成员命名为 `sig_algs`（允许的签名算法表）
和 `group_list`（允许的协商组表），其默认配置分支也按是否只启用 1.2 版本选择上述两张表。

## 5. 能力边界

- 已闭合：全部 60 个源字节、三张表的精确边界、逐项编号、两个结束标记、两字节对齐填充、
  配置对象内的保存位置和版本分支选择。
- 表中出现某个算法只证明原厂允许它参与协商，不证明每次连接都会选中它；最终选择还取决于
  对端共同支持项、证书类型和握手结果。
- 本段没有提前解释 `0x006010` 起的全局状态；该地址由另一条独立调用直接使用。
