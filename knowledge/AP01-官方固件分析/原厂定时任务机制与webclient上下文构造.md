# 原厂定时任务机制与 webclient 上下文构造（独立调度取证）

固件基线：`ap01-1.0.2_0031`（XIP 基址 0x9FFFF000）。本文回答两个问题：第三方功能如何注册**完全独立于天气任务**的周期定时器；如何在没有天气任务参与时**自行构造 webclient 上下文**发起 HTTP 请求。 libuv（一个事件循环库，负责定时器和异步事件的调度）的基本概念见《系统软件、页面与图形资源.md》，本文不重复定义，只记录本固件内的实际实现。

## 1. 定时器三件套（可直接复用的原厂函数）

| 函数地址 | 语义 | 调用约定 |
| --- | --- | --- |
| `0xa009b376` | `timer_init(loop, timer)` | a0=事件循环指针，a1=定时器结构（至少 0x50 字节） |
| `0xa009b3b6` | `schedule(timer, cb, delay_lo, delay_hi, arg1, arg2)` | a0=定时器，a1=回调，a2/a3=64 位毫秒延时，a4/a5=回调参数（本固件未用，恒 0） |
| `0xa01ab0c2` | `cancel(timer)` | a0=定时器；未排队时无任何副作用直接返回 |

`schedule` 是**重启式单发**预约：回调触发后需在回调尾部再次预约自身实现周期。反汇编（`0xa009b3ce` 起）证实：读 `timer+0x2c` 状态后，若 bit2（已排队）置位，先内部调用 `cancel`（`0xa009b3ea` 处 `jalr` 至 `0xa01ab0c2`）再重新插入，因此对已排队定时器重复预约不会失败；-22 返回值只出现在回调指针为空（`0xa009b3dc`）或关闭中状态。天气回调（`0xa00b6ca6`..`0xa00b6ff0`）全函数仅一处 `jal 0xa009b3b6`（尾部 `0xa00b6fe4`），无任何 cancel 调用——回调尾部直接再预约即原厂模式。`cancel` 对未排队定时器安全（已验证跳转至 `0xa01ab214` 直接返回）。

### 1.1 定时器结构布局（0x58 字节，init 后有效）

| 偏移 | 内容 |
| --- | --- |
| +0x04 | 所属 loop 指针 |
| +0x08 | 对象类型标记（定时器 = 0x0d，u8） |
| +0x10/+0x14 | loop 对象链表的 prev/next 节点 |
| +0x2c | 状态位：bit2 = 已排队；低 2 位 = 关闭状态 |
| +0x30 | 回调函数指针 |
| +0x34~0x3c | 定时器到期队列的链表节点 |
| +0x40/+0x44 | 64 位到期时刻 |
| +0x48/+0x4c | 回调参数（本固件不用） |
| +0x50/+0x54 | `schedule` 写入的 loop 计数快照（`0xa009b43a`/`0xa009b43c` 两处 `sw`，因此结构至少 0x58 字节） |

### 1.2 回调签名

**`cb(handle)`，handle 即定时器结构指针。** 直接证据：天气回调 `0xa00b6ca6` 入口保存入参到 s6，尾部 `0xa00b6fdc: c.mv a0, s6`（把入参作为 timer 句柄）→ `jal 0xa009b3b6` 再次预约自身。因此回调内无需任何全局状态即可拿到自己的 timer 并再预约。

### 1.3 loop 指针的获取

天气定时器是全局静态结构 `0x62fca9a8`，系统启动时由原厂初始化（初始化调用点 `0xa0070b82`，位于系统启动序列）。运行时读取 `*(void **)(0x62fca9a8 + 4)` 即得 loop 指针；用 `*(u8 *)(0x62fca9a8 + 8) == 0x0d` 验证已初始化。

### 1.4 线程上下文

UI 秒级定时器（回调 `0xa00bb5da`，1000ms，注册点 `0xa00b27e4`）与天气定时器注册于同一套机制、同一 loop。注册点与第三方载荷注入点 `0xa00b2732`（页面创建函数内，详见《ap01-1.0.2_0031-opt.bin技术实现.md》）相距 0xB2 字节，属同一函数同一执行上下文。 **结论：在页面创建路径注入的代码直接调用 timer 三件套是线程安全的，原厂在同处注册 UI 定时器即为此用法。**

### 1.5 已注册定时器的零状态探测

loop 的对象链表头：prev 槽 = loop+8，next 槽 = loop+0xc；`timer_init`（`0xa009b396`..`0xa009b398`）把 timer+0x10 **头插入**该链表（新节点成为 head->next 指向的第一个节点，原首节点后移）。遍历方法：`cur = *(loop + 0xc)`；当 `cur != loop + 8` 时，handle = `cur - 0x10`，检查 `*(u8 *)(handle + 8) == 0x0d && *(void **)(handle + 0x30) == 目标回调`，随后 `cur = *(cur + 4)`。头插入只影响节点顺序，不影响该遍历的成员判断。用途：无需任何可写全局变量即可判断"自己的定时器是否已注册"，规避只读载荷区限制（见第 3 节）。

## 2. webclient 上下文的手工构造

天气回调不调用任何 create 函数：webclient 上下文是** 116 字节（0x74）栈结构**，memset 清零后按以下字段填充即可交给 `fw_webclient_perform`（0xa00d86ba）。构造证据为天气回调 `0xa00b6d60` 起的初始化序列。

| 偏移 | 值 | 说明 |
| --- | --- | --- |
| +0x00 | 0（u8） | |
| +0x04 | 指向 `"GET"` 的指针 | 原厂常量在 0xa01ed934；自备等价字符串亦可 |
| +0x08 | URL 指针 | 请求地址 |
| +0x24 | 超时秒数 | 原厂天气用 5 |
| +0x30 | 4096 字节堆缓冲指针 | 回调内 fw_malloc，用毕 fw_free |
| +0x34 | 4096 | 缓冲大小 |
| +0x3c | sink 回调指针 | 数据接收回调 |
| +0x40 | sink_arg | 传给 sink 的用户参数 |
| +0x60 | HTTP 状态（出参） | |
| +0x6c | work_state | 请求间清零 |
| +0x70 | 1（u8） | |

其余字段清零即可。现有 `ap01_agents_download_package`（result_loader.c）对 URL/超时/sink/sink_arg 的设置偏移与此表一致，可原样复用。

## 3. 只读载荷区的可写状态禁令（现有构建的既成事实）

`result_loader.ld` 只声明 `PAYLOAD (rx)` 一个区：链接器把 `.data`/`.bss` 放到 PAYLOAD 尾部 flash 地址（见 agents-sync.map：`.data 0xa024e3fc`、`.bss 0xa024e404`），而 `objcopy -j .payload` 不提取它们。后果：**载荷内一切带初值的静态变量读到的初值是 flash 原始内容（初值丢失），一切运行时写静态变量的操作都落在 flash 上（不生效）**。实测证据（2026-08-20，V2 个性化固件 `ap01-1.0.2_0031-opt-personalized.bin`）：`.data` 落位文件偏移 `0x24f3fc` 恰在载荷末尾之后，最终固件在该处保留原厂 GIF 数据字节 `30 83 3e 6a`，即 `agents_transport_mode` 运行时实际读到 1782481712（既非 0=天气模式也非 1/2），V2 包装函数按"非天气模式"分支直接执行看板下载、跳过原厂天气请求。这是"静态可写状态在只读载荷中不可用"的直接运行时证据。第二条实测（同日同文件）：`.bss` 中 `download_disabled`（编译期初值 0）落位文件偏移 `0x24f404`，运行时实读原厂字节 `63 1c 2a 50` ≠ 0，`ap01_agents_download_package` 在入口即返回 `ERR_INVAL`。即旧 V2 固件两条网络路径全灭：天气请求被 `agents_transport_mode` 幻读整体跳过、看板下载被 `download_disabled` 幻读永久阻断——"等待首次同步"的完整解释。修复：下载禁用开关改为 `#if` 编译期判断（见 DESIGN 9.5 第 4 条）。因此在载荷代码里：

1. 禁止新增任何依赖运行时写入的静态变量（含初值读取）；
2. 可写状态一律 `fw_malloc` 分配、指针经参数或结构自身传递（定时器回调的 handle 参数、sink_arg 即为此设计）；
3. "一次性初始化"判断用第 1.5 节的链表探测，不用布尔标志。

## 4. 天气任务真实死亡位置（本次事故取证）

抓包显示：设备以约 30 次/秒频率发送 ARP 广播探测两个未在固件二进制中出现的地址，说明这两个地址来自运行环境配置的失效 DNS；无任何 UDP/TCP 数据包发出；桥接服务请求数为 0。结合《通信、存储与更新与恢复.md》第 7 节：天气回调在位置编号获取后的 URL 组装/DNS 环节因 DNS 服务器不可达而阻塞或提前退出，看板取包（当时挂在天气任务 webclient 调用之后）从未获得执行机会。该环境故障是"等待首次同步"的导火索；触发链设计（取包完全寄生天气任务）是放大器。修复方向见 DESIGN"独立取包定时器"章节。
