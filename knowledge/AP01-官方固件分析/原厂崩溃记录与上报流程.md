# 原厂崩溃记录与上报流程

## 1. 调查对象与结论

调查对象为原厂 `1.0.2_0031` 固件。文件到运行地址仍按项目既有映射增加 `0x9ffff000`。

原厂已经包含完整的异常现场生成、崩溃分区、持久开关、米家命令入口和崩溃上报路径。后续异常取证应先复用这些能力，不得先写新的崩溃处理程序。

## 2. 异常现场生成

运行地址 `0xa002ab42` 起的异常入口读取 `mepc` 与 `mtval`，并使用以下原厂文字：

| 固件偏移 | 运行地址 | 原厂文字与作用 |
| ---: | ---: | --- |
| `0x1b9720` | `0xa01b8720` | 输出异常类型、原因值、程序地址和故障地址 |
| `0x1b975c` | `0xa01b875c` | 输出异常编号 |
| `0x1b96d2` | `0xa01b86d2` | 标记原厂崩溃记录格式 |
| `0x1b942c` | `0xa01b842c` | 输出断言发生时的程序地址 |
| `0x1b9590` | `0xa01b8590` | 检查栈指针是否落在任务栈内 |

`0xa002a624` 起继续输出保存的寄存器；`0xa002a740` 起检查任务栈范围；同一区域还存在任务列表、栈内容和回溯输出。该流程能提供此前设置页失败缺少的异常地址与栈证据。

## 3. 崩溃分区

原厂在 `0xa00592b2` 加载 `/dev/crash`，随后调用 `0xa019c97c` 完成文件系统挂载。它与 `/dev/ota`、`/dev/reserve`、`/dev/resource` 位于同一原厂分区挂载流程，不是本项目新增路径。

原厂崩溃上报路径在 `0xa006d8ba` 后检查崩溃分区状态。分区存在时，`0xa006d962` 把 `_otc.crash` 写入上报消息并继续组装数据；失败文字分别位于 `0xa01c5d50`、`0xa01c5d70` 和 `0xa01c5da0`。

## 4. 持久开关与米家命令

原厂持久键 `coredump_flag` 位于 `0xa01bf4d0`。启动读取路径 `0xa005cf66` 取得该键后调用 `0xa004ee5c`；后者在关闭中断的短临界区内把值写到运行时字节 `0x62fc6010`。

设置函数 `0xa005d40c` 只接受布尔值：更新持久键后再次调用 `0xa004ee5c`，使持久状态与当前运行状态一致。

原厂命令描述表位于文件偏移 `0x677260`：

| 字段 | 原厂值 |
| --- | --- |
| 内部名称 | `config_coredump` |
| 米家命令 | `miIO.config_coredump` |
| 处理函数 | `0xa0068018` |
| 参数数量 | `2` |

处理函数从参数描述 `0xa01b70f4` 读取键名 `coredump`，只允许数值 `0` 或 `1`，随后调用 `0xa005d40c`。命令成功后走原厂统一结果返回；解析失败或值超界时返回错误，不改变开关。

## 5. 适用范围

当前静态证据证明原厂能够启用崩溃记录并生成、保存和上报异常现场，但尚未证明：

1. 当前设备的开关初值；
2. 米家云是否把 `_otc.crash` 内容暴露给当前账号；
3. 界面卡死但没有触发处理器异常时是否生成记录；
4. 已经发生的历史卡死能否在恢复固件启动后继续上报。

因此下一步只能先在当前正常恢复固件上调用一次原厂开关命令并核对返回、在线状态、运行时间和更新状态；不得同时安装测试版本固件或再次进入设置。若原厂云端不提供记录读取结果，再调查原厂本地日志导出能力，不得把“命令成功”等同于“崩溃记录已可读取”。

## 6. 当前设备验证

在正常恢复固件上调用一次 `miIO.config_coredump`，参数为 `{"coredump":1}`。设备返回 `ok`。调用前后设备保持在线，运行时间从 573 秒连续增长到 577 秒，版本仍为 `1.0.2_0031`，更新状态保持空闲，近五分钟更新错误为 0；没有刷机或重启。

随后只读核对现有读取通道：

1. 当前账号的普通设备历史数据接口在最近七天对 `_otc.crash`、`arch_crash`、`coredump`、 `coredump_flag` 和 `reboot_reason` 均返回 0 条；同一接口能返回 15 条既有更新错误，说明查询本身有效；
2. 云端转发 `cmd.crash_coredump` 与 `local.log_path` 均接受命令，但不返回正文；
3. 局域网 54321 端口能响应原厂发现包；使用当前账号设备记录中的本地令牌发送两条加密只读请求均超时，没有取得响应正文；
4. 固件还包含 `local.query_log_enc_key`、`local.log_enc_key` 和蓝牙设备日志分段发送函数，但当前没有已经验证的蓝牙认证与日志接收工具链。

因此当前结论固定为：原厂崩溃记录开关已经被设备接受，异常现场格式和保存、上报代码存在；现有云端历史接口、云端命令返回和局域网令牌路径均不能导出正文。下一步若要取得异常地址与栈，必须先建立原厂蓝牙日志通道或硬件串口读取通道。完成该通道前，不得再次触发设置页失败。

## 7. 蓝牙日志链逐指令复查

原厂日志链的直接调用关系如下：

1. 配网任务只在消息类型 `0x100`、命令字节 `166` 时调用 `0xa011d1f4`，生成 `local.query_log_enc_key` 请求，并把 `0xa011c136` 注册为回复回调；
2. 统一消息解析器从 `0xa01b4c64` 识别 `local.log_enc_key`，读取 `derive_key` 等参数，使用原厂连接上下文准备内存日志；
3. 内存日志和文件日志都使用 2048 字节发送缓冲区，前两字节分别保存片号和总片数，每片正文最多 2046 字节；内存日志以传输类型 `17` 发送；
4. 文件路径入口 `0xa011dcca..0xa011dd32` 把最长 64 字节路径投递到配网任务，文件首片由 `0xa011f978..0xa011fbf4` 处理，后续分片由 `0xa0124d2a..0xa0124f26` 处理；
5. 内存日志后续分片由 `0xa0124f28..0xa01250a4` 处理，完成或失败后清理发送状态。

两次被动扫描没有发现正常运行的 AP01 公开可直接识别的日志服务。这只说明当时扫描窗口内没有可直接使用的广播，不能证明设备永远不广播。当前仍缺少进入原厂配网认证会话的方法、接收端服务和特征标识以及认证步骤，因此该证据没有解除第 6 节的设置页固件封停。
