# 原厂崩溃记录与上报链路

## 1. 调查对象与结论

调查对象为原厂 `1.0.2_0031` 固件。文件到运行地址仍按项目既有映射增加
`0x9ffff000`。

原厂已经包含完整的异常现场生成、崩溃分区、持久开关、米家命令入口和崩溃上报路径。后续
异常取证应先复用这些能力，不得先写新的崩溃处理程序。

## 2. 异常现场生成

运行地址 `0xa002ab42` 起的异常入口读取 `mepc` 与 `mtval`，并使用以下原厂文字：

| 固件偏移 | 运行地址 | 原厂文字与作用 |
| ---: | ---: | --- |
| `0x1b9720` | `0xa01b8720` | 输出异常类型、原因值、程序地址和故障地址 |
| `0x1b975c` | `0xa01b875c` | 输出异常编号 |
| `0x1b96d2` | `0xa01b86d2` | 标记原厂崩溃记录格式 |
| `0x1b942c` | `0xa01b842c` | 输出断言发生时的程序地址 |
| `0x1b9590` | `0xa01b8590` | 检查栈指针是否落在任务栈内 |

`0xa002a624` 起继续输出保存的寄存器；`0xa002a740` 起检查任务栈范围；同一区域还存在任务列表、
栈内容和回溯输出。该链路能提供此前设置页失败缺少的异常地址与栈证据。

## 3. 崩溃分区

原厂在 `0xa00592b2` 加载 `/dev/crash`，随后调用 `0xa019c97c` 完成文件系统挂载。它与
`/dev/ota`、`/dev/reserve`、`/dev/resource` 位于同一原厂分区挂载流程，不是本项目新增路径。

原厂崩溃上报路径在 `0xa006d8ba` 后检查崩溃分区状态。分区存在时，`0xa006d962` 把
`_otc.crash` 写入上报消息并继续组装数据；失败文字分别位于 `0xa01c5d50`、`0xa01c5d70` 和
`0xa01c5da0`。

## 4. 持久开关与米家命令

原厂持久键 `coredump_flag` 位于 `0xa01bf4d0`。启动读取路径 `0xa005cf66` 取得该键后调用
`0xa004ee5c`；后者在关闭中断的短临界区内把值写到运行时字节 `0x62fc6010`。

设置函数 `0xa005d40c` 只接受布尔值：更新持久键后再次调用 `0xa004ee5c`，使持久状态与当前
运行状态一致。

原厂命令描述表位于文件偏移 `0x677260`：

| 字段 | 原厂值 |
| --- | --- |
| 内部名称 | `config_coredump` |
| 米家命令 | `miIO.config_coredump` |
| 处理函数 | `0xa0068018` |
| 参数数量 | `2` |

处理函数从参数描述 `0xa01b70f4` 读取键名 `coredump`，只允许数值 `0` 或 `1`，随后调用
`0xa005d40c`。命令成功后走原厂统一结果返回；解析失败或值超界时返回错误，不改变开关。

## 5. 能力边界

当前静态证据证明原厂能够启用崩溃记录并生成、保存和上报异常现场，但尚未证明：

1. 当前设备的开关初值；
2. 米家云是否把 `_otc.crash` 内容暴露给当前账号；
3. 界面卡死但没有触发处理器异常时是否生成记录；
4. 已经发生的历史卡死能否在恢复固件启动后继续上报。

因此下一步只能先在当前正常恢复固件上调用一次原厂开关命令并核对返回、在线状态、运行时间
和更新状态；不得同时安装候选固件或再次进入设置。若原厂云端不提供记录读取结果，再调查原厂
本地日志导出能力，不得把“命令成功”等同于“崩溃记录已可读取”。
