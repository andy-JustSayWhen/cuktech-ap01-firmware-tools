# AP01 固件制作安全规范

## 1. 文档地位

本文汇总制作、修改、校验、安装、回退和发布 AP01 固件时必须遵守的安全规则。具体产品表现由 SPEC 系列文档规定，具体实现由 DESIGN 系列文档规定。本文只定规则，不重复操作命令。看板服务地址配置见 [`ap01-1.0.2_0031-opt.bin 技术实现第 9.3 节`](../reference/DESIGN/ap01-1.0.2_0031-opt.bin技术实现/ap01-1.0.2_0031-opt.bin技术实现.md#93-地址配置与两种固件)，个人固件制作命令见 [`AP01 刷机安装`](../reference/DESIGN/AP01刷机安装.md)。

本文是安全规则唯一依据。

固件版本与文件特征、结构和校验术语的定义见 [`AP01 固件版本、结构与校验`](AP01-官方固件分析/固件版本、结构与校验.md)，恢复层级、恢复接口和固件产物类型的原文见 [`AP01 离线恢复与救砖证据`](AP01-官方固件分析/离线恢复与救砖证据.md)，本文不重复定义。

## 2. 安全结论

“优化固件可以安装”和“设备变砖后可以恢复”是两项不同结论。

当前证据只证明：

1. 官方 `1.0.2_0031` 固件的版本和文件特征、容器结构以及文件尾恢复校验已经静态复核；
2. 固件中存在双槽、更新和恢复代码；
3. 原厂 `BFNP` 文件是应用更新包，不是已经证明可整片写回的全闪存备份；
4. 本项目尚未完成指定设备从优化固件回刷原厂固件的真机验证；
5. 尚无已经验证的厂家恢复模式、外露刷机接口或拆机硬件恢复通道。

因此，在补齐第 4、5 项之前：

- 不得承诺“绝不变砖”；
- 不得把云端原厂固件安装路径描述成离线救砖能力；
- 不得向日常使用设备安装实验固件；
- 可以继续静态分析、离线制作和自动测试；
- 日常使用设备、普通用户和发布流程中的实验固件正式安装必须停止；专用测试设备只按第 7.1 节执行。

首次实验安装只有在至少一种不依赖优化固件正常启动、联网和米家通信的恢复通道已经实测通过后才允许进行。原厂固件在线回刷还必须在同一台测试设备上完成全流程实测，才能作为发布回退方案。

“仅下载”不是只读操作；本次真机已经证明它会切换运行内容。全部实验固件和原厂恢复流程都不得调用该入口。本项目刷机必须使用 [`如何刷机`](../SOP/如何刷机.md) 中的当前项目命令，并在固件判断、完整性检查、服务检查、上传后完整回读和唯一 AP01 检查全部通过后执行。

## 4. 制作前先核对官方原版固件

开始制作前必须取得并固定一份未经修改的原厂固件。当前只允许分析以下官方原版固件：

| 项目 | 固定值 |
| --- | --- |
| 设备型号 | `njcuk.enstor.ap01` |
| 固件版本 | `1.0.2_0031` |
| 文件字节数 | 6,804,520 |
| MD5 | `469a7329d496f81ae8625c4d76ccf56d` |
| SHA-256 | `8a721fc8ef25458d415b2460e4a251e0503a82f7743fdff85b12612190e5c1cb` |
| 文件头 | `BFNP` |
| 文件尾恢复校验值 | `0x7ffd605b` |

执行规则：

1. 每次制作前通过 `python3 app/ap01_firmware.py official-firmware-info` 重新查询小米云当前版本；
2. 版本、字节数或文件指纹任一不一致，立即停止并重新分析；
3. 需要重新取得官方原版时，通过 `python3 app/ap01_firmware.py official-firmware-download` 下载、校验并只读保存；
4. 官方原版、设置备用版和不含用户地址的公开优化版按 `artifacts/firmware/README.md` 只读保存；
5. 带用户地址的个人固件、个人构建记录、登录态和本机配置不得提交；
6. 构建工具只读原厂文件，不允许原地修改；
7. 独立功能阶段每次从官方原版固件重新开始；组合固件可以从已经真机验收并由 DESIGN 固定完整文件指纹的阶段固件开始，但必须同时复核官方原版固件、阶段固件文件信息和两者间全部批准差异。

### 4.1 什么时候可以在已验收固件上继续制作

阶段固件只有同时满足以下条件，才能成为组合固件的制作输入：

1. 对应功能已经完成真机验收；
2. DESIGN 已固定文件名、字节数、两个完整文件指纹和文件尾恢复校验值；
3. 构建器逐字节比较官方原版固件与阶段固件；
4. 所有差异只落在原批准修改区间和文件尾恢复校验值；
5. 阶段固件以只读方式打开，不允许原地修改；
6. 后续每一处修改仍需单独记录地址、原字节、替换字节和修改范围。

### 4.2 原厂应用更新包能恢复什么

匹配的原厂 `BFNP` 文件必须为 R0 回刷准备，但不得称为“完整救砖包”。在 AP01 真实闪存容量、分区图和读取通道没有确认前：

1. 不得把该文件写到物理地址零；
2. 不得用该文件执行整片写入或整片擦除；
3. 不得声称它能重建第二阶段启动程序、分区表、校准区或设备专属数据；
4. 不得用其他设备的全闪存备份替代当前设备自己的备份。

全闪存备份必须由同一测试设备经已确认的只读通道取得两次一致结果，并保存在仓库外两个独立位置。两次读取一致仍不能替代恢复写入和重新启动演练。

## 5. 修改固件前必须确认的事项

### 5.1 每一处修改都要有证据

每个修改区间必须记录：

- 对应目标功能；
- 文件偏移和长度；
- 修改前预期字节；
- 修改后字节的来源；
- 对应运行地址；
- 所属程序、资源或数据区域；
- 修改范围和地址对齐检查；
- 复查方法；
- 失败时的原厂行为。

实际字节与预期字节不一致时，构建必须失败，禁止模糊匹配或继续写入。

### 5.2 默认禁止修改的区域

没有新的明确授权和已经验证的独立恢复通道时，禁止修改：

- 启动引导程序；
- 分区表和恢复记录格式；
- 当前槽与更新槽选择逻辑；
- 无线网络初始化；
- 米家通信；
- 官方在线更新和安装流程；
- 看门狗和启动早期初始化；
- 厂家恢复代码；
- 物理闪存中的第二阶段启动程序、分区表、校准区、设备身份区和密钥区；
- 一次性配置、防降级版本、安全启动配置和调试密码。

文件尾恢复校验值必须按原格式重新计算，但不得改变恢复记录的结构、位置和总文件长度。

整片擦除、使用芯片家族示例地址写入、把应用更新包写到地址零，以及在未知焊盘上试错短接，均不属于允许的恢复探索方法。

### 5.3 最小变化

1. 每个可测试阶段只引入一个能够独立验收的变化；
2. 优先调用原厂逻辑，不复制原厂已有能力；
3. 自定义逻辑失败时必须返回原厂安全行为；
4. 新功能不得占用未经证明为空闲的程序、堆、栈、资源或持久化空间；
5. 新旧功能共用数据结构时，必须检查读写是否超出允许范围；
6. 任何未确认的地址、调用约定、文件路径、容量或时序都属于阻塞项，不得用猜测补齐。

### 5.4 修改启动过程前必须确认的事项

只要修改会在用户界面创建期间执行，即使功能位于设置页，也按启动路径变更处理。

1. 修改原厂创建循环数量前，必须证明循环依赖的指针表、局部数组、对象数量、状态编号和后续遍历都能容纳新增项目；
2. 复用原厂创建入口前，必须证明每个参数的实际类型和间接层级，不能只根据寄存器位置推断；
3. 上述任一项没有直接证据时，不得增加原厂创建循环次数，也不得在启动后强行增加或覆盖对象；原厂对象树和创建过程必须保持不变，优先继续使用既有对象，无法继续使用时停止实现该功能；
4. 首次真机必须拆成“原路径空接入”和“单一新增行为”两个固件，前一个固件确认能够进入一级页面后，才允许安装后一个固件；
5. 自动测试、修改区间一致和文件尾校验不能替代启动验收；设备重启并重新上线后，立即提示用户肉眼确认是否已经离开开机动画并进入一级页面；
6. 卡在开机动画时立即停止继续叠加修改，优先通过仍可用的更新通道回刷上一份已验收固件；
7. 导致设备无法正常启动的固件，必须在固件清单和当前记录中标为禁止安装；找到并证实原因且新固件重新完成分阶段验收前不得解除；
8. 在一级窗口中插入新对象时，必须保持原厂内部对象的既有序号，或逐一证明所有读取该序号的原厂路径已经同步调整；真机回归必须覆盖每个原厂详情页的进入和返回、每个一级页面的确认操作，以及所有菜单“返回”操作；任一确认操作误入其他流程或触发重启时立即禁止该固件再次安装。
9. 包装原厂界面回调、选择原厂辅助入口或复用原厂字段时，必须同时满足 [`原厂各页面物理旋钮交互实现`](AP01-官方固件分析/原厂各页面物理旋钮交互实现.md) 第 6～8 节；原厂一级回调的版本专用调用链见该文档第 3～4 节。
10. 新的原厂直接证据使当前设计失效时，已经确认但尚未安装的固件也必须立即标为禁止安装；不得以自动测试通过或尚未发生真机故障为理由继续安装。
11. 扩大原厂状态申请时，必须证明原申请长度、全部原厂字段边界、申请失败路径和释放路径；新增尾部只能由一个功能使用，原厂字段地址和值必须保持不变，构建器必须逐字节断言长度修改并检查设备端程序没有新增申请或释放调用。

## 6. 构建产物与记录

每次构建必须生成独立固件和一份不可后补的构建清单。构建清单至少记录：

- 构建时间和工具版本；
- 工具代码版本；
- 原厂输入文件的两个文件指纹；
- 固件文件名、字节数和两个文件指纹；
- 全部修改区间；
- 设备端程序、资源和持久化数据的大小；
- 文件头、型号、版本、文件尾长度和恢复校验结果；
- 自动测试结果；
- 与本次固件实际分支要求一致的连续页面事件模拟结果；
- 修改区间外逐字节一致的结果；
- 是否允许进入上传、安装和发布阶段。

构建前如果目标路径已经存在，必须停止；不得覆盖、截断或原地重建任何已有固件。相同文件名不得对应两个不同指纹。最终发布名已被历史固件占用时，必须先单独完成历史固件改名、固件清单更新和全部引用核对，再开始最终构建。

固件一旦通过离线验证即设为只读。上传、上传后重新下载并逐字节核对、正式安装和回退验证必须使用同一份逐字节相同的文件；中途重新构建后，全部校验从头开始。

凡是修改或包装物理旋钮、一级页面、确认、详情进入或返回，构建器必须在写出固件前执行对应 DESIGN 规定的严格连续事件模拟。模拟必须使用最终固件的实际接入点和分支要求；只验证单个函数返回值或少量状态组合不算通过。原厂继续地址执行后的最终页面无法解析时必须停止构建，不得把预期结果填入报告。该模拟不能替代已确认并设为只读的固件的真机旋钮、启动、功率确认和返回验收。

功率页模拟和真机验收还必须把基座生命周期作为输入条件：连接并有实时功率数据时验证功率页可达和详情进入返回；离线时验证功率页不参与一级循环；离线后页面短暂残留或功率数据指针失效时验证确认只回到时钟，不读取功率详情数据。真机记录必须写明基座是否吸附、是否供电和功率数据是否正在变化；缺少任一项时，不得把功率页不可见或确认结果归因于固件。

## 7. 每个阶段必须完成什么

| 阶段 | 进入条件 | 退出证据 |
| --- | --- | --- |
| 静态分析 | 官方原版固件全部匹配 | 地址、调用、空间和原厂行为有直接证据 |
| 离线构建 | 修改清单已审批 | 构建清单完整，修改区间外逐字节一致 |
| 自动验证 | 固件已确认且设为只读 | 容器、代码、资源、连续页面事件、状态和失败处理测试通过 |
| 独立恢复演练 | 专用测试设备的原厂 R0 回刷已通过 | 至少一条 R2、R3 或 R4 恢复演练通过 |
| 上传后重新下载并逐字节核对 | 独立恢复演练已通过，固件已设为只读 | 从云端下载的文件与本机固件逐字节一致 |
| 首次实验安装 | 严格模拟与上传后核对已通过，设备、版本、固件和运行状态未变 | 自动单次安装、重启、重新上线和全部基础功能通过 |
| 原厂回刷验证 | 已保存匹配原厂文件 | 同一设备回刷、重启、上线和原厂能力通过 |
| 发布 | 优化固件安装与原厂回刷均通过 | 发布清单、限制和恢复步骤完整 |

任一阶段的通过结果不能替代后续阶段。

### 7.1 专用测试设备可以持续安装实验固件的条件

当 AP01 专属接口客观上无法取得时，用户把唯一设备明确指定为专用测试设备并发起“制作并刷入” 流程后，允许该设备的实验固件持续跳过以下恢复类条件：

1. 当前槽、更新槽与实际写入目标证据；
2. 两份逐字节一致的同机全闪存备份；
3. 同机原厂固件回刷验证；
4. 不依赖设备正常启动和联网的独立恢复验证。

持续授权只对记录中的唯一设备和通过严格模拟的实验固件有效；目标设备变化、专用测试用途撤销或用户明确停止时立即失效。它不得转用于发布、批量安装或“不变砖、可刷回原厂”的结论。官方原版固件、修改前旧字节、修改范围、固件长度、文件头、型号、文件尾恢复校验、上传后重新下载并逐字节核对、稳定供电和安装后重新上线不得跳过。

资源上限和存储行为允许在上述单次实验中逐步补测；未取得的项目必须在构建清单中保持 “待真机测量”，不得伪造成已验证结果。

## 8. 安装与回退保护

正式安装前必须在操作记录和当前页面展示：

- 唯一目标设备；
- 当前版本和目标固件；
- 原厂与固件文件指纹；
- 修改范围；
- 已通过的检查；
- 尚存风险；
- 独立恢复通道；
- 原厂回刷材料和命令。

用户发起“制作并刷入”流程后不得再出现正式安装确认。刷机前的交互模拟通过，且设备、版本、固件、检查结果和运行状态都没有变化时，流程自动上传固件，重新下载并逐字节核对，然后只下发一次正式安装；任一项发生变化都必须停止，不得询问用户是否强行继续。

安装期间保持稳定供电、联网和设备身份，不并行下发其他命令。状态未知、短暂离线或超时时先查询状态，不盲目重复安装。

安装成功必须同时证明：设备接受更新、下载完成、进入安装、发生重启、运行时间重新计数、重新上线、原厂页面正常、米家通信正常、官方更新能力正常、目标功能通过。

原厂回刷成功必须在同一台设备上证明：官方固件上传后重新下载并逐字节核对通过、安装完成、设备重启、重新上线、原厂页面恢复、米家通信正常、官方更新能力正常。

### 8.1 首次安装前的自救能力验证

恢复事实和当前缺口只见 [`AP01 离线恢复与救砖证据`](AP01-官方固件分析/离线恢复与救砖证据.md)。至少必须完成：

1. 使用专用测试设备，不使用日常使用设备；
2. 在原厂状态先完成同机 R0 回刷；
3. 拍摄并记录主板、板号、芯片丝印和测试点；
4. 只通过断电通断测量、正常供电高阻测量和被动波形观察识别接口；
5. 确认真实闪存身份、容量和读取范围；
6. 取得两份逐字节一致的同机全闪存备份；
7. 在应用不能运行的条件下完成至少一条独立恢复通道演练；
8. 恢复后验收设备身份、原厂页面、联网、米家通信和官方更新。

任一项依赖猜测、芯片开发板地址或另一台设备的备份时，这项验证就不算通过。

### 8.2 完整性检查不能替代恢复验证

固定长度、旧字节断言、修改区间外一致、文件尾恢复校验、上传后重新下载并逐字节核对和固定使用同一份固件，分别降低误用、误写、意外改动、容器损坏和固件替换风险。它们不能证明新代码一定能启动、自动回退一定触发或离线恢复一定可用。每项保护能证明什么、不能证明什么，详见 [`AP01 离线恢复与救砖证据`](AP01-官方固件分析/离线恢复与救砖证据.md) 第 5 节。

## 9. 强制停止条件

出现以下任一情况立即停止后续高风险动作：

- 设备、版本、官方来源或文件指纹不能唯一确认；
- 官方原版固件与 `artifacts/firmware/README.md` 记录的文件指纹不一致；
- 修改范围超出清单；
- 修改前字节与预期不一致；
- 文件长度、文件头、型号、恢复记录或校验不一致；
- 新功能可能影响启动、联网或更新，且不满足第 7.1 节中专用测试设备持续安装实验固件的条件；
- 把原厂应用更新包当作全闪存备份或使用未经确认的物理地址；
- 要求整片擦除、写入一次性配置或套用开发板接线；
- 拆机后无法确认地线、信号电平、主控、闪存容量或读取范围；
- 两次全闪存读取不一致；
- 上传后重新下载并逐字节核对失败；
- 供电、网络或设备状态不稳定；
- 构建后固件发生任何变化；
- 安装或回退证据链不完整；
- 设备重启并重新上线后，用户肉眼确认仍卡在开机动画或界面没有完成启动；
- 要求跳过第 7.1 节明确保留的不可跳过检查。

## 10. 持续维护触发条件

以下任一变化发生时，必须在同一次变更中更新本文：

- 官方固件版本或结构变化；
- 新增修改区间、设备端程序区、资源区或持久化数据；
- 制作、上传、安装或回退工具变化；
- 新增或失效恢复通道；
- AP01 主板、接口、闪存、分区或一次性配置取得新证据；
- 芯片厂商工具、文档或固定证据版本变化；
- 真机安装、失败或回退取得新证据；
- 安全规则、停止条件或发布范围变化。
