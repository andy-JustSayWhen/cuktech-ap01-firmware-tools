## 1. 设计目标与硬边界

本设计实现三项设备端能力：

1. 六个可开关一级页面及其持久化；
2. AGENTS 看板概览、三个详情页和后台刷新；
3. 系统设置菜单旋钮首尾循环。

本设计全部功能必须遵守 [`design.md`](../design.md) 第 2.2 节的原厂复用先行门禁。每项
当前有效方案必须先完成原厂逻辑调查，并在对应章节精确引用

## 2. 已确认事实

下列事实的定义、证据位置和复查方法以
[`AP01 官方固件分析`](../../knowledge/AP01-官方固件分析/AP01-官方固件分析.md) 为唯一原文：

- 目标设备型号为 `njcuk.enstor.ap01`，原厂版本为 `1.0.2_0031`；
- 原厂文件为 6,804,520 字节，文件头为 `BFNP`；
- 主程序为 32 位 RISC-V 指令；
- 设备使用 NuttX、LVGL、libuv 和 mbedTLS；
- 原厂程序存在六个一级页面创建函数；
- `/data/sysconfig.bin` 是原厂设置文件，但没有一级页面显隐字段；
- `/data` 可用于原厂持久化设置，设备还存在临时文件系统；
- 原厂固件区分当前槽和更新槽，并包含在线更新与恢复代码；
- 原厂 `BFNP` 文件属于应用更新包，不是已经证明可整片写回的全闪存备份；
- 原厂文件内未检出博流分区表标记，文件头安全字段也不能证明芯片的一次性配置状态；
- 博流芯片家族具有串口和调试器读写能力，但没有找到 AP01 主板的对应焊盘和接线证据；
- 参考项目只真机验证了一个复用原厂虚拟形象页的实时画面加载器；
- 参考项目没有实现本 SPEC 所需的七页导航、页面开关、四页原子结果和原厂回刷；
- 当前没有 AP01 专属离线恢复成功案例。

当前基线文件指纹和文件尾恢复校验值以
[`固件制作规范`](../固件制作规范.md) 第 4 节为唯一记录，本文不重复维护。

## 3. 总体实现结构

本项目应用架构的完整规则只见 [`Architecture.md`](../Architecture.md)。设备端优化固件由
构建工具把经过验证的最小修改和新增载荷写入原厂基线，服务端生成看板完整结果，设备按
优先顺序主动取得。

```mermaid
flowchart LR
    A["已校验原厂固件"] --> B["版本专用分析结果"]
    B --> C["设备端载荷与资源"]
    C --> D["带旧字节断言的修改器"]
    D --> E["优化固件与构建清单"]
    E --> F["离线验证"]
    F --> G["同机 R0 回刷与独立恢复演练门禁"]
    G --> H["上传对象完整回读"]
    H --> I["即时确认后真机安装与验收"]
    I --> J["同一设备原厂回刷验收"]
```

设备端职责拆分为：

| 模块 | 单一职责 |
| --- | --- |
| 一级导航候选与过滤 | 在原厂既有页面与 AGENTS 虚拟状态之间计算下一目标，不创建页面 |
| 页面开关设置 | 展示六个复选项，保存成功后更新实际状态 |
| 旋钮事件路由 | 区分唤醒、一级导航、详情导航和设置操作 |
| 设置菜单循环 | 根据当次有效设置项计算前后项 |
| 看板页面 | 显示概览和三个详情，处理详情循环与返回 |
| 结果刷新 | 按服务端优先顺序取得一份完整结果 |
| 结果提交 | 完整校验后一次切换四页结果 |
| 持久化 | 保存页面开关和最后一次成功结果 |

服务端职责拆分为：

| 模块 | 单一职责 |
| --- | --- |
| 数据读取 | 从当前用户已授权环境读取可确认数据 |
| 统计计算 | 生成北京时间范围内的固定字段 |
| 页面渲染 | 生成四个 320×240 成品页面 |
| 完整结果封装 | 把同一轮四页结果组成不可拆分的数据包 |
| 设备授权 | 只向持有该设备专属配置的请求提供结果 |
| 多位置部署 | 在主电脑、NAS、云服务器提供相同协议 |

首批实现只建立离线校验与制作门禁，不声明尚未确认的修改地址：

直接把任意清单改成已批准状态的参数。

## 4. 固件修改策略

### 4.1 基线与输出

设置菜单阶段构建器只接受第 2 节精确原厂版本。完整优化固件构建器同时接受该原厂基线和
下列已验收的设置菜单阶段成品；两者任一身份或相对差异不匹配都必须停止：

| 项目 | 固定值 |
| --- | --- |
| 输入文件名 | `opt-setting.bin` |
| 文件字节数 | 6,804,520 |
| MD5 | `13a7286f4824b1ad87d9bc32f1d3d39c` |
| SHA-256 | `348d0843ac3f3f380eb155170c4104fd8467a018ddfd13670d67be998f269dc1` |
| 文件尾恢复校验值 | `0xe57875a7` |

完整优化固件制作必须先证明该输入相对原厂基线只包含已批准的设置菜单四个修改区间和文件尾
恢复校验值变化，再以它作为后续新增功能的字节输入。完整功能全部实现并通过分阶段验证后，
最终组合成品固定命名为 `ap01-1.0.2_0031-opt.bin`。当前该名称被第 10.4 节历史失败成品
占用；最终构建前必须按 [`固件制作规范`](../固件制作规范.md) 第 6 节先完成失败成品改名和
引用核对，构建器不得覆盖现有文件。两种成品都不得覆盖原厂文件。

当前设置菜单阶段制作入口只接受第 6.1 节已经批准的四个精确修改区间。它不包含参考项目
实时画面加载器，也不代表第 5、7、8、9 节已经进入固件实现。

完整优化固件在新增修改区间尚未完成直接证据、DESIGN 记录和批准前，只允许生成制作就绪
报告，不得生成 `ap01-1.0.2_0031-opt.bin`。

构建器必须：

1. 从仓库外只读路径打开原厂文件，禁止输入路径与输出路径相同；
2. 校验型号、版本、总字节数和两个完整文件指纹；
3. 校验文件头、主程序起点、文件尾恢复记录和安全字段均与当前证据基线一致；
4. 校验每个修改位置的原字节；
5. 编译并检查新增载荷边界；
6. 只写入知识证据和本 DESIGN 已批准的事件、刷新挂接点，并证明页面注册点保持原字节；
7. 写入设备专属的非公开配置；
8. 保持容器总长度、文件头安全字段和恢复记录格式；
9. 重算并复核文件尾恢复校验；
10. 生成全部修改区间、修改前后字节和修改区间外逐字节一致报告；
11. 对冻结成品重新计算两个完整文件指纹，并以只读方式保存。

当前尚未形成的地址、调用约定和空闲空间不得写入本文。它们必须先形成带反汇编位置、
原字节和调用关系的分析记录，随后再进入本节和构建器。

### 4.2 禁止触碰

本固件不修改：

- 启动引导和分区表；
- 当前槽、更新槽与恢复选择；
- 无线网络初始化；
- 米家通信；
- 官方在线更新、下载和安装；
- 原厂恢复记录格式；
- 看门狗启动逻辑；
- 第二阶段启动程序、两份分区表、校准、设备身份和密钥数据；
- 一次性配置、防降级版本、安全启动设置和调试密码。

如果后续实现发现必须修改上述任一范围，本设计立即停止，先更新
[`固件制作规范`](../固件制作规范.md) 的恢复门禁并取得新的明确授权。

构建器不得输出整片擦除、地址零写入、分区表写入或一次性配置写入任务。原厂 `BFNP` 文件
只能进入已经验证的在线更新路径，不得被转换成全闪存写入任务。

### 4.3 安装器拒绝条件

安装器默认只允许离线检查。下列记录全部存在且匹配后，才显示正式安装入口：

1. 唯一目标设备、型号、当前版本和在线状态；
2. 原厂输入和优化成品的完整字节数与两个文件指纹；
3. 构建清单、修改范围、离线测试和文件尾恢复校验；
4. 上传对象被完整下载回本机后，与冻结成品逐字节一致；
5. 同一测试设备的 R0 原厂回刷案例；
6. 同一测试设备至少一条独立恢复演练案例；
7. 当前槽、更新槽和本次写入目标不会覆盖当前运行槽的 AP01 直接证据；
8. 匹配原厂应用更新包、同机全闪存备份和冻结恢复记录均可用；
9. 用户对本次唯一设备和唯一成品的正式安装动作作出即时确认。

正式安装要求第 1～9 项再次成立。第 5～8 项客观上
无法取得时，专用测试设备只允许使用
[`固件制作规范`](../固件制作规范.md) 第 7.1 节定义的逐次风险授权；第 1～4、9 项及该节
保留的完整性检查不得跳过。不能只检查文件开头四字节；本机成品、上传对象和正式安装必须
使用同一份逐字节相同的文件。`--download-only` 已被真机证明会切换运行内容，安装器必须拒绝。

如果现有设备接口不能取得当前槽、更新槽和目标槽的直接证据，第 8 项判定失败。芯片家族
通用更新源码只能作为调查线索，不能替代 AP01 真机结果。

### 4.4 新增逻辑的失败隔离

新增入口必须挂在原厂页面、联网和官方更新任务已经完成初始化之后。准确挂接点必须先由
当前版本调用关系证明，不能按函数名猜测。

每个新增模块必须满足：

1. 未取得合法持久化记录时使用固件内安全默认值；
2. 网络、文件、图片或授权校验失败时继续显示最后成功结果或原厂页面；
3. 新增任务退出、超时或分配失败时不阻塞原厂界面、米家通信和更新任务；
4. 所有缓冲区有固定上限，写入前检查长度，释放路径覆盖全部失败分支；
5. 新增状态只能写入已经验证的独立文件，不扩展原厂设置结构；
6. 新功能连续失败时停止自身刷新，不触发设备复位或修改启动状态；
7. 原厂更新开始时停止新增网络请求和持久化写入，释放相关资源。

这些隔离只能降低新增逻辑间接影响原厂路径的概率，不能替代独立恢复演练。

## 5. 一级页面与开关实现

### 5.1 固定页面表

一级导航候选表按原厂真实对象顺序固定如下：

| 导航位置 | 页面 | 原厂交互分派序号 | 是否允许关闭 |
| ---: | --- | ---: | --- |
| 0 | 功率 | 0 | 是 |
| 1 | 时钟 | 3 | 是 |
| 2 | 日历 | 4 | 是 |
| 3 | 天气 | 5 | 是 |
| 4 | 设置 | 6 | 否 |
| 5 | 萌宠 | 7 | 是 |
| 6 | AGENTS 看板 | 虚拟状态 | 是 |

序号 1、2 的 C1、C2 条件页和序号 8 的米家详情不进入自定义一级导航候选表。每项保存页面
标识、原厂交互分派序号或 AGENTS 虚拟标识，以及对应开关位；设置页的启用值在运行时固定为
真，不从持久化记录读取。

设备只创建原厂既有对象。AGENTS 不创建页面对象，而是按第 6.1、7.1.1 节复用原厂萌宠
动图对象。关闭状态只从一级导航候选表中排除对应位置，不改变原厂初始化、对象生命周期、
直接子对象数量或米家详情序号。向任一方向寻找下一页时最多检查七个导航位置；达到七项仍
未命中即选择设置页，防止异常数据造成死循环。

第 10.11 节的原厂精确调用链观察成品尚不实现页面开关，七个导航位置全部视为启用，以便
逐一复测六个原厂页面的确认、详情和返回。只有第 5.4 节设置实现门禁解除后，最终组合成品
才读取第 5.2、5.3 节状态并排除关闭位置。

### 5.2 页面开关状态

六个可开关页面使用一个 6 位状态值。位序与
[`SPEC-PAGE-002`](../SPEC.md#spec-primary-page-switches) 的复选项顺序完全一致。

首次没有有效记录时使用：

| 页面 | 值 |
| --- | --- |
| 时钟 | 开 |
| 功率 | 开 |
| 天气 | 关 |
| 日历 | 关 |
| 萌宠 | 关 |
| AGENTS 看板 | 开 |

恢复出厂设置时删除优化固件自己的有效记录，再按上表重新建立。不得扩大或改写原厂
`/data/sysconfig.bin` 的现有结构。

### 5.3 保存事务

页面开关使用 `/data/.ap01-page0` 与 `/data/.ap01-page1` 两份 16 字节独立小记录轮换
保存。每份记录依次包含固定标记、递增序号、6 位状态值和异或校验值。启动或导航前读取两份
记录，选择校验有效且序号较新的记录；两份都无效时使用第 5.2 节默认值。

切换复选项时：

1. 在内存中生成候选状态；
2. 选择非当前有效记录对应的文件并以固定长度覆盖；
3. 关闭后重新打开、完整回读并校验；
4. 校验成功后更新当前界面；
5. 任一步失败即保留旧状态并恢复界面。

写入时始终保留另一份有效记录，单次写入中断不会同时破坏两份记录。设备端文件系统剩余空间
和反复断电结果仍需真机验收；验收前构建清单必须把持久化标为待验证。

### 5.4 设置菜单与开关页实现门禁

原厂设置列表创建入口、循环边界和分支位置的现有静态证据只见
[`一级页面开关挂接静态定位`](../../knowledge/AP01-官方固件分析/cases/2026-07-28-一级页面开关挂接静态定位.md)；
空挂接真机边界只见
[`设置列表空挂接首次安装`](../../knowledge/AP01-官方固件分析/cases/2026-07-28-设置列表空挂接首次安装.md)。
空挂接只证明原分支可以安全进入并返回，没有证明原厂创建循环、局部数组、状态编号、事件
回调或对象生命周期可以容纳第八项。曾经同时增加循环数量、设置行和覆盖页的组合成品卡在
开机动画，因此当前阶段必须保持原厂项目数 7、原厂“返回”分支、设置键值回调和对象创建
路径不变。

1. 屏幕处于熄屏或屏幕保护状态：消费本次有效事件，只执行原厂唤醒和计时重置；
2. 页面开关设置：左右移动复选项，完整按下与松开后切换；

5. AGENTS 看板概览：完整按下与松开后进入周剩余额度详情；
6. 一级页面：左右在当前已启用页面间循环；
7. 其他原厂页面：交还原厂处理。

每个物理有效格只产生一次页面移动。确认操作只在同一轮按下、松开配对完整后执行，避免
按下阶段和松开阶段各执行一次。

| 值 | 含义 |
| ---: | --- |
| 0 | AGENTS 关闭 |
| 1 | 概览 |
| 2 | 周剩余额度 |
| 3 | 今日消耗 |
| 4 | 近 30 天消耗 |

描述有效，再以一次对齐写入提交新界面状态；失败时立即恢复原画面并写入关闭状态。离开
AGENTS 时先写入关闭状态，再把既有动图对象恢复为原厂描述地址 `0xa01f7090`。调用
`0xa00bfa4e` 后必须再次用 `0xa00be388` 核对结果；结果不是目标序号时恢复原厂萌宠画面并
写入关闭状态。

后台界面定时回调先执行原厂定时回调，再读取 `0xa00be388`。当前交互分派不是 `7` 时不读取
萌宠状态、不替换动图数据源；当前为 `7` 时才沿已验证对象关系取得动图对象。状态无效时，
恢复原厂描述并初始化为关闭；状态为关闭且解码描述无效时重试恢复原厂描述；状态有效且开启
时才应用对应页面。实现不得新增内存申请或释放调用，不得替换萌宠根对象的用户数据，不得
写入原厂萌宠状态偏移 `0`、`4`、`8`、`12`。

原厂旋钮输入解码把一次旋转步骤中的中途方向变化直接按新方向强制完成。机械触点抖动形成
一次有效的相反相位时，该路径会立即更新旋钮位置并向界面上报反方向。方向过滤必须在原厂
判定“已有步骤且新方向与当前方向不同”之后、强制完成之前返回，不更新旋钮位置、不发出
按键事件，也不改变原厂同方向处理、完整步骤处理和按钮处理。

系统设置菜单不得使用写死的首尾序号。每次事件从实际显示项目表取得数量；数量为零时不
移动，数量为一时保持当前项。

[`SPEC-ROTARY-005`](../SPEC.md#spec-settings-rotary)。

### 7.3 数值格式化与占位

页面渲染器使用一个公共 Token 格式化入口，严格实现
[`SPEC-DASHBOARD-015` 至 `SPEC-DASHBOARD-018`](../SPEC.md#spec-dashboard-values)，
返回互相独立的“整数数值”和“单位”
两段文字。所有页面只能使用该入口，禁止各页自行拼接单位。

格式化器使用整数运算完成四舍五入，不把 Token 数量转换为浮点数。它先按 SPEC 表格选择
除数，再用“原始值加半个除数后执行整数除法”得到显示整数；结果达到下一单位门槛时，重新
使用下一单位计算。输入必须是非负 64 位整数，超出 SPEC 上限或发生加法溢出时拒绝生成
本轮画面并继续保留最后成功结果。

数值文字位置按四位数字和一个可选千位分隔符预留，使用固定右边界；单位文字使用独立固定
位置。字体变化、单位变化和四舍五入都不能移动相邻指标。渲染完成后必须检查四张页面没有
小数点、文字越界、重叠或裁切。

今日消耗页的主数值按 `56 px`、`48 px`、`45 px`、`42 px`、`36 px`、`32 px` 依次测量，
输入、输出和缓存命中数值按 `30 px`、`24 px` 两档字号依次测量，选择能完整放入固定数值
位置的最大一档。各档共用同一右边界和基线；最小字号仍放不下时拒绝生成本轮画面。
`9,000 Token`、`9,999 万 Token`、`20 亿 Token`、`10 亿 Token` 和 `5 亿 Token` 是必须
通过的版面边界用例。

概览页今日消耗和近 30 天消耗的数值按 `38 px`、`31 px`、`27 px`、`23 px`、`20 px`、
`19 px` 依次测量；最小字号必须完整容纳 `9,999` 和千位分隔符。

百分比和金额使用公共整数显示入口。请求数等原始整数不做缩放；百分比与金额完成四舍五入
后再拼接各自符号。概览页只把本周剩余额度传给圆环控件，今日消耗和近 30 天消耗只进入
普通数值与单位位置。

圆环和进度条的颜色方向只实现
[`AP01 AGENTS 看板效果图评审` 第 2 节](../image/DESIGN/AP01-AGENTS看板/README.md#2-视觉方向)；
表示剩余额度和命中率时不得使用相反色序。近 30 天页只在“活动洞察”和“常用插件”两个
组标题旁分别绘制一个组图标，十条数据行不创建图标、圆弧或进度控件。每条数据的字段名、
数值和单位共用同一个文字颜色，不按数值或单位设置点缀色。

#### 7.4.2 按模型归集今日原始 Token

采集器流式扫描每个会话记录文件，并为每个文件独立维护会话编号、当前模型、上一组累计
Token 和正增量事件序号：

1. `thread_settings_applied`（设置已经应用的记录）中的 `thread_settings.model` 更新当前
   模型；没有该记录时使用最近的 `turn_context.payload.model`；
2. `total_token_usage`（会话累计 Token）使用当前累计值减去上一累计值得到非负增量；只有
   `last_token_usage` 时直接使用本次值；
3. `last_token_usage`（本次请求 Token）和累计差值都读取原始输入、缓存命中、缓存写入、
   输出与推理输出；缓存命中与缓存写入总和不得超过原始输入，推理输出不得超过输出；
4. 原始输入、缓存命中、缓存写入和输出均为零的记录不计为请求；
5. 使用“会话编号 + 正增量事件序号”去除活动目录与归档目录中的重复记录；
6. 只保留记录时间落在北京时间当天的正增量，再按模型汇总；
7. 新增输入等于原始输入减去缓存命中；当天总 Token、命中率和请求数继续执行
   [`SPEC-DASHBOARD-021` 至 `SPEC-DASHBOARD-028`](../SPEC.md#spec-dashboard-fields)。

安全聚合结果保存每个模型标识、请求数、原始输入、新增输入、缓存命中、缓存写入、输出、
推理输出、长上下文请求数、单价是否匹配和 API 成本，不保存原始会话行、任务标题、提示词、
回复正文或会话编号。

#### 7.4.3 API 成本计算

模型标识映射、固定单价、长上下文规则、唯一公式、取整顺序和无法计算条件只见
[`Codex 模型 API 计费表`](../Codex-模型API计费表.md)。实现放在
`features/agents_dashboard/pricing.py`，使用十进制定点计算，不使用二进制浮点数。

采集器逐次请求计算未取整美元费用，以便正确应用长上下文规则；随后按模型汇总，最后对当天
总和只取整一次。当天全部正 Token 用量均能匹配模型、必要 Token 字段和单价时，今日页显示
带美元符号的整数“API 成本”；任何一组无法匹配时显示“无法获取”。

自动测试必须固定当前表内每个本地模型标识、四类单价和长上下文规则，检查实现表与唯一计费
文档逐行一致，并覆盖多模型求和后只取整一次、缓存写入、长上下文、未知模型和未公布价格
模型。

#### 7.4.4 官方请求、缓存与安全边界

三个官方请求都使用当前 Codex 登录文件中的访问凭据和账号标识，设置连接与总响应超时，
绝不打印、保存或写入快照。额度和重置卡每 5 分钟最多联网一次；个人统计沿用 Codex 桌面端
6 小时有效期。规范化后的安全聚合结果保存到被版本控制忽略的 `env/agents-dashboard-cache/`。
联网失败、登录过期、字段缺失或返回类型变化时使用对应来源的最后一次成功缓存；没有成功缓存
时才把该来源标记为无法获取。

服务运行时允许显式指定一个 Codex 数据根目录和一个安全聚合缓存目录。未指定数据根目录时
使用当前用户的 `CODEX_HOME`（告诉程序去哪里找 Codex 数据的环境参数），该环境参数不存在
时使用当前用户目录下的 `.codex`；未指定
缓存目录时使用项目的 `env/agents-dashboard-cache/`。运行状态和构建清单只记录各来源是否
可用，不记录这两个目录的绝对路径。

采集结果只保存第 7.4.1 节列出的安全聚合数值、中文展示名称、数据截止时间和来源可用状态。
测试必须扫描结果键值，确认不含提示词、回复正文、令牌、账号、设备标识和本机绝对路径；
还必须证明删除三个参考应用后不影响采集路径。

#### 7.4.5 换机时的设备配置连续性

设备专属配置与当前服务电脑的运行参数分开维护。设备专属配置包含第 8.2 节的设备代号、访问
标识和秘密值，必须与已经刷入设备的固件保持同一份；当前电脑的运行参数只包含数据根目录、
缓存目录、字体目录、结果目录、绑定地址、端口和刷新周期。

服务正常启动和固件构建都只能读取已经存在的设备专属配置；文件缺失、格式错误或权限不符合
要求时必须停止，禁止静默生成新身份。只有用户明确执行初始化入口时才允许新建设备专属配置，
且初始化只生成配置，不启动服务、不生成固件。换机时优先原样迁移已有配置；无法取得旧配置
时，新配置只能用于后续重新制作并安装的设备专属成品，不能声称兼容当前已刷固件。

服务健康结果只公开四类数据来源是否可用、最后成功刷新、最后设备请求、请求次数、是否正在
刷新以及安全错误摘要。不得公开设备代号、访问标识、秘密值、登录信息、绝对路径或请求查询
字段。

### 7.5 字体、图标与光栅化

服务端渲染器以 4 倍画布绘制后缩小到 320×240，生成不带透明通道的 PNG。字重层级只见
[`AP01 AGENTS 看板效果图评审` 第 2 节](../image/DESIGN/AP01-AGENTS看板/README.md#2-视觉方向)。
渲染器使用 Michroma Regular 绘制超大主数字和主要 Token 数字，使用 MiSans Medium、
Semibold 和 Bold 绘制次级数字、中文、单位、字段名和状态标题，并以语义角色调用，不允许
页面代码任意填写字体文件名。字体文件只保存在被版本控制忽略的 `env/fonts/`；渲染器找不到
任一字体时拒绝生成，不能静默换成系统字体。

两套字体的取得地址与许可记录在 [`requirements.md`](../requirements.md)。成品图片和使用
说明注明所用字体，不把字体文件复制进仓库、安装包或固件。

自动测试必须验证主数字使用 Michroma，另外三个文字角色映射到 MiSans 的不同字重，并在本机
字体齐全时验证小字号文字的墨迹量依次增加，防止文件名不同但实际仍呈现为同一粗细。

“活动洞察”和“常用插件”组标题，以及今日页的输入、输出和缓存符号，使用仓库内随模块

将图标着色并缩放，不用圆环替代语义图标。

颜色函数只接受 0 至 100 的整数，按红、橙、黄、绿顺序插值得到当前颜色；未完成部分使用
暗灰色。圆弧和进度条只能接收百分比字段，Token 字段类型检查失败时拒绝绘制。

## 8. 完整结果协议

### 8.1 单次完整包

服务端每次只发布一个完整结果包。第二版固定使用小端序，包头为 64 字节，随后按
“概览、周剩余额度、今日消耗、近 30 天消耗”的顺序连续存放四个页面。包头字段固定如下：

| 偏移 | 长度 | 内容 |
| ---: | ---: | --- |
| 0 | 4 | 固定标记 `APAG` |
| 4 | 2 | 协议版本，第二版为 2 |
| 6 | 2 | 包头长度，固定为 64 |
| 8 | 4 | 非零结果代号 |
| 12 | 4 | 整包字节数 |
| 16 | 8 | 北京时间生成时刻对应的 Unix 秒数 |
| 24 | 4 | 页面数，固定为 4 |
| 28 | 4 | 保留位，固定为 0 |
| 32 | 16 | 四个页面各自的字节数 |
| 48 | 16 | 四个页面各自的 CRC-32（边接收边计算的四字节损坏检查值） |

每页必须是 320×240、GIF89a、至少双帧，单页不超过 96 KiB；完整包不超过 384 KiB。
结果代号在同一服务端配置内必须单调增加。

设备必须在临时位置接收完整数据包，完成长度、四页、文件格式、尺寸和逐页损坏检查后，才把
“当前结果代号”切换到新包。任何一项失败都删除临时结果并继续使用旧包。

首次后台刷新实验只写入 `/tmp` 的三组轮换槽，每组四个页面；接收方不会覆盖已提交槽和
界面已确认使用的槽。该阶段用于验证联网、整包校验、四页显示和连续刷新，不宣称重启后保留。
最终持久化位置仍需先完成 `/data` 可用空间与读写寿命测试。

### 8.2 设备授权

每台设备在制作时生成自己的 32 字节随机秘密值、8 位十六进制设备代号和 16 位十六进制
访问标识。这三项只进入该用户的设备专属成品和服务端本地配置，不进入公开代码、通用固件、
日志或文档。

设备请求受原厂天气格式区长度限制，携带设备代号末 4 位、访问标识末 12 位和原厂天气请求
生成的时间数值作为一次性随机数；服务端以设备专属配置核对完整映射。服务端拒绝未知设备
代号、访问标识不匹配和已经处理过的同设备随机数。

`FW-TRANSPORT-002` 保留请求授权，响应包只使用第 8.1 节的逐页损坏检查值。该候选只能在
当前局域网内使用；原因是原厂天气后台任务的剩余栈尚无实测值，设备端响应授权所需的两个
32 字节计算状态会把下载状态扩大到 540 字节，已经与本次启动失败共同出现。只有取得任务栈
实测余量并证明更强响应授权不会造成启动、刷新和界面回归后，才能先修订本节再恢复实现。

云服务器只允许使用 HTTPS（给网络传输加密并核对服务器身份的连接方式），并启用服务器
证书校验。虽然原厂固件包含加密通信程序库，但本项目尚未证明新增载荷可以正确复用证书
校验路径；证明完成前，云服务器位置不得启用。

局域网服务必须核对设备专属请求授权，不能只依赖地址隐蔽或固定网址。

## 9. 刷新、故障切换与状态保持

每次刷新从主电脑开始，依次尝试 NAS 和云服务器。每个位置必须设置连接、读取和整包总超时，
一个位置失败后才进入下一个。具体秒数需要在真机网络测试后写入，不在当前无证据状态下猜测。

AGENTS 看板关闭时取消刷新定时器，不发起网络请求，保留最后成功包。重新开启时立即触发
一次后台刷新，完成后再按 5 分钟周期运行。

最后成功包必须位于重启后仍存在的存储中；新包只能替换完整旧包。恢复出厂设置删除优化
固件的页面开关记录和最后成功包，但不改变三个服务端的固定优先顺序。

服务进程启动时先尝试生成新包。生成失败但磁盘上存在一份能由当前设备专属配置完整验签的旧包
时，服务继续提供旧包并进入降级状态，后台按固定周期重试；旧包不存在、损坏或不属于当前
设备配置时停止启动。健康结果中的 `ok`（表示当前完整包能安全提供的状态字段）只表示当前
存在可安全提供的完整包，刷新错误单独标记，不能因为一次刷新失败把仍可提供的旧包报告为
完全不可用。

- 新增载荷的代码和只读数据大小；

每个成品必须通过：

7. 两份设置记录的损坏、旧版本和断电模拟测试；
8. 四页结果缺一、截断、串代、指纹错误和授权错误测试；
9. 服务端顺序、超时、恢复优先级和全部失败测试；
10. 文件头、总长度、型号、版本和文件尾恢复校验；
11. 修改区间外逐字节一致；

14. 冻结成品重新读取后的完整文件指纹一致。

### 11.2 恢复门禁验证

进入任何优化固件安装前，必须按
[`AP01 分级恢复与救砖操作规程`](../SOP/AP01-分级恢复与救砖.md) 完成：

1. 原厂状态下同机 R0 回刷；
2. AP01 主板、芯片、测试点和信号电平记录；
3. 同机两份逐字节一致的全闪存备份；
4. AP01 真实分区图；
5. 应用没有运行时进入 R2、R3 或 R4 中至少一条通道；
6. 只对已确认应用槽恢复同机原厂内容；
7. 写后读回一致、原厂启动和全部基础能力验收。

上述证据必须指向具体设备、硬件批次、工具版本、备份文件指纹和案例记录。只有只读备份而
没有写回启动演练，仍判定不通过。

### 11.3 分阶段实验成品

恢复门禁通过后，真机实验仍按最小变化拆分：

1. 先安装匹配原厂应用更新包，固定 R0 基线；
2. 第一份实验成品只加入一个不涉及后台网络、持久化和启动早期的可见变化；
3. 验证启动、联网、米家通信、官方更新和该变化后，回刷原厂；
4. 后续每份成品只新增一个可独立验收的模块；
5. 页面开关、持久化、看板页面、后台刷新和设置循环分别进入不同实验阶段；
6. 任一阶段出现重启、持续内存增长、联网异常或更新异常，停止合并后续模块并回到原厂；
7. 最终组合成品重新执行全部离线检查、独立恢复门禁、安装验收和原厂回刷。

不得用一份同时引入全部未知能力的成品完成首次实验。

真机阶段固定顺序如下：

1. 核对第 11.2 节恢复证据仍与当前设备和工具匹配；
2. 查询并保存当前槽、更新槽和启动成功状态；
3. 上传冻结成品并完整下载回本机，逐字节比对；
4. 取得本次安装即时确认；
5. 在指定测试设备安装一次；

3. 构建与真实材料测试只接收只读副本；仓库内版本化来源保持可写时仍必须被现有门禁拒绝；
4. 按当前提交重新运行全部现有自动测试；
5. 重建阶段成品与局部分支观察成品，比较完整文件指纹、修改区间和修改区间外字节；
6. 核对编译工具、字体、动图整理工具和独立解码工具仍满足 `requirements.md`；
7. 任一结果与已记录指纹不同，先把差异写入本 DESIGN，不进入真机。

只读副本准备能力归入 `core/firmware_image/`：它只负责复制、权限、长度、指纹和来源记录，不
包含 AP01 业务规则。具体固件身份仍由现有基线定义和各功能构建门禁判断。测试使用临时只读
副本，不再假设版本控制可以保存跨系统只读权限。

实现合同固定为：

1. `core/firmware_image/material.py` 提供 `prepare_read_only_copy` 公开能力；
2. 调用方必须给出预期字节数、SHA-256 和可选 MD5，复制前后分别核对；
3. 默认工作目录为被版本控制忽略的
   `env/firmware-inputs/<SHA-256>/<原文件名>`，目录只允许当前用户访问；
4. 先写同目录临时文件，写完同步到磁盘、复核指纹、设为只读，再以原子替换形成目标；
5. 目标已存在时，只有身份和只读状态全部匹配才复用；任何不一致都停止，不覆盖未知文件；
6. `app/ap01_firmware.py` 只增加参数转换和结果打印，不保存第二套身份规则；
7. 自动测试分别覆盖正确复制、错误指纹、可写目标、已存在未知文件和复制后只读。

冻结构建还必须从当前提交建立独立干净工作区。该工作区只接收当前提交跟踪的代码与固定资源，
以及从原工作区显式提供的被忽略字体和设备专属配置；不得把原工作区未提交文件复制进去。构建
前后分别核对原工作区六个看板成品的状态，证明没有读取后改写、暂存或覆盖它们。

### 14.2 `FW-AGENTS-005` 观测候选

写代码前必须在本节补齐观测载荷的精确挂接地址、原字节、缓冲区位置、长度上限、导出方式和
清理时机。当前拟定的单次事件记录只包含：

1. 单调递增的事件序号；
2. 原厂回调收到的原始键值；
3. 当前方向过滤结果；
4. 当前原厂一级页面对象或可证明的页面状态；
5. AGENTS 状态尾部当前值；
6. 实际进入的局部分支；
7. 分支调用前后的可证明目标状态。

先做主机侧边界和编码测试，再生成只增加观测、不改变分支目标的专用候选。没有独立恢复门禁
和当次安装授权时，只完成离线构建，不安装。

### 14.3 物理证据到分支修正

只有同一冻结观测成品取得下列一组完整记录，才允许拟定分支修正方案：

1. 从可见 AGENTS 概览开始的单格左旋；
2. 从可见 AGENTS 概览开始的单格右旋；
3. 从功率、时钟或萌宠原厂页分别进入相邻页；
4. 同一方向连续两格；
5. 快速反转后下一完整格；
6. 每组操作的事件记录、可见画面、时间和设备身份。

证据只证明键值解释错误时，修改键值到局部分支的映射；证据只证明活动状态不同步时，修改状态
同步；两者都不能证明时继续观测，不同时改两个变量。

### 14.4 `FW-PAGE-003` 四段候选

AGENTS 导航通过后，页面开关按下列四个独立成品推进：

1. 只读挂接：设置列表增加入口但不创建开关对象、不保存、不改变导航；
2. 设置对象：进入开关页、七项首尾循环和复选显示，但退出后丢弃变化；
3. 独立保存：两份记录轮换、断电、损坏、旧版本和首次默认值；
4. 导航生效：保存成功后立即更新候选过滤，关闭当前页时只在下一次旋转寻找目标。

每一段分别执行启动、联网、米家通信、官方更新、全部原厂页面和设置二级菜单回归。前一段没有
真机通过，不得进入后一段或组合完整页面开关。

### 14.5 服务端与最终组合

设备交互通过后，再补：

1. 四类主机的同一服务入口、系统重启恢复和最后成功结果；
2. 设备端多个服务位置按顺序切换；
3. 字段级“无法获取”、断网和不完整结果保持；
4. 四页真机画质、五分钟刷新和全部详情旋钮路径；
5. 从同一原厂基线确定性组合完整成品；
6. 第 11 节全部验证、原厂回刷、独立恢复和发布验收。

完整优化版之前的任何候选都必须保持实验名称，不得使用最终成品名称。

完成第 6 节逐回调审计与代码纠偏后，才允许按 `FW-INTEGRATION-003` 生成一份先完成离线
验证、随后只能按《固件制作规范》第 7.1 节逐次授权进行人工实验验证的完整集成候选。该候选
必须同时满足：

1. 输入为 `FW-MATERIAL-001` 生成的只读 `opt-setting.bin`；
2. 只挂接原厂萌宠左旋、右旋、确认三个局部分支，不恢复已经否定的新增对象、总分派、总回调替换或重复功率左键方案；
3. 页面开关只使用当前已记录的四个固定挂接点和独立双记录保存实现；
4. 清单类型固定为 `opt-rewrite-candidate-firmware`，状态固定为
   `built-not-approved-for-installation`；
5. 清单逐项列出已组合范围、待真机验证范围和全部修改区间；
6. 构建入口和清单都把 `installation_allowed` 固定为 `false`，用于阻止普通安装、自动
   安装和发布；它不构成专用测试设备逐次风险授权，后者必须另行绑定唯一设备、唯一指纹和
   一次动作；
7. 输出名固定为 `ap01-1.0.2_0031-opt-rewrite-candidate.bin`，不覆盖当前被历史失败成品占用的最终文件名；
8. 分别核对一级窗口与系统设置回调的键值分支，不存在跨回调共用的全局方向解释；
9. 一级窗口只调用唯一事实原文列出的实际状态与切换入口，链接进成品的旧导航实现不可达且
   不得被清单批准。

逐次实验必须先完成同一上传对象的完整回读，再即时展示设备、成品、已通过检查、
未完成恢复条件和回退材料。只有用户在展示后明确确认这一次安装，执行端才能人工下发一次；
确认不写回冻结构建清单，也不得解除普通安装与发布门禁。

该候选即使全部离线检查通过，也不能自动变为 `FW-FINAL-001`。只有第 14.2 至 14.5 节要求的
真机交互、原厂回归、回刷和恢复证据齐全，先更新本 DESIGN 后，才能启用最终名称和安装权限。
