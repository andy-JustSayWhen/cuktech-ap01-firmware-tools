## 1. 设计目标与硬边界

本设计实现三项设备端能力：

1. 六个可开关一级页面及其持久化；
2. AGENTS 看板概览、三个详情页和后台刷新；
3. 系统设置菜单旋钮首尾循环。

原厂页面、米家通信、官方在线更新、恢复记录、启动槽选择和设备基础能力必须保留。

固件制作全过程必须遵守
[`固件制作规范`](../固件制作规范.md)。当前没有已验证的离线救砖通道，且尚未完成同一设备
原厂回刷，因此通用安装与发布门禁仍未通过。2026-07-28 用户只对精确指纹绑定的修正版设置
菜单阶段成品作出一次性安装授权；该次安装结果不替代恢复证据，也不授权其他成品或后续安装。

恢复层级、产物类型和现有保护的能力边界只见
[`AP01 离线恢复与救砖证据`](../../knowledge/AP01-官方固件分析/离线恢复与救砖证据.md)，
恢复操作顺序只见
[`AP01 分级恢复与救砖操作规程`](../SOP/AP01-分级恢复与救砖.md)。本设计不把芯片家族或
开发板资料转写成 AP01 接线、分区地址或恢复命令。

## 2. 已确认事实

下列事实的定义、证据位置和复查方法以
[`AP01 官方固件分析`](../../knowledge/AP01-官方固件分析/AP01-官方固件分析.md) 为唯一原文：

- 目标设备型号为 `njcuk.enstor.ap01`，原厂版本为 `1.0.2_0031`；
- 原厂文件为 6,804,520 字节，文件头为 `BFNP`；
- 主程序为 32 位 RISC-V 指令；
- 设备使用 NuttX、LVGL、libuv 和 mbedTLS；
- 原厂程序存在六个一级页面创建函数；
- `/data/sysconfig.bin` 是原厂设置文件，但没有一级页面显隐字段；
- `/data` 可用于原厂持久化设置，设备还存在临时文件系统；
- 原厂固件区分当前槽和更新槽，并包含在线更新与恢复代码；
- 原厂 `BFNP` 文件属于应用更新包，不是已经证明可整片写回的全闪存备份；
- 原厂文件内未检出博流分区表标记，文件头安全字段也不能证明芯片的一次性配置状态；
- 博流芯片家族具有串口和调试器读写能力，但没有找到 AP01 主板的对应焊盘和接线证据；
- 参考项目只真机验证了一个复用原厂虚拟形象页的实时画面加载器；
- 参考项目没有实现本 SPEC 所需的七页导航、页面开关、四页原子结果和原厂回刷；
- 当前没有 AP01 专属离线恢复成功案例。

当前基线文件指纹和文件尾恢复校验值以
[`固件制作规范`](../固件制作规范.md) 第 4 节为唯一记录，本文不重复维护。

## 3. 总体实现结构

本项目应用架构的完整规则只见 [`Architecture.md`](../Architecture.md)。设备端优化固件由
构建工具把经过验证的最小修改和新增载荷写入原厂基线，服务端生成看板完整结果，设备按
优先顺序主动取得。

```mermaid
flowchart LR
    A["已校验原厂固件"] --> B["版本专用分析结果"]
    B --> C["设备端载荷与资源"]
    C --> D["带旧字节断言的修改器"]
    D --> E["优化固件与构建清单"]
    E --> F["离线验证"]
    F --> G["同机 R0 回刷与独立恢复演练门禁"]
    G --> H["实验成品仅下载校验"]
    H --> I["真机安装与验收"]
    I --> J["同一设备原厂回刷验收"]
```

设备端职责拆分为：

| 模块 | 单一职责 |
| --- | --- |
| 一级页面注册与过滤 | 建立固定七页顺序，只让已启用页面进入一级循环 |
| 页面开关设置 | 展示六个复选项，保存成功后更新实际状态 |
| 旋钮事件路由 | 区分唤醒、一级导航、详情导航和设置操作 |
| 设置菜单循环 | 根据当次有效设置项计算前后项 |
| 看板页面 | 显示概览和三个详情，处理详情循环与返回 |
| 结果刷新 | 按服务端优先顺序取得一份完整结果 |
| 结果提交 | 完整校验后一次切换四页结果 |
| 持久化 | 保存页面开关和最后一次成功结果 |

服务端职责拆分为：

| 模块 | 单一职责 |
| --- | --- |
| 数据读取 | 从当前用户已授权环境读取可确认数据 |
| 统计计算 | 生成北京时间范围内的固定字段 |
| 页面渲染 | 生成四个 320×240 成品页面 |
| 完整结果封装 | 把同一轮四页结果组成不可拆分的数据包 |
| 设备授权 | 只向持有该设备专属配置的请求提供结果 |
| 多位置部署 | 在主电脑、NAS、云服务器提供相同协议 |

### 3.1 制作工具首批模块

首批实现只建立离线校验与制作门禁，不声明尚未确认的修改地址：

| 模块路径 | 单一职责 |
| --- | --- |
| `core/firmware_image/` | 校验原厂身份、文件尾恢复记录、完整文件指纹和修改区间 |
| `features/offline_firmware_build/` | 执行带旧字节断言的修改计划，生成成品与构建清单，并按阶段门禁拒绝越权产物 |
| `features/settings_menu_wrap/` | 复现并校验当前版本系统设置菜单首尾循环的 3 个等长修改区间，生成待批准清单和批准范围绑定清单 |
| `app/ap01_firmware.py` | 接收命令参数并组合离线制作功能，不承载固件处理规则 |

本阶段没有经过证据文档批准的修改区间时，只允许输出原厂基线检查报告；不得把未修改副本
命名为优化固件或标记为离线构建完成。

用户批准后，版本控制内的批准记录必须同时绑定目标型号、原厂版本、原厂完整文件指纹、证据
路径、修改区间数量、全部修改前后字节、代码间隙和日志保持范围。制作入口重新从真实原厂
基线生成修改内容并计算批准范围指纹；任一字段不一致时继续保持待批准状态。命令行不得提供
直接把任意清单改成已批准状态的参数。

## 4. 固件修改策略

### 4.1 基线与输出

构建器只接受第 2 节精确版本。当前设置菜单独立阶段成品固定命名为 `opt-setting.bin`；
完整功能全部实现并通过分阶段验证后，最终组合成品固定命名为
`ap01-1.0.2_0031-opt.bin`。两者都不得覆盖原厂文件。

当前设置菜单阶段制作入口只接受第 6.1 节已经批准的三个精确修改区间。它不包含参考项目
实时画面加载器，也不代表第 5、7、8、9 节已经进入固件实现。

构建器必须：

1. 从仓库外只读路径打开原厂文件，禁止输入路径与输出路径相同；
2. 校验型号、版本、总字节数和两个完整文件指纹；
3. 校验文件头、主程序起点、文件尾恢复记录和安全字段均与当前证据基线一致；
4. 校验每个修改位置的原字节；
5. 编译并检查新增载荷边界；
6. 写入页面、事件、设置和刷新挂接点；
7. 写入设备专属的非公开配置；
8. 保持容器总长度、文件头安全字段和恢复记录格式；
9. 重算并复核文件尾恢复校验；
10. 生成全部修改区间、修改前后字节和修改区间外逐字节一致报告；
11. 对冻结成品重新计算两个完整文件指纹，并以只读方式保存。

当前尚未形成的地址、调用约定和空闲空间不得写入本文。它们必须先形成带反汇编位置、
原字节和调用关系的分析记录，随后再进入本节和构建器。

### 4.2 禁止触碰

本固件不修改：

- 启动引导和分区表；
- 当前槽、更新槽与恢复选择；
- 无线网络初始化；
- 米家通信；
- 官方在线更新、下载和安装；
- 原厂恢复记录格式；
- 看门狗启动逻辑；
- 第二阶段启动程序、两份分区表、校准、设备身份和密钥数据；
- 一次性配置、防降级版本、安全启动设置和调试密码。

如果后续实现发现必须修改上述任一范围，本设计立即停止，先更新
[`固件制作规范`](../固件制作规范.md) 的恢复门禁并取得新的明确授权。

构建器不得输出整片擦除、地址零写入、分区表写入或一次性配置写入任务。原厂 `BFNP` 文件
只能进入已经验证的在线更新路径，不得被转换成全闪存写入任务。

### 4.3 安装器拒绝条件

安装器默认只允许离线检查。下列记录全部存在且匹配后才显示实验成品仅下载入口；仅下载
成功且全部记录仍匹配后，才显示正式安装入口：

1. 唯一目标设备、型号、当前版本和在线状态；
2. 原厂输入和优化成品的完整字节数与两个文件指纹；
3. 构建清单、修改范围、离线测试和文件尾恢复校验；
4. 上传对象被完整下载回本机后，与冻结成品逐字节一致；
5. 设备仅下载校验成功；
6. 同一测试设备的 R0 原厂回刷案例；
7. 同一测试设备至少一条独立恢复演练案例；
8. 当前槽、更新槽和本次写入目标不会覆盖当前运行槽的 AP01 直接证据；
9. 匹配原厂应用更新包、同机全闪存备份和冻结恢复记录均可用；
10. 用户分别对本次唯一设备的仅下载动作和正式安装动作作出即时确认。

实验成品仅下载入口要求第 1～4、6～10 项成立，并使用“仅下载”当次确认；仅下载成功后形成
第 5 项。正式安装要求第 1～10 项再次成立，并另取“正式安装”当次确认。任一项缺失、过期
或互相冲突时，安装器必须拒绝对应动作，不提供跳过参数。不能只检查文件开头四字节；本机
成品、上传对象、设备仅下载和正式安装必须使用同一份逐字节相同的文件。

如果现有设备接口不能取得当前槽、更新槽和目标槽的直接证据，第 8 项判定失败。芯片家族
通用更新源码只能作为调查线索，不能替代 AP01 真机结果。

### 4.4 新增逻辑的失败隔离

新增入口必须挂在原厂页面、联网和官方更新任务已经完成初始化之后。准确挂接点必须先由
当前版本调用关系证明，不能按函数名猜测。

每个新增模块必须满足：

1. 未取得合法持久化记录时使用固件内安全默认值；
2. 网络、文件、图片或授权校验失败时继续显示最后成功结果或原厂页面；
3. 新增任务退出、超时或分配失败时不阻塞原厂界面、米家通信和更新任务；
4. 所有缓冲区有固定上限，写入前检查长度，释放路径覆盖全部失败分支；
5. 新增状态只能写入已经验证的独立文件，不扩展原厂设置结构；
6. 新功能连续失败时停止自身刷新，不触发设备复位或修改启动状态；
7. 原厂更新开始时停止新增网络请求和持久化写入，释放相关资源。

这些隔离只能降低新增逻辑间接影响原厂路径的概率，不能替代独立恢复演练。

## 5. 一级页面与开关实现

### 5.1 固定页面表

新增一张固定页面表，顺序为：

1. 时钟；
2. 功率；
3. 天气；
4. 日历；
5. 设置；
6. 萌宠；
7. AGENTS 看板。

每项保存页面标识、原厂创建入口或新增创建入口、是否允许关闭。设置页的启用值在运行时
固定为真，不从持久化记录读取。

导航只遍历当前启用项，不为关闭项创建空白占位。向任一方向寻找下一页时最多检查七项；
达到七项仍未命中即回到设置页，防止异常数据造成死循环。

### 5.2 页面开关状态

六个可开关页面使用一个 6 位状态值。位序与 SPEC 第 2.2 节复选项顺序完全一致。

首次没有有效记录时使用：

| 页面 | 值 |
| --- | --- |
| 时钟 | 开 |
| 功率 | 开 |
| 天气 | 关 |
| 日历 | 关 |
| 萌宠 | 关 |
| AGENTS 看板 | 开 |

恢复出厂设置时删除优化固件自己的有效记录，再按上表重新建立。不得扩大或改写原厂
`/data/sysconfig.bin` 的现有结构。

### 5.3 保存事务

页面开关使用两份独立小记录轮换保存。每份记录包含固定标记、格式版本、递增序号、6 位状态
值、长度和校验值。启动时读取两份记录，选择校验有效且序号较新的记录。

切换复选项时：

1. 在内存中生成候选状态；
2. 写入较旧记录对应的临时文件；
3. 回读并校验；
4. 以文件系统原子改名替换目标记录；
5. 再更新当前实际状态和一级页面表；
6. 任一步失败即保留旧状态并恢复界面。

设备端文件系统的可用空间、原子改名行为和断电一致性尚未真机测量。完成这些测试前，本节
只能作为实现方案，不能作为已验证能力。

## 6. 旋钮事件与导航

旋钮原厂事实只见
[`AP01 物理旋钮动作、事件与功能表`](../../knowledge/AP01-物理旋钮交互设计/AP01-物理旋钮原厂功能映射表.md)。

新增统一事件入口按以下优先级处理：

1. 屏幕处于熄屏或屏幕保护状态：消费本次有效事件，只执行原厂唤醒和计时重置；
2. 页面开关设置：左右移动复选项，完整按下与松开后切换；
3. 系统设置菜单：左右按当次有效项目首尾循环；
4. AGENTS 看板详情：左右在三个详情间循环，完整按下与松开后返回概览；
5. AGENTS 看板概览：完整按下与松开后进入周剩余额度详情；
6. 一级页面：左右在当前已启用页面间循环；
7. 其他原厂页面：交还原厂处理。

每个物理有效格只产生一次页面移动。确认操作只在同一轮按下、松开配对完整后执行，避免
按下阶段和松开阶段各执行一次。

原厂旋钮输入解码把一次旋转步骤中的中途方向变化直接按新方向强制完成。机械触点抖动形成
一次有效的相反相位时，该路径会立即更新旋钮位置并向界面上报反方向。方向过滤必须在原厂
判定“已有步骤且新方向与当前方向不同”之后、强制完成之前返回，不更新旋钮位置、不发出
按键事件，也不改变原厂同方向处理、完整步骤处理和按钮处理。

系统设置菜单不得使用写死的首尾序号。每次事件从实际显示项目表取得数量；数量为零时不
移动，数量为一时保持当前项。
选中状态、选中样式和列表可视位置的同步验收只见 [`SPEC`](../SPEC.md) 第 1.1 节。

### 6.1 当前版本实现

当前版本的设置列表创建、控件数量、对象查找、左右处理、原字节、首次候选和真机根因只见
[`2026-07-27 系统设置菜单首尾循环静态定位`](../../knowledge/AP01-官方固件分析/cases/2026-07-27-系统设置菜单首尾循环静态定位.md)。

实现放入 `features/settings_menu_wrap/`。原厂左右分支先遍历页面根控件并把系统设置列表数据
保存在 `s3`。当前安装版从 `s3 + 8` 取得实际设置列表控件，再调用原厂子控件计数入口
`0xa00c5fe4`，把返回值作为当次设置项目数：小于 2 或状态越界时返回；位于当次首尾时调用
原厂选择切换完成循环；其余有效位置交回原厂相邻切换。不得使用进入挂接前保存在 `s5` 的
页面根控件子控件数作为项目数。

原厂内部相邻切换按需要先调用列表位置调整入口 `0xa00c6dfe`，再写入选中状态并调用选择切换。
当前安装版的两个首尾分支只执行后两步，造成选中状态已经循环、列表仍停在原位置。视觉同步
修正版必须复用原厂顺序：

1. 最后一项向右循环到第一项时，调用列表位置调整入口，位置参数为 `0`，动画参数为 `0`；
2. 第一项向左循环到最后一项时，调用列表位置调整入口，位置参数为 `400`，动画参数为 `0`；
3. 列表位置调整返回后，才写入新状态并调用原厂选择切换；
4. 内部相邻切换继续直接回到原厂分支。

动画参数 `0` 只关闭跨越中间条目的滚动过渡，不取消列表位置调整。两个首尾分支仍在同一次
旋钮事件中分别把列表直接移动到顶部和底部；原厂内部相邻切换继续使用原厂动画参数。

菜单循环修正范围只包含系统设置一级列表。二级菜单不能首尾循环的原厂行为保持不变。方向
过滤属于 `core/rotary_encoder/`，作用于所有页面的旋钮旋转，不处理按钮；系统设置功能通过
该系统能力取得单方向事件。原厂日志字符串和日志调用代码保留；被过滤的中途反向边沿不再
进入原厂“强制完成”日志。图形资源、持久化和运行时内存分配均不修改。版本限定处理程序
继续使用已经验证的原厂零填充代码间隙。

首次候选的批准和离线构建只见上述证据记录第 10、11 节，真机结果与根因只见第 13、14 节。
修正版全部精确修改前后字节、控制流、验证结果和批准范围指纹只见第 15 节，重新批准、离线
构建与单次真机安装只见第 16～18 节。

当前安装版已经完成上传对象完整回读、设备接受、下载、安装、重启和连续在线检查。真机观察、
视觉误判说明和静态根因只见上述证据记录第 19 节。首尾立即定位修正版的完整字节、控制流、
验证结果和新批准范围只见第 21 节；此前批准范围不适用于该修正版。

顶部第一项左旋偶发落到第二项的真机失败、能够写入第二项的原厂路径和旋钮解码证据只见上述
证据记录第 22 节。方向过滤必须新增一个精确修改区间，并与第 21 节三个区间合成新的完整
批准范围；第 21 节批准不得继续使用。固定实现、静态验证和新范围指纹只见第 23 节。

## 7. AGENTS 看板页面

### 7.1 页面对象

AGENTS 看板是新增一级页面，不复用萌宠页作为产品导航位置。页面对象包括：

- 一个概览页面；
- 周剩余额度详情；
- 今日消耗详情；
- 近 30 天消耗详情。

进入详情时固定把详情索引设为周剩余额度。离开详情、切换一级页面、重启或恢复出厂设置都
不保存当前详情索引。

### 7.2 成品画面

服务端生成四个 320×240 成品画面，设备只负责校验、保存和显示，不在设备中读取 Codex
任务原文或重新计算统计。

当前效果图、唯一视觉方向和生成提示只见
[`AP01 AGENTS 看板效果图评审`](../image/DESIGN/AP01-AGENTS看板/README.md)。
四张页面已经按原厂时间页、功率页风格以及
[`SPEC` 第 4.1 节](../SPEC.md#41-看板数值显示合同)完成修订。用户已经确认四张页面的内容
与视觉方向，允许实现服务端渲染器并生成真实数据对照图；对照图通过评审前不转为固件内置
资源。

周剩余额度详情需要多批重置卡时，由服务端生成一份动图；自动换批不改变设备端详情索引。
其他静态页面优先使用经过真机验证后体积更小的格式。采用 PNG 或不同 GIF 约束前，必须先
补充设备端加载与真机结果。

从未有成功结果时，固件内置四张完整的“等待首次同步”页面。内置资源必须计入修改区间和
资源容量，不得覆盖未经确认的原厂资源。

### 7.3 数值格式化与占位

页面渲染器使用一个公共 Token 格式化入口，严格实现
[`SPEC` 第 4.1 节](../SPEC.md#41-看板数值显示合同)，返回互相独立的“整数数值”和“单位”
两段文字。所有页面只能使用该入口，禁止各页自行拼接单位。

格式化器使用整数运算完成四舍五入，不把 Token 数量转换为浮点数。它先按 SPEC 表格选择
除数，再用“原始值加半个除数后执行整数除法”得到显示整数；结果达到下一单位门槛时，重新
使用下一单位计算。输入必须是非负 64 位整数，超出 SPEC 上限或发生加法溢出时拒绝生成
本轮画面并继续保留最后成功结果。

数值文字位置按四位数字和一个可选千位分隔符预留，使用固定右边界；单位文字使用独立固定
位置。字体变化、单位变化和四舍五入都不能移动相邻指标。渲染完成后必须检查四张页面没有
小数点、文字越界、重叠或裁切。

今日消耗页的主数值按 `62 px`、`46 px` 两档字号依次测量，输入、输出和缓存命中数值按
`31 px`、`24 px` 两档字号依次测量，选择能完整放入固定数值位置的最大一档。各档共用
同一右边界和基线；两档都放不下时拒绝生成本轮画面。`9,000 Token`、`20 亿 Token`、
`10 亿 Token` 和 `5 亿 Token` 是必须通过的版面边界用例。

百分比和金额使用公共整数显示入口。请求数等原始整数不做缩放；百分比与金额完成四舍五入
后再拼接各自符号。概览页只把本周剩余额度传给圆环控件，今日消耗和近 30 天消耗只进入
普通数值与单位位置。

圆环和进度条的颜色方向只实现
[`AP01 AGENTS 看板效果图评审` 第 2 节](../image/DESIGN/AP01-AGENTS看板/README.md#2-视觉方向)；
表示剩余额度和命中率时不得使用相反色序。近 30 天页只在“活动洞察”和“常用插件”两个
组标题旁分别绘制一个组图标，十条数据行不创建图标、圆弧或进度控件。每条数据的字段名、
数值和单位共用同一个文字颜色，不按数值或单位设置点缀色。

### 7.4 本机真实数据采集

`features/agents_dashboard` 负责一次性采集、整理和渲染四张页面。外部只能通过该模块入口
调用，不直接读取模块内部文件。

Cockpit Tools、CC Switch 和 Codex 桌面端只作为已经验证过的取数实现参考，不是安装依赖，

#### 7.4.2 按模型归集今日原始 Token

采集器流式扫描每个会话记录文件，并为每个文件独立维护会话编号、当前模型、上一组累计
Token 和正增量事件序号：

1. `thread_settings_applied`（设置已经应用的记录）中的 `thread_settings.model` 更新当前
   模型；没有该记录时使用最近的 `turn_context.payload.model`；
2. `total_token_usage`（会话累计 Token）使用当前累计值减去上一累计值得到非负增量；只有
   `last_token_usage` 时直接使用本次值；
3. `last_token_usage`（本次请求 Token）和累计差值都读取原始输入、缓存命中、缓存写入、
   输出与推理输出；缓存命中与缓存写入总和不得超过原始输入，推理输出不得超过输出；
4. 原始输入、缓存命中、缓存写入和输出均为零的记录不计为请求；
5. 使用“会话编号 + 正增量事件序号”去除活动目录与归档目录中的重复记录；
6. 只保留记录时间落在北京时间当天的正增量，再按模型汇总；
7. 新增输入等于原始输入减去缓存命中；当天总 Token、命中率和请求数继续执行
   [`SPEC` 第 4.2 节](../SPEC.md#42-看板字段口径)。

安全聚合结果保存每个模型标识、请求数、原始输入、新增输入、缓存命中、缓存写入、输出、
推理输出、长上下文请求数、单价是否匹配和 API 成本，不保存原始会话行、任务标题、提示词、
回复正文或会话编号。

#### 7.4.3 API 成本计算

模型标识映射、固定单价、长上下文规则、唯一公式、取整顺序和无法计算条件只见
[`Codex 模型 API 计费表`](../Codex-模型API计费表.md)。实现放在
`features/agents_dashboard/pricing.py`，使用十进制定点计算，不使用二进制浮点数。

采集器逐次请求计算未取整美元费用，以便正确应用长上下文规则；随后按模型汇总，最后对当天
总和只取整一次。当天全部正 Token 用量均能匹配模型、必要 Token 字段和单价时，今日页显示
带美元符号的整数“API 成本”；任何一组无法匹配时显示“无法获取”。

自动测试必须固定当前表内每个本地模型标识、四类单价和长上下文规则，检查实现表与唯一计费
文档逐行一致，并覆盖多模型求和后只取整一次、缓存写入、长上下文、未知模型和未公布价格
模型。

#### 7.4.4 官方请求、缓存与安全边界

三个官方请求都使用当前 Codex 登录文件中的访问凭据和账号标识，设置连接与总响应超时，
绝不打印、保存或写入快照。额度和重置卡每 5 分钟最多联网一次；个人统计沿用 Codex 桌面端
6 小时有效期。规范化后的安全聚合结果保存到被版本控制忽略的 `env/agents-dashboard-cache/`。
联网失败、登录过期、字段缺失或返回类型变化时使用对应来源的最后一次成功缓存；没有成功缓存
时才把该来源标记为无法获取。

采集结果只保存第 7.4.1 节列出的安全聚合数值、中文展示名称、数据截止时间和来源可用状态。
测试必须扫描结果键值，确认不含提示词、回复正文、令牌、账号、设备标识和本机绝对路径；
还必须证明删除三个参考应用后不影响采集路径。

### 7.5 字体、图标与光栅化

服务端渲染器以 4 倍画布绘制后缩小到 320×240，生成不带透明通道的 PNG。字重层级只见
[`AP01 AGENTS 看板效果图评审` 第 2 节](../image/DESIGN/AP01-AGENTS看板/README.md#2-视觉方向)。

不允许页面代码任意填写字体文件名。字体文件只保存在被版本控制忽略的 `env/fonts/`；
渲染器找不到任一字体时拒绝生成，不能静默换成系统字体。

MiSans 的取得地址与许可文件记录在 [`requirements.md`](../requirements.md)。成品图片和
使用说明注明“使用 MiSans 字体”，不把字体文件复制进仓库、安装包或固件。

自动测试必须验证四个语义角色映射到四个不同字重，并在本机字体齐全时验证同一小字号文本的
墨迹量依次增加，防止文件名不同但实际仍呈现为同一粗细。

“活动洞察”和“常用插件”组标题，以及今日页的输入、输出和缓存符号，使用仓库内随模块

颜色函数只接受 0 至 100 的整数，按红、橙、黄、绿顺序插值得到当前颜色；未完成部分使用
暗灰色。圆弧和进度条只能接收百分比字段，Token 字段类型检查失败时拒绝绘制。

### 7.6 真实数据对照产物

真实数据对照图写入效果图目录下的 `真实数据/`，包含四张 320×240 PNG、一个只含聚合字段
的数据快照、一份生成说明，以及一张把四组效果图与真实图并排排版的审阅总图。每次刷新
真实数据时必须同时刷新总图，不能保留上一轮数据。它们用于比较服务端实际渲染与效果图的

## 8. 完整结果协议

### 8.1 单次完整包

服务端每次只发布一个完整结果包。数据包包含：

- 固定标记和协议版本；
- 结果代号；
- 北京时间生成时间；
- 四个页面的类型、长度和文件指纹；
- 四个页面字节；
- 整包长度和完整性校验；
- 设备授权校验值。

设备必须在临时位置接收完整数据包，完成长度、四页、文件格式、尺寸、文件指纹和设备授权
校验后，才把“当前结果代号”切换到新包。任何一项失败都删除临时结果并继续使用旧包。

最终数据包格式、最大尺寸和持久化位置需要先完成 `/data` 可用空间与读写寿命测试。测试
完成前，结果包实现属于阻塞项。

### 8.2 设备授权

每台设备在制作时生成自己的随机秘密值，秘密值只进入该用户的设备专属成品和服务端本地
配置，不进入公开代码、通用固件、日志或文档。

设备请求携带一次性随机数，服务端响应使用
HMAC-SHA-256（双方用同一把秘密钥匙给数据盖章，确认内容没有被替换）生成授权校验值。
服务端拒绝设备标识、随机数或校验值不匹配的请求。

云服务器只允许使用 HTTPS（给网络传输加密并核对服务器身份的连接方式），并启用服务器
证书校验。虽然原厂固件包含加密通信程序库，但本项目尚未证明新增载荷可以正确复用证书
校验路径；证明完成前，云服务器位置不得启用。

局域网服务也使用设备专属授权校验，不能只依赖地址隐蔽或固定网址。

## 9. 刷新、故障切换与状态保持

每次刷新从主电脑开始，依次尝试 NAS 和云服务器。每个位置必须设置连接、读取和整包总超时，
一个位置失败后才进入下一个。具体秒数需要在真机网络测试后写入，不在当前无证据状态下猜测。

AGENTS 看板关闭时取消刷新定时器，不发起网络请求，保留最后成功包。重新开启时立即触发
一次后台刷新，完成后再按 5 分钟周期运行。

最后成功包必须位于重启后仍存在的存储中；新包只能替换完整旧包。恢复出厂设置删除优化
固件的页面开关记录和最后成功包，但不改变三个服务端的固定优先顺序。

## 10. 线程、内存与失败隔离

网络读取、文件写入、图片校验和结果提交不得在界面事件处理过程中同步执行。界面线程只读取
已经提交的当前结果。

实现前必须测量并固定：

- 新增载荷的代码和只读数据大小；
- 每个任务的栈上限；
- 接收缓冲、解码缓冲和页面对象峰值；
- `/data` 可用空间；
- 四页最大成品总量；
- 连续刷新后的内存变化；
- 网络失败、文件损坏和断电后的恢复结果。

任一上限没有测量值，或压力测试出现持续增长、越界、看门狗重启和界面卡死，禁止进入真机
安装阶段。

## 11. 构建与验证

### 11.1 离线验证

每个成品必须通过：

1. 原厂基线身份检查；
2. 文件头安全字段和文件尾结构未发生非预期变化；
3. 修改前旧字节检查；
4. 新增载荷符号、重定位、跳转范围和调用约定检查；
5. 页面表和设置表边界测试；
6. 旋钮唤醒、一级循环、详情循环和设置循环测试；
7. 两份设置记录的损坏、旧版本和断电模拟测试；
8. 四页结果缺一、截断、串代、指纹错误和授权错误测试；
9. 服务端顺序、超时、恢复优先级和全部失败测试；
10. 文件头、总长度、型号、版本和文件尾恢复校验；
11. 修改区间外逐字节一致；
12. 禁止修改区域无差异；
13. 构建清单完整；
14. 冻结成品重新读取后的完整文件指纹一致。

### 11.2 恢复门禁验证

进入任何优化固件安装前，必须按
[`AP01 分级恢复与救砖操作规程`](../SOP/AP01-分级恢复与救砖.md) 完成：

1. 原厂状态下同机 R0 回刷；
2. AP01 主板、芯片、测试点和信号电平记录；
3. 同机两份逐字节一致的全闪存备份；
4. AP01 真实分区图；
5. 应用没有运行时进入 R2、R3 或 R4 中至少一条通道；
6. 只对已确认应用槽恢复同机原厂内容；
7. 写后读回一致、原厂启动和全部基础能力验收。

上述证据必须指向具体设备、硬件批次、工具版本、备份文件指纹和案例记录。只有只读备份而
没有写回启动演练，仍判定不通过。

### 11.3 分阶段实验成品

恢复门禁通过后，真机实验仍按最小变化拆分：

1. 先安装匹配原厂应用更新包，固定 R0 基线；
2. 第一份实验成品只加入一个不涉及后台网络、持久化和启动早期的可见变化；
3. 验证启动、联网、米家通信、官方更新和该变化后，回刷原厂；
4. 后续每份成品只新增一个可独立验收的模块；
5. 页面开关、持久化、看板页面、后台刷新和设置循环分别进入不同实验阶段；
6. 任一阶段出现重启、持续内存增长、联网异常或更新异常，停止合并后续模块并回到原厂；
7. 最终组合成品重新执行全部离线检查、独立恢复门禁、安装验收和原厂回刷。

不得用一份同时引入全部未知能力的成品完成首次实验。

### 11.4 真机验证顺序

真机阶段固定顺序如下：

1. 核对第 11.2 节恢复证据仍与当前设备和工具匹配；
2. 查询并保存当前槽、更新槽和启动成功状态；
3. 使用冻结成品完成仅下载校验；
4. 完整下载回上传对象并再次逐字节比对；
5. 取得本次安装即时确认；
6. 在指定测试设备安装一次；
7. 验证重启、重新上线、实际启动槽和原厂基础能力；
8. 完成 SPEC 第 14.2 节全部功能验收；
9. 使用冻结的匹配原厂应用更新包完成仅下载校验；
10. 回刷原厂应用更新包；
11. 验证重启、重新上线、原厂页面、米家通信和官方更新；
12. 再决定是否允许发布。

第 1～2 步和第 9～11 步没有完整证据时，不得声称本固件满足“不变砖、可刷回原厂”。

## 12. 恢复实现边界

### 12.1 R0 回刷

R0 复用已经真机证明可到达设备的米家在线更新通道，不另造传输协议。实现必须补齐第 4.3
节的完整文件回读、全文件指纹、槽证据、单次安装和完整验收门禁。

R0 依赖原厂应用仍能启动、联网并响应更新，不能作为首次实验安装所需的独立恢复通道。

### 12.2 R1 至 R4

R1 至 R4 当前只进入证据记录和门禁模块，不生成自动写入命令：

- R1 记录 AP01 真机实际回退条件、次数、槽和启动成功标记；
- R2 记录 AP01 下载、复位、串口、电平和只读识别结果；
- R3 记录 AP01 调试焊盘、映射、锁定状态和只读结果；
- R4 记录实体闪存、在电路读取条件、拆焊要求和同机备份。

只有对应层级在专用测试设备上完成恢复演练后，才允许把冻结的接线、工具、地址范围和停止
条件写入操作规程。工具界面提供写入或擦除功能，不代表本项目可以调用。

### 12.3 故障处理

安装状态未知时，安装器只查询，不重复下发。设备离线后，安装器停止所有在线写入并生成
故障现场记录，不自动尝试断电、切槽、硬件连接或整片恢复。

恢复成功标准与准确发布措辞只见
[`AP01 离线恢复与救砖证据`](../../knowledge/AP01-官方固件分析/离线恢复与救砖证据.md)
第 8、9 节。
