# `ap01-1.0.2_0031-opt.bin`技术实现

本文档按用户功能记录 `ap01-1.0.2_0031-opt.bin` 的技术方案

## 1. 设置列表首尾循环

### 1.1 用户功能

设置列表在第一项继续向上时跳到最后一项，在最后一项继续向下时跳到第一项。

### 1.2 实现

该功能已在输入固件 `ap01-1.0.2_0031-opt-setting.bin` 中实现，看板固件不再重复修改它。

`features/settings_menu_wrap/settings_menu_wrap_patch.S` 从原厂列表对象读取当前项目数和选中位置：

- `right_validate` 发现当前位置已经越过末项时，调用原厂列表位置调整和选中过渡函数，切到第一项；
- `left_validate` 发现当前位置是第一项时，调用同一组原厂函数，切到动态计算出的最后一项；
- 非边界位置直接返回原厂切换分支。

修改位置固定为：

| 文件偏移 | 作用 |
| --- | --- |
| `0x01c008` | 存放 `right_validate` 和 `left_validate` |
| `0x0f919e` | 把原厂右旋边界检查跳到 `right_validate` |
| `0x0f976a` | 把原厂左旋边界检查跳到 `left_validate` |

## 2. 旋钮单步方向稳定

### 2.1 用户功能

一次旋钮步进只产生一次选择移动。方向判定沿用原厂中断处理逻辑，固件不修改旋钮中断处理函数 `0xa0107bca..0xa0108060` 的任何字节。

### 2.2 调查结论：不修改原厂方向处理

曾引入"中途反向边沿过滤"补丁（文件偏移 `0x108e20`，把 `li s11,8` 改为跳回中断返回 `0xa0107cbc`），目的是让步进中途的反向毛刺边沿不触发反向移动。真机验证发现该补丁跳过了原厂在 `0xa0107e74` / `0xa0107f40` 对步进方向状态字节 `0x62fd27d4` 的更新：状态字节一旦记录某个方向，后续反方向边沿永远命中"中途反向"分支并直接返回，造成反方向旋转全局失效（首页、看板、设置页左旋全部无效）。该补丁已移除，`0x108e20` 恢复原厂字节 `a14d`。

原厂中断处理对中途反向边沿会"强制完成上一步"并更新状态字节，毛刺可能偶发一次反向移动，这是概率极低的固有行为；相比方向永久锁死，保留原厂行为是唯一已验证安全的方案。完整案例记录见 [`物理旋钮部分交互功能失效案例及解决办法.md`](../../../knowledge/物理旋钮部分交互功能失效案例及解决办法.md)。

## 3. 隐藏日历、天气和萌宠页

### 3.1 用户功能

一级页面左右切换时不显示日历、天气和萌宠，但不删除原厂页面对象。

### 3.2 实现

原厂一级页面调度号中，`3` 是时钟、`4` 是日历、`5` 是天气、`6` 是设置、`7` 是萌宠。固件把原厂切页调用挂接到 `ap01_agents_primary_page_filter_and_switch`：

1. 目标是 `4` 或 `5` 时，按原厂传入的方向改写为时钟 `3` 或看板共用序号 `7`；
2. 目标是 `7` 时，不显示萌宠，而是取得萌宠状态对象并调用 `ap01_agents_show_page(1)` 显示看板概览；
3. 看板显示失败时，把目标改为设置 `6`，不留在半切换状态；
4. 调用原厂 `stock_switch_page` 后再读回实际调度号；如果没有真正切到目标，恢复萌宠状态并回到设置页。

该函数只过滤导航目标，不删除日历、天气或萌宠对象，因此原厂对象数量和注册顺序不变。

## 4. 在萌宠位置提供四页看板

### 4.1 用户功能

看板包含概览、周剩余额度、今日消耗和近 30 天消耗。概览按下进入详情，详情页左右循环，详情页按下返回概览。

### 4.2 复用原厂动图对象

固件不创建新页面或新动图对象。`ap01_agents_find_pet_state` 通过原厂主题对象取得第 `7` 页，再检查包装对象类型是 `10`，最后取得 `stock_pet_state`。

原厂 `stock_pet_state` 为 `16` 字节。固件把申请长度从 `16` 改为 `20` 字节，在偏移 `16` 新增 `agents_state`，原有四个字段保持原位置。状态编码为：

| 值 | 含义 |
| ---: | --- |
| `0` | 看板关闭 |
| `1` | 概览 |
| `2` | 周剩余额度 |
| `3` | 今日消耗 |
| `4` | 近 30 天消耗 |

`agents_state` 的高 16 位保存 `0xa501`，中间 8 位保存状态，低 8 位保存状态的按位取反值。 `ap01_agents_state_read` 同时检查标记、取值范围和反值；任一检查失败时返回无效状态并恢复萌宠。

### 4.3 页面状态机

`ap01_agents_stock_pet_left_entry`、`ap01_agents_stock_pet_right_entry` 和 `ap01_agents_stock_pet_enter_entry` 分别接管原厂萌宠回调中的三个局部分支，其他按键分支不变。

| 当前状态 | 左旋 | 右旋 | 按下 |
| --- | --- | --- | --- |
| 关闭 | 交还原厂萌宠左旋 | 打开概览 | 交还原厂萌宠按下 |
| 概览 | 关闭看板并切到设置 | 关闭状态后交还原厂右旋续行点 | 打开周剩余额度 |
| 周剩余额度 | 近 30 天消耗 | 今日消耗 | 返回概览 |
| 今日消耗 | 周剩余额度 | 近 30 天消耗 | 返回概览 |
| 近 30 天消耗 | 今日消耗 | 周剩余额度 | 返回概览 |

`ap01_agents_show_page` 先根据状态把原厂动图对象指向对应的内置“等待同步”画面，再写入状态，最后调用 `ap01_agents_apply_current` 尝试采用已下载画面。动图源设置失败时， `ap01_agents_show_failed` 立即调用 `ap01_agents_restore_pet`，不保留半完成的看板状态。

### 4.4 固件挂接点

| 原厂分支 | 文件偏移 | 新入口 | 原厂续行地址 |
| --- | --- | --- | --- |
| 萌宠左旋 | `0x0bd460` | `ap01_agents_stock_pet_left_entry` | `0xa00bc464` |
| 萌宠右旋 | `0x0bd712` | `ap01_agents_stock_pet_right_entry` | `0xa00bc716` |
| 萌宠按下 | `0x0bea64` | `ap01_agents_stock_pet_enter_entry` | `0xa00bda68` |
| 一级页面过滤 | `0x0bd092` | `ap01_agents_primary_page_filter_and_switch` | `0xa00bc096` |

## 5. 保护看板相邻的功率页

### 5.1 用户功能

底座离线或功率数据已失效时，在功率页按下旋钮不得崩溃或重启。

### 5.2 实现

原厂功率确认分支在文件偏移 `0x0bd8c6` 挂接到 `ap01_agents_stock_power_confirm_guard`。该函数检查底座连接指针 `0x62fc4cd8` 和总功率数据指针 `0x62fcaa00`：

- 两者都有效：跳回原厂功率确认续行地址 `0xa00bc8ca`；
- 任一无效：调用原厂端口离线处理，再调用原厂主页切换函数回到时钟调度号 `3`；
- 非确认事件直接交还原厂按键结束路径。

## 6. 让看板不遮挡系统时间和日期

### 6.1 用户功能

四页主标题位于系统时间和日期之间，正文不与系统顶部字段重叠，同时不浪费顶部下方空间。

### 6.2 实现

`features/agents_dashboard/renderer.py` 以设备坐标为基准，在四倍画布上绘制后缩小为 `320×240`。系统顶部位置使用两个已测量范围：

```text
时间：(19, 17) - (75, 33)
日期：(253, 16) - (316, 37)
```

`PAGE_TITLE_X` 取时间右边界和日期左边界的中点，再应用 `-3` 像素的视觉校正，结果为 `161`。 `PAGE_TITLE_Y` 取两个系统范围垂直中心的平均值，结果为 `25.75`。`_draw_page_title` 以中心对齐绘制 `14` 号字，正文从 `y=60` 之后开始。

主数字使用 `MiSans-Bold.ttf`，其他内容按层级使用 `MiSans-Medium.ttf` 和 `MiSans-Semibold.ttf`。字体文件位置以 [`fonts/README.md`](../../../fonts/README.md) 为准。

## 7. 从当前电脑生成真实看板数据

### 7.1 用户功能

看板显示当前电脑的额度、重置时间、今日消耗、近 30 天消耗、活动和常用插件，不上传会话正文。

### 7.2 采集链路

`collect_snapshot` 使用四个并行任务：

```text
当前电脑登录状态
  ├─ fetch_quota          -> 周剩余比例、重置时间
  ├─ fetch_reset_cards    -> 可用重置卡和到期时间
  ├─ fetch_profile        -> 30 天统计、活动、插件
  └─ scan_today_sessions  -> 今日输入、输出、缓存、请求数
```

本地会话扫描只提取令牌计数、模型名、时间和已有费用字段。对同一会话内的累计计数做差值，只累加当日增量；缓存读取量不得大于输入量，缓存写入量不得大于扣除缓存读取后的输入量。费用计算不写在画面坐标代码里，而是统一调用计费函数，价格来源以 [`Codex-模型API计费表.md`](../../../knowledge/Codex-模型API计费表.md) 为准。

四个来源各自记录是否可用。某一来源失败时，对应字段显示“无法获取”，其他来源仍然生成。

### 7.3 图片怎么生成

AGENTS 看板的视觉参考位于 [`reference/DESIGN/ap01-1.0.2_0031-opt.bin技术实现/image/`](image/README.md)。看板实际显示的主标题、字段名称、单位、提示语和四页排版以该视觉参考为准；其中的数值会随采集结果变化，不作为固定文案。

`render_all` 用同一个 `DashboardSnapshot`（一次采集结果的数据对象）生成概览、周剩余额度、今日消耗和近 30 天消耗。每一页都新建一张 `1280×960` 的纯黑画布，不读取视觉参考图片或其他图片作为底图。绘图程序按固定坐标画出光晕、圆环、折线、分隔线和文字，并从 `features/agents_dashboard/assets/icons/` 读取小图标，从运行时字体目录读取字体。画完后缩小为 `320×240`。周剩余额度采用第一张静态画面。圆环和半圆的彩色进度弧长度按剩余比例绘制：剩余比例为 `0` 时不绘制彩色进度弧，仅显示底环；区块标题颜色（如“本周剩余”）与视觉参考保持一致，使用强调黄色。

普通页面转为视觉静态的两帧 GIF：第一帧保留源图颜色；第二帧复制第一帧，然后只把右下角 `1` 个像素改为调色板中最接近的另一种颜色，确保当前设备端加载器能看到真实的第二帧。每帧等待时间设置为 `600` 秒，用户正常查看时按静态图呈现。

原厂图形资源规格以 [`系统软件、页面与图形资源.md`](../../../knowledge/AP01-官方固件分析/系统软件、页面与图形资源.md) 为依据：原厂固件存在 `320×240`、最多 `41` 帧、单帧最多 `255` 种实际颜色的 GIF，且原厂软件直接具备 PNG 和 GIF 解码能力。当前动态看板仍沿用已验证的 GIF 加载路径，不在未验证前改用 PNG。

今日消耗页的缓存命中率进度条按设备像素列绘制，不使用小数位置叠加矩形，避免缩小采样后出现短横杂色。

### 7.4 视觉一致性怎么保证

部署后日常刷新没有任何 AI 介入，视觉一致性分三层保证：

1. **运行时一致靠确定性**：渲染是确定性程序——同一份代码、同一份字体文件、同一份快照数据，画出的图逐像素一致。数据变化只改变数字和弧长，不改变版式。这一层不需要任何人工或 AI 参与。
2. **参数唯一来源**：全部视觉参数（颜色表、字体角色表、字号、坐标）集中定义在 `features/agents_dashboard/renderer.py` 顶部的常量区和四个 `render_*` 函数内；渲染不读取参考图。本节和第 7.3 节只钉总规则（字体角色、0% 无弧、标题强调色），具体坐标数值的唯一定义处是 `renderer.py`，文档不重复抄写，避免两处定义不一致。
3. **改代码时靠黄金图回归测试拦截**：`features/agents_dashboard/test_visual_golden.py` 用一份固定的合成快照（不包含真实个人数据）渲染四页，与 `features/agents_dashboard/testdata/golden/` 下的四张黄金图逐像素比对。换字体、改颜色、动字号、挪坐标或升级 Pillow 大版本导致画面变化时，测试失败。比对容差：允许不超过 `0.1%` 的像素出现大于 `60/255` 的偏差（跨电脑字体渲染的轻微抖动），允许不超过 `0.5%` 的像素出现 `12/255`～`60/255` 的轻微偏差（抗锯齿差异）；超出任一额度即失败。字体被换或颜色被改会造成数千像素大幅偏差，必然触发。

黄金图更新流程：先改本 DESIGN 记录新规定并人工确认新画面与视觉参考相符，再执行 `.venv/Scripts/python.exe -m features.agents_dashboard.test_visual_golden --update` 重新生成黄金图，两者必须同一次提交。视觉参考图 `image/` 目录是人工验收依据，黄金图是自动比对依据，两者由上述流程保持同步。

## 8. 把四页封装成设备可校验的结果包

### 8.1 用户功能

设备一次只采用同一批四页画面，不能出现某一页已更新、其他页仍是旧数据的情况。

### 8.2 主机端发布链路

`publish_current_result` 在输出目录中创建临时目录，按以下顺序执行：

```text
collect_snapshot
  -> render_all / render_weekly_batches
  -> png_to_device_gif / weekly_to_device_gif
  -> encode_package
  -> decode_package 回读验证
  -> 刷新四个动图和 manifest.json
  -> 最后替换 agents-dashboard.apag
```

设备只下载最后一步替换的 `agents-dashboard.apag`，因此生成中途的文件不会被设备读取。新包生成失败时，旧包保持不变。

### 8.3 结果包头

结果包头固定为 `64` 字节，整数使用低字节在前的顺序：

| 偏移 | 长度 | 字段 | 约束 |
| ---: | ---: | --- | --- |
| `0` | `4` | 标记 | 固定为 `APAG` |
| `4` | `2` | 版本 | 固定为 `2` |
| `6` | `2` | 包头长度 | 固定为 `64` |
| `8` | `4` | 生成代号 | `1..0x7fffffff` |
| `12` | `4` | 整包长度 | 包头与四页总长度 |
| `16` | `8` | 生成时间 | 秒级时间 |
| `24` | `4` | 页数 | 固定为 `4` |
| `28` | `4` | 保留字段 | 固定为 `0` |
| `32` | `16` | 四页长度 | 四个 `4` 字节整数 |
| `48` | `16` | 四页 `CRC32` | `CRC32`（用四字节数字检查页面是否损坏） |

包头后面按概览、周剩余额度、今日消耗、近 30 天消耗的顺序直接连接四个动图。整包不超过 `384 KiB`（按 1024 字节计算的容量单位），单页不超过 `96 KiB`。主机端另外检查每页为 `320×240`、至少两帧、每帧色表不超过 `256` 项，并能解码到最后一帧。PNG 源图不超过 `256` 种颜色时精确保留；超过 `256` 种颜色时使用 `256` 色且关闭抖动，避免碎点。

## 9. 通过局域网自动更新看板

### 9.1 用户功能

用户先按优先级填写 1～10 个服务地址，再从公开固件二次制作个人固件。电脑每 300 秒生成新数据，设备每 300 秒按配置顺序跨服务端取包。

### 9.2 电脑端服务

`BridgeState`（服务运行状态对象）的 `refresh` 方法调用 `publish_current_result`。服务启动时先刷新一次，随后由后台线程每 `300` 秒刷新一次。每次刷新都按第 8.2 节的顺序，在临时目录完成数据采集、四页绘制、设备动图转换、结果包合成和回读检查。全部成功后才替换服务目录中的四页动图、清单和结果包；任一步失败时保留能通过 `decode_package` 的上一次结果。

定时刷新只更新服务目录，不改写视觉参考图片。

- `/a` 请求：返回 `agents-dashboard.apag`；
- `/health` 请求：返回服务状态、四个数据来源状态、刷新和请求计数；
- 其他路径：返回不存在；
- 每次响应都带准确长度并禁止缓存。

macOS 运行路径为：

| 内容 | 路径 |
| --- | --- |
| 服务代码、字体、图标 | 用户指定的部署目录（默认 `~/Library/Application Support/Cuktech/AP01/agents-dashboard-service/`） |
| 四页画面、动图、结果包和清单 | `<部署目录>/service-output/` |
| 采集缓存 | `<部署目录>/service-cache/` |

macOS 的独立部署改用用户指定或默认的部署目录；其中服务代码、字体、四页画面、动图、结果包、清单和缓存均位于该目录。文件复制、登录自启注册、检查命令和默认路径只见 [`AGENTS 看板常驻部署`](../../../features/agents_dashboard/deployment/README.md#macos)。

Windows 部署路径为：

| 内容 | 路径 |
| --- | --- |
| 服务代码、字体、图标 | 用户指定的部署目录（默认 `%LOCALAPPDATA%\Cuktech\AP01\agents-dashboard-service`） |
| 四页画面、动图、结果包和清单 | `<部署目录>\service-output\` |
| 采集缓存 | `<部署目录>\service-cache\` |

Windows 用 `tools/deploy-agents-dashboard.ps1` 一次性部署：脚本把服务代码、字体和图标复制到用户指定目录（用户无要求时用默认目录），生成 `run-bridge.ps1` 启动脚本，并注册当前用户登录时自启的计划任务（Windows 系统自带的定时任务功能，重启电脑并登录后自动运行）。部署在固件刷入完成后执行，部署路径由 AI 显式询问用户。部署完成后服务独立于本项目运行，删除本项目不影响设备取包。数据来源仍是用户主目录的 Codex 登录态（`~/.codex`），登录态不进入部署目录，也不随部署复制；因此计划任务用当前用户身份而非系统账户运行，否则读不到登录态。

Windows 的参数、复制内容和完成检查只见 [`AGENTS 看板常驻部署`](../../../features/agents_dashboard/deployment/README.md#windows)。

### 9.3 地址配置与两种固件

地址配置的唯一原文是本节。其他文档和代码注释只引用本节，不重复规定变量含义。

本机实际值保存在项目根目录的 `env/agents-dashboard.env`。该文件权限必须是 `0600`，并由 `.gitignore` 排除。仓库只提交 `env/agents-dashboard.env.example`。配置包含：

| 名称 | 用途 |
| --- | --- |
| `AP01_AGENTS_HOSTS` | 按访问优先级排列的服务电脑地址，用英文逗号分隔 |
| `AP01_AGENTS_PORT` | 所有服务电脑共同使用的看板服务端口 |

构建程序接受 1～10 个不同的 IPv4 局域网地址和一个 `1` 至 `65535` 的端口。地址前后空格会被去掉，空项、重复地址、局域网以外的地址和超过 10 项的配置都会停止构建。程序在内存中按填写顺序组成 `http://<地址>:<端口>/a` 地址表，不把真实值打印到终端。

固件分为两种：

| 文件 | 是否包含地址 | 用途 |
| --- | --- | --- |
| `artifacts/firmware/ap01-1.0.2_0031-opt.bin` | 否 | 公开发布和检查无地址版本，不直接安装 |
| `ap01-1.0.2_0031-opt-personalized.bin` | 是 | 只保存在用户电脑上，用于检查、模拟和安装 |

公开固件把地址数量编译为 `0`。设备保留看板页面和等待画面，但不发起看板取包。二次制作入口读取本机配置，把地址按填写顺序写入设备端程序；个性化固件及其构建记录和交互报告不得写入仓库。

### 9.4 设备端如何跨服务端取数据

固件把原厂网络执行调用挂接到 `ap01_agents_webclient_wrapper`。包装函数先保存原厂网络上下文：

| 上下文偏移 | 字段 |
| ---: | --- |
| `+8` | 地址指针 |
| `+36` | 超时值 |
| `+60` | 数据接收函数 |
| `+64` | 数据接收参数 |
| `+96` | 响应状态 |
| `+108` | 网络工作状态 |

原厂天气请求仍由原厂网络函数执行。天气请求返回后，包装函数调用 `ap01_agents_download_package` 取看板包，然后恢复上述字段。如果本轮来自天气路径，最终返回原厂天气的返回值和响应状态，看板成功或失败都不改写它们。

原厂网络入口、调用时机和上下文字段的事实依据见 [`通信、存储、更新与恢复`](../../../knowledge/AP01-官方固件分析/通信、存储、更新与恢复.md#7-天气任务首次取数条件)。本次地址表扩展只改变自定义看板地址的数量和尝试顺序，不增加原厂网络入口，也不改变原厂天气任务的调用条件。

个性化固件中的 `ap01_agents_download_package` 每轮按下面的顺序执行：

1. 使用地址表中的第一个地址请求 `/a`；
2. 连续 3 秒没有下载进展时，清理本轮未发布文件并改用下一个地址；
3. 任一服务返回完整且检查通过的四页包后，立即停止本轮后续请求；
4. 所有地址都失败时，保留本次开机期间最后一次成功画面；
5. 300 秒后开始新一轮，并再次从地址表中的第一个地址开始。

这里的 3 秒是单地址无进展超时，不是为连接、读取和整包分别设置三个计时器。各服务彼此独立，各自根据本机登录状态和本地会话生成完整包；设备不合并多台电脑的数据，只采用本轮首先取得的完整包。

公开固件的地址数量为 `0`，`ap01_agents_download_package` 直接返回，不调用网络函数，也不会把原厂天气地址误当成看板地址。

### 9.5 独立取包定时器（standalone_timer 变体）

#### 是什么

一种新的取包触发方式：看板取包由**独立注册的原厂定时器**每 300 秒驱动一次，与原厂天气任务完全解耦。天气任务活着、卡住或死亡都不影响看板取包。

#### 为什么

9.4 节的触发链把看板取包挂在天气任务的联网调用之后。真机抓包证明：当设备运行环境中的 DNS 服务器不可达时，天气任务在网络前置环节阻塞退出，看板取包从未获得执行机会，屏幕永远停在"等待首次同步"。此外，V2 固件的传输模式静态变量位于只读载荷 `.data` 区，运行时实读原厂 GIF 填充字节（1782481712，见取证文档第 3 节实测），包装函数因此长期走"跳过天气、直接下载"的错误分支——静态可写状态在只读载荷中本就不可用。环境故障无法从固件侧根治，触发链必须自带独立心跳。事故取证、`.data` 实测与原厂定时器机制的完整证据见 [`原厂定时任务机制与webclient上下文构造`](../../../knowledge/AP01-官方固件分析/原厂定时任务机制与webclient上下文构造.md)。

#### 怎么做

构建变体 `standalone_timer=1` 时定义 `AP01_AGENTS_STANDALONE_TIMER`，设备端行为：

1. **注册（每秒重试直到成功）**：`ap01_agents_ui_timer_wrapper` 开头调用 `ap01_agents_standalone_timer_ensure`。该函数从原厂天气定时器全局结构 `0x62fca9a8` 读取事件循环指针（用 `+8` 处类型标记 `0x0d` 验证原厂已完成初始化），遍历事件循环的对象链表查找"类型为定时器且回调等于本变体回调"的节点（上限 64 个节点，防御链表异常导致 UI 秒回调卡死）；找不到时申请 0x58 字节定时器结构、调用原厂 `timer_init` 和 `schedule`（首次延时 2000 毫秒）。已找到则直接返回。UI 定时器包装每秒执行，因此事件循环未就绪的窗口期最多 1 秒。
2. **取包回调**：定时器回调收到定时器结构指针（回调签名 `cb(handle)`，与原厂一致）。回调用 `fw_malloc` 申请 116 字节 webclient 上下文（`"GET"` 方法字符串为载荷自备只读常量、4096 字节堆接收缓冲、超时秒数 5、`+0x70` 就绪字节置 1，字段按取证文档第 2 节的表填充），调用现有 `ap01_agents_download_package` 完成取包和三槽发布（该函数无任何改动），随后释放接收缓冲和上下文，最后以 `AP01_AGENTS_REFRESH_SECONDS × 1000` 毫秒在回调尾部再次预约自身。回调不调用 `cancel`：取证文档证实 `schedule` 对已排队定时器会先内部取消再重新插入（重启式语义），原厂天气回调同样是尾部直接再预约。上下文用堆而非栈分配，是因为本变体沿用 FW-PAGE-011 的 96 字节单函数静态栈上限。
3. **天气路径退位**：该变体下 `ap01_agents_webclient_wrapper` 改为一行透传 `return fw_webclient_perform(context);`——不读写任何上下文字段、不调用 `ap01_agents_download_package`，原厂天气请求（含 HTTPS 路径）按原字节执行并原样返回。传输模式静态变量在该分支下不再被读取，其 flash 幻读问题随之消失。实测（取证文档第 3 节）：V2 个性化固件中 `agents_transport_mode` 幻读值 1782481712 ≠ 0，旧包装函数因此整体跳过原厂天气请求分支——旧固件的天气请求从未真正发出，与抓包"零天气流量"一致。
4. **下载禁用开关改编译期**：`ap01_agents_download_package` 原先用静态变量 `download_disabled`（`.bss`）做运行时禁用判断。实测该位置在最终固件 `0x24f404` 处保留原厂字节 `63 1c 2a 50` ≠ 0，即旧固件的下载调用永远在入口处返回 `ERR_INVAL`——"等待首次同步"的第二个独立原因。该开关改为 `#if AP01_AGENTS_DISABLE_DOWNLOAD` 编译期判断（公开固件编译为桩函数，个人固件直接进入下载主体），静态变量删除。构建校验同步调整：禁用下载的构建中下载包装的 `fw_malloc`/`fw_free` 调用次数预期为 0。
5. **零静态可写状态**：本变体不新增任何静态可写变量。定时器结构的指针不需要保存（回调参数自带），"是否已注册"用对象链表探测而不是布尔标志。这是对载荷只读区限制的遵守（取证文档第 3 节：`.data`/`.bss` 初值不进固件且运行时写入无效）。
6. **线程与并发**：定时器回调运行在原厂事件循环线程，与天气任务同线程串行执行，不存在并发冲突；回调内使用与天气任务相同的 `fw_malloc`/`fw_free`。

复用的原厂函数地址（C 侧与 `VA_STOCK_UI_TIMER` 等一致用函数指针直调，不改 `result_loader.ld`；该文件的 PROVIDE 仅供汇编使用，本变体无汇编改动）：

| 地址 | 用途 |
| --- | --- |
| `0xa009b376` | `timer_init(loop, timer)`：初始化定时器结构并头插入事件循环对象链表 |
| `0xa009b3b6` | `schedule(timer, cb, 64 位毫秒延时, 参数1, 参数2)`：重启式单发预约 |
| `0x62fca9a8` | 原厂天气定时器（RAM 全局，读取事件循环指针并验证类型标记） |

#### 构建与验证

- `sync_build.py` 新增 `standalone_timer` 制作参数：变体沿用 V2 的页面拓扑（固定隐藏一级页、天气页隐藏、电源确认保护、交互模拟 `FW-PAGE-011` 全部不变），仅追加 `AP01_AGENTS_STANDALONE_TIMER` 与 `AP01_AGENTS_REFRESH_SECONDS` 两个编译宏，并把 `ap01_agents_standalone_timer_ensure`、`ap01_agents_standalone_timer_cb` 加入必备符号表；构建时对两函数的反汇编做专项校验（注册路径唯一 malloc/timer_init/ schedule，回调路径恰好两次 malloc/两次 free/一次下载调用/一次尾部再预约，包装函数不含下载调用）。
- `app/ap01_firmware.py` 的 `agents-personalized-build` 与 `agents-release-build` 固定传 `standalone_timer=True`：个人固件获得独立取包心跳；公开固件（无地址）的天气路径从"被幻读误跳过"恢复为按原字节执行，取包定时器周期回调只调用编译期禁用的桩函数，不产生任何网络请求。
- 主机自测（`test_build.py`，`AP01_LOADER_SELF_TEST`）覆盖三分支：注册探测（含第二次 ensure 不重复注册的幂等性）、回调取包（上下文字段、下载调用、按刷新周期再预约）、天气路径透传（原厂上下文字段零改动、返回值原样透传）。自测构建是 64 位主机指针， method/buffer/buffer_size/ready 四个字段若沿用固件的 +4/+48/+52/+112 偏移，会与 url(+8)、sink(+48)、work_state(+108) 的 8 字节指针写各重叠 4 字节（固件 32 位指针无此问题）；这四个偏移在自测构建中改为 16/24/32/40（与 `SINK_OFFSET` 的既有规避同法），固件构建保持原厂上下文布局不变。

#### 怎样算完成

1. 构建产物的符号表含 `ap01_agents_standalone_timer_ensure` 和 `ap01_agents_standalone_timer_cb`，主机自测三分支与反汇编专项校验全部通过；
2. 真机刷入后：桥接服务健康检查的请求计数在 5 分钟内开始增长（首次预约 2 秒 + 周期 300 秒），看板脱离"等待首次同步"；
3. 屏蔽天气任务（位置编号不可得）时看板仍按周期取包。

三条已于 2026-08-20 真机验证：V3 个人固件（SHA256 `f4ef6c86…ac677`）经本机 443 自签 HTTPS 路径刷入测试设备，回读逐字节一致、安装阶段与重启均被轮询观察到；设备重启后，第一优先桥接服务收到首次取包请求，约 5 分钟后收到第二次（间隔 296 秒，符合 300 秒周期）。当次环境 DNS 不可达、天气任务正处阻塞状态，取包仍按周期发生，第 3 条随第 2 条一并成立。

V3 的设置阶段输入含"中途反向边沿过滤"补丁，真机表现为左旋在所有页面失效（案例见 [`物理旋钮部分交互功能失效案例及解决办法`](../../../knowledge/物理旋钮部分交互功能失效案例及解决办法.md)）。 2026-08-20 已重建不含该补丁的三个区间设置阶段固件（SHA256 `24e50a65…fa13`），并基于它重建公开固件（SHA256 `796abb53…48c09`）与 V4 个人固件（SHA256 `c044b85a…660d0`，交互模拟 19 场景 118080 穷举序列全部通过）。 V4 已于 2026-08-20 经同一 443 自签 HTTPS 路径刷入同一测试设备：回读逐字节一致、安装与重启被轮询观察到、上线后按 300 秒周期取包（实测间隔 295 秒）、左旋在首页、 AGENTS 看板和设置页恢复正常，设置列表首尾循环正常。

## 10. 下载失败时不破坏当前画面

### 10.1 用户功能

网络失败、结果包损坏或只下载了部分页面时，看板继续显示本次开机期间最近一次成功画面。

### 10.2 三槽下载

设备在 `/tmp` 中使用三组槽位，每组四个动图：

```text
/tmp/.ap01a00.gif ... /tmp/.ap01a03.gif
/tmp/.ap01a10.gif ... /tmp/.ap01a13.gif
/tmp/.ap01a20.gif ... /tmp/.ap01a23.gif
```

`/tmp/.ap01a.meta` 是已发布记录，`/tmp/.ap01a.ack` 是显示程序已采用记录。两者都使用同一个 `agents_meta` 结构：

```text
u32 magic       = 0x47415041
u32 generation  = 1..0x7fffffff
u32 slot        = 0..2
u32 check       = magic ^ generation ^ slot ^ 0x5101a501
```

`u32`（不保存负数的四字节整数）是上述四个字段的存储类型。

新下载优先选择不是 `meta.slot` 且不是 `ack.slot` 的槽位，避免覆盖正在显示或等待采用的数据。下载状态结构大小为 `136` 字节，在取包开始时申请，结束时释放。

### 10.3 流式校验和发布

`ap01_agents_sink` 在网络数据到达时边接收边检查，不需要把整包放进内存：

1. 先收齐 `64` 字节包头并调用 `validate_package_header`；
2. 按包头长度依次打开四个槽位文件；
3. `gif_consume_byte` 用状态机检查动图头、全局色表、扩展块、图像描述块、局部色表、图像数据和结尾；
4. 同时累计每页 `CRC32` 和帧数；
5. 单页结束时检查长度、文件头、状态机已到结尾、帧数至少为 `2` 以及 `CRC32` 一致；
6. 四页都完成、实际总长度等于包头总长度、网络返回成功且响应状态为 `200` 时，才把新代号和槽位写入 `meta`。

任一检查失败时调用 `clear_slot`清空当轮槽位，不改写 `meta`，因此当前画面不变。

### 10.4 显示端采用

`ap01_agents_ui_timer_wrapper` 每次先调用原厂界面定时函数，然后只在当前调度号是 `7`、萌宠包装对象和看板状态都有效时继续。

它读取 `meta` 和 `ack`；两者的代号和槽位相同时不重复设置动图源。不同时调用 `ap01_agents_apply_current`，根据 `agents_state - 1` 选择新槽位中的页面，设置成功后写入 `ack`。动图对象拒绝新文件时恢复萌宠，不写 `ack`。

### 10.5 重启边界

四页文件、`meta` 和 `ack` 都位于 `/tmp`。当该目录在设备重启后被清空时，固件先显示内置 “等待同步”画面，直到取得新的完整结果包。当前没有实现重启后保留上次成功画面。

## 11. 固件怎样制作和限制修改范围

### 11.1 载荷布局

`build_live_data_weather_hidden_dashboard_v2_firmware` 把当前功能参数传给 `build_sync_firmware`：

```text
reuse_stock_pet = true
shared_page_filter = true
fixed_hidden_primary_pages = true
weather_hidden_primary_page = true
power_confirm_guard = true
interaction_name = FW-PAGE-011
endpoint_timeout_seconds = 3
refresh_seconds = 300
```

新增程序使用 RISC-V（该设备处理器的指令格式）编译和链接，链接地址固定为 `0xa02465d0`，对应文件偏移 `0x2475d0`。该区域容量是 `60,934` 字节，当前载荷为 `32,096` 字节，不包含需要运行时修正的地址，单函数固定临时区上限为 `96` 字节。

载荷空间来自缩小原厂第一张动图的文件大小：制作程序先核对原动图指纹，再写入等效的优化动图，最后把新增程序写入腾出的后续空间。

### 11.2 固定补丁集

固件只允许修改以下类型的区域：

- 设置列表循环，由输入固件提供；
- 原厂萌宠状态长度；
- 原厂动图长度和优化后动图数据；
- 五个页面局部挂接点及其近跳板；
- 原厂网络执行、位置查询和界面定时器的局部挂接点；
- 新增程序区域；
- 文件尾恢复校验值。

`build_sync_firmware` 在每次替换前断言原字节完全一致，替换后用 `validate_candidate` 检查固件长度、清单外字节、恢复结构和恢复校验。页面路径反汇编检查还会禁止调用新建页面、删除页面、新建动图和通用内存申请函数；下载路径中的 `136` 字节申请只允许出现在网络下载调用链中。

### 11.3 刷入前检查

构建过程使用 `InteractionContract`（页面操作规则模型）模拟一级页面、四页看板、功率连接状态以及左旋、右旋、按下事件。构建内嵌模拟失败时，`build_sync_firmware` 在写入成品前立即停止。独立操作报告使用深度 `8`。

当前保留的独立操作报告有一个已知证据缺口：报告合约中的“固定隐藏一级页”是关闭状态，与固件构建记录不一致。因此，该报告不能单独作为三个隐藏页路径的证明；已刷入固件的真机页面行为以用户已完成的屏幕验收为准。
