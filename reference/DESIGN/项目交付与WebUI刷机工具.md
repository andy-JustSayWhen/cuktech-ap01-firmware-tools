# 项目交付与 WebUI 刷机工具 DESIGN 落点

## 1. 文档状态

本文只为本轮重写后的 SPEC 建立实现落点和模块边界，确保后续实现不得绕过 DESIGN。
具体技术选型、接口、状态结构和测试设计必须在写对应代码前继续细化；本轮不据此新增功能代码。

本项目采用的应用架构及模块归属规则只见
[`Architecture.md`](../Architecture.md)，本文不重新定义。

## 2. 文档传递与自动核对

承接 `SPEC-DOC-001` 至 `SPEC-DOC-004`、`SPEC-VERSION-001` 至 `SPEC-VERSION-003`。

- Brief 文件指纹、逐句定位符和 SPEC 条款编号由文档核对任务检查；
- SPEC 条款变更后，核对任务检查 DESIGN 索引中是否仍有对应落点；
- 代码、测试和生成文档引用稳定条款编号，不依赖章节序号；
- 事实、依赖、安全、操作和视觉变化分别回写其唯一上游文档，再更新受影响条款。

## 3. 产品交付边界

承接 `SPEC-PRODUCT-001` 至 `SPEC-PRODUCT-006`。

- `app/` 只组合设备识别、固件核对、刷机执行、结果验收和发布检查功能；
- 平台差异收敛到无业务含义的平台能力，用户流程和状态合同由功能模块持有；
- 浏览器页面不得直接接触设备凭据、账号凭据、开发者路径或固件内部修改细节；
- Windows 与 macOS 共用同一套用户流程、结果状态和验收数据结构；
- 发布过程在产物形成后、对外提供前执行敏感内容检查，检查失败时不生成可发布结果。

## 4. MVP 编排

承接 `SPEC-MVP-001` 至 `SPEC-MVP-009`。

- MVP 状态由官方基线、规范工作流、阶段成品、完整成品、真实刷机、文档回写、双平台 WebUI
  和其他用户操作八组结果共同计算；
- 任一组结果缺失或失效时，MVP 状态保持未完成；
- 阶段成品结果不能替代完整成品或 WebUI 结果；
- 固件相关结果由
  [`AP01 1.0.2_0031 优化固件 DESIGN`](AP01-1.0.2_0031-opt.bin.md) 提供，本文件不重复实现。

## 5. WebUI 状态流

承接 `SPEC-FLASH-001` 至 `SPEC-FLASH-008`。

- 前端按准备条件、设备识别、固件核对、风险确认、刷机执行和结果六个状态展示；
- 后端每次只接受一个冻结设备身份和一个冻结成品身份组成的执行上下文；
- 状态变更必须附带对应证据；没有证据时只能保持等待或无法确认；
- 写入动作具有单次执行标识，状态未知时只允许查询，不再次下发；
- 平台能力只负责启动本地服务、打开 Chrome 和访问本机文件，不能改变刷机业务状态；
- 零基础交付包必须包含启动入口、依赖检查和页面内处置提示，不要求用户输入内部命令；
- 前端显示经过最小化处理的设备和固件信息，后端原值不得进入页面、日志或导出结果；
- 具体设备登录、上传、更新指令和验收接口必须先复核参考项目，再在后续 DESIGN 修订中固定。

## 6. 依赖、复用与安全治理

承接 `SPEC-GOV-001` 至 `SPEC-GOV-008`。

- 构建和运行入口只从 `requirements.md` 读取依赖合同；
- 参考项目资产先复制、归属和改造，再由本项目模块公开入口使用；
- 运行与发布检查拒绝引用参考项目绝对路径；
- 固件安全判断只读取固件制作规范及其证据，不在功能代码内维护第二套规则；
- 文档核对任务检查 Brief、SPEC、DESIGN 和代码之间的引用方向。

## 7. 总体验收编排

承接 `SPEC-ACCEPT-001` 至 `SPEC-ACCEPT-006`。

- 固件功能验收结果由优化固件 DESIGN 的构建与真机验证章节提供；
- WebUI 验收分别在 Windows 与 macOS 执行同一组浏览器流程；
- 发布验收汇总敏感内容检查、原厂能力回归、原厂回刷和安全工作流；
- 验收记录必须绑定成品指纹、目标设备范围、环境和时间；
- 历史成品、其他设备或其他环境的结果不能自动继承到当前发布候选。

## 8. 写代码前的继续设计门禁

下列内容在对应代码开始前必须补齐：

1. 参考项目可复用资产及边界；
2. Windows 与 macOS 本地服务启动方式；
3. 六阶段状态与接口字段；
4. 单次写入标识和状态恢复；
5. 敏感内容检查范围；
6. 双平台测试与发布产物结构。

任一项未形成可执行 DESIGN 时，不得开始对应功能代码。
