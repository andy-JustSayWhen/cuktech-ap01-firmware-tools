# AP01 第三方固件制作与刷机工具 SPEC 总索引与公共合同

本文档是本项目唯一的 SPEC 总索引，记录完整项目的公共产品合同、需求归属、规范状态和
验证状态。每项永久 Feature 使用 [`SPEC/`](SPEC/) 下的一份独立文档描述。

本文档不增加 [`brief.md`](brief.md) 没有声明的开发需求。操作流程归入 [`SOP/`](SOP/)，
固件安全门槛归入 [`firmware-safety.md`](firmware-safety.md)，技术实现归入 design 系列，
设备与固件证据归入 [`knowledge/`](../knowledge/README.md)。

本项目采用 FCMA 架构，详细内容见 [`Architecture.md`](Architecture.md)。本目录只声明功能
合同和组合关系，不重新定义应用架构。

## 1. 唯一 SPEC 集合

- `SPEC.md` 只负责公共合同、需求覆盖和功能索引；
- `SPEC/` 中每份功能文档只负责一个用户可以独立使用和验收的 Feature；
- 文件夹只做主题归类，不代表 Feature；
- 不创建临时 SPEC、阶段 SPEC 或另一套完整项目 SPEC；
- 当前优先定稿的功能文档以后继续作为完整项目 SPEC 的组成部分；
- 同一功能的前端、服务端、设备端、异常和验收必须在同一份功能文档中闭环；
- 公共系统能力写入本文件或后续 design，不伪装成用户功能；
- 未经真实制作与刷机闭环确认的工具界面和产品形态只登记，不提前编造。

## 2. 状态定义

### 2.1 规范状态

| 状态 | 含义 |
| --- | --- |
| 未定义 | Brief 已提出方向，但尚未形成可执行的用户功能合同 |
| 待确认 | 已形成部分合同，仍有会改变用户表现的事项没有确定 |
| 已定稿 | 用户表现、异常和验收已经足以进入 design |
| 待真实闭环后拆分 | 必须先取得真实制作或刷机记录，才能判断功能边界 |

### 2.2 验证状态

| 状态 | 含义 |
| --- | --- |
| 未实现 | 本项目尚无对应实现 |
| 静态证据 | 只能由固件、源代码或文件检查证明 |
| 离线验证 | 本项目构建结果已经通过离线检查，但没有完成设备安装验收 |
| 真机验证 | 已在明确设备、版本和环境中完成对应功能验收 |

规范状态和验证状态必须分开记录。“已定稿”不代表已经实现，“静态证据”不代表已经在真机
运行成功。

## 3. 证据等级

| 等级 | 可以支持的结论 |
| --- | --- |
| 用户需求 | 证明产品应当实现什么，不证明已经实现 |
| 官方固件静态证据 | 证明当前精确固件中存在的字符串、数据、资源或代码 |
| 参考项目证据 | 证明参考项目在记录环境中实现或验证过的能力 |
| 本项目离线证据 | 证明本项目构建、差异、边界或自动测试结果 |
| 本项目真机证据 | 证明指定设备、固件、网络和服务环境中的实际结果 |

官方版本、字节数或文件指纹变化后，当前版本的地址、偏移和修改结论全部失效，必须重新
分析。

## 5. Feature 组合公共合同

- 每份功能文档声明自己的前端入口、输入、状态、输出、异常和验收；
- 多个 Feature 的页面切换和事件路由由应用入口组合，不由一个 Feature 调用另一个 Feature；
- 多个 Feature 需要相同数据时，共同读取同一份公共数据结果，不读取其他 Feature 的内部状态；
- 公共的旋钮输入、设置存储、数据读取、图片生成、最后成功结果保存和服务端尝试能力不建立
  伪 Feature；
- 后续代码模块及依赖关系必须遵守 [`Architecture.md`](Architecture.md)；
- 后续工具 A 和工具 B 只能通过公开输入输出交接，不复制或读取对方内部状态。

## 6. AGENTS 看板公共数据合同

### 6.1 允许显示的数据

服务端和设备端只处理 Brief 明确要求的数据：

| 数据范围 | 字段 |
| --- | --- |
| 本周剩余额度 | 剩余百分比、下次重置倒计时、重置时间、可用重置卡数量、每张卡的发放时间、到期时间和过期倒计时 |
| 今日消耗 | 总消耗 Token、请求数、总成本、输入、输出和缓存命中 |
| 近 30 天消耗 | 累计消耗、最长任务时长、活动洞察、常用插件 |
| 近 7 天消耗 | 每天的消耗结果，用于概览曲线 |

参考图中出现但 Brief 没有点名的字段，不进入本项目数据合同。

### 6.2 数据来源与缺失值

- 服务端从当前用户已经登录的 Codex 环境和 Brief 点名的本机应用缓存中读取数据；
- 本地任务记录只用于计算汇总值，不把任务原文交给 AP01；
- 不同服务端环境可以提供不同字段；
- 某字段无法从当前服务端准确取得时，该字段显示“无法获取”；
- 缺失值不得伪造成 `0`、空字符串或估算值；
- 同名字段在概览和详情中必须使用同一份公共数据结果；
- “今日”和“近 30 天”的统计时区与边界必须在数据服务 design 中统一确定，未确定前不得
  由各功能自行计算。

### 6.3 刷新与最后成功结果

- 标准刷新周期为 5 分钟；
- 数据读取、字段处理和最终画面全部成功后，才能替换最后一次成功结果；
- 单个字段确定无法取得时，可以用“无法获取”生成一份完整的新结果；
- 本轮刷新过程异常时，继续提供最后一次成功结果；
- 服务端重启后继续提供重启前最后一次成功结果；
- AP01 请求失败时继续显示设备内最后一次成功画面；
- 设备没有任何成功结果时，使用完整页面结构并把无法取得的字段显示为“无法获取”，不在
  屏幕显示网络错误或程序报错。

### 6.4 画面合同

- AP01 最终显示画布为 320×240；
- 首次批准的视觉底图不包含实时数据文字；
- 服务端把实时数据放入底图的对应文字槽位，生成最终画面；
- AP01 获取并显示的是最终画面，不是空白底图；
- 最终格式优先选择 AP01 已验证支持且满足画面要求的最小体积格式；
- 没有动图需求时不得仅因参考项目使用 GIF（动图格式）就强制生成 GIF；
- 具体格式、压缩方式和资源上限由 design 根据当前精确固件证据确定。

### 6.5 服务端运行合同

- 服务端目标环境包括 Windows、macOS、Linux NAS 和 Linux 云服务器；
- 服务端在对应系统重启后自动恢复运行；
- AP01 按保存顺序尝试多个服务端；
- 当前服务端不可达时，继续尝试下一个服务端；
- 服务端地址的配置入口和持久化方式等待真实固件闭环后单独拆分，不在当前功能文档中
  编造；
- 服务端切换超时、重试次数和恢复原服务端的规则由后续 design 在不改变上述用户表现的
  前提下确定。

### 6.6 敏感信息边界

AP01 只取得最终显示数据或最终画面，不取得：

- Codex 卡密或登录信息；
- 米家登录态或米家账号信息；
- AP01 设备身份信息；
- 本地任务原文；
- 本机文件路径；
- 服务端保存的其他账号信息。

项目、固件、构建清单、日志和发布物不得包含开发者的上述敏感内容。

## 7. AGENTS 看板公共导航合同

- AGENTS 看板概览作为一级页面参与原厂一级页面轮换；
- 在概览页按下并松开旋钮，应用入口显示“查看周剩余额度详情”Feature；
- 第一次进入详情时固定显示周剩余额度详情；
- 在详情区域向右旋转，依次显示周剩余额度、今日消耗、近 30 天消耗，并从末尾回到开头；
- 在详情区域向左旋转，按相反顺序显示，并从开头回到末尾；
- 在任一详情页按下并松开旋钮，应用入口返回 AGENTS 看板概览；
- 页面切换只改变当前显示的 Feature，不允许详情 Feature 互相调用或读取内部状态；
- 熄屏状态下的首次旋钮操作继续遵守原厂唤醒处理，不能同时误触发页面业务操作。

原厂旋钮证据见
[`AP01 物理旋钮原厂功能映射表`](../knowledge/AP01-物理旋钮交互设计/AP01-物理旋钮原厂功能映射表.md)。

## 11. 阶段推进与维护

1. 当前六项 Feature 定稿后，进入对应 design；
2. design 通过后制作候选优化固件；
3. 按安全规则完成离线检查、仅下载、正式安装和真机验收；
4. 只根据真实证据更新验证状态；
5. 完成首次闭环后拆分工具 A 和工具 B 的 Feature；
6. 新功能继续加入同一套 `SPEC/`，不得复制现有设备功能正文。

开发需求变化先修改 `brief.md`；用户表现、状态或验收变化修改对应 SPEC；技术实现变化修改
design；操作顺序和停止条件变化修改 `SOP/` 与 `firmware-safety.md`；固件证据变化先更新
`knowledge/`，再同步本文。
