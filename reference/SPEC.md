## 1. 产品目标、用户与发布边界

`SPEC-PRODUCT-001`：产品必须为酷态科 10 号电能基站 AP01 屏幕提供第三方固件制作和刷机能力。

`SPEC-PRODUCT-002`：产品既支持开发者本人使用，也必须形成其他用户能够取得和使用的交付物。
没有固件开发经验的用户不得被要求理解文件偏移、处理器指令、设备通信命令或命令行参数。

`SPEC-PRODUCT-003`：开发与首次完整验证优先在 macOS 完成；产品行为、数据格式和操作流程必须
同时为 Windows 版本保留一致实现边界，不能把只在 macOS 存在的能力写入用户功能合同。

`SPEC-PRODUCT-004`：Windows 与 macOS 用户刷机时，只通过 Chrome 打开 WebUI 完成操作。
正式交付不得要求用户另外使用命令行、修改脚本或直接调用设备接口。

`SPEC-PRODUCT-005`：项目、固件、安装包、图片、日志、缓存、说明文档和其他发布内容均不得包含
Codex 卡密、米家登录态、AP01 设备信息、米家账号信息或开发者的其他敏感内容。

`SPEC-PRODUCT-006`：同一项用户操作在 Windows 与 macOS 上必须使用相同名称、相同阶段顺序、
相同确认含义和相同成功或失败判定；平台差异只能由 DESIGN 在实现层处理。

## 2. MVP 完成合同

本节整体承接 Brief 中“最小可用版本”的范围声明。

`SPEC-MVP-001`：开始制作前，系统必须取得并通读小米云当前提供给目标型号的最新官方固件，
固化其身份、结构、校验方式和官方制作规律。当前 Brief 指定的制作基线是
`ap01-1.0.2_0031.bin`；如果小米云最新版本不再与它一致，现有成品不得继续构建、安装或发布，
必须先重新完成分析并更新上游文档。

`SPEC-MVP-002`：项目必须持续维护固件制作规范和刷机安全规范。两类规范都必须包含从准备、
检查、执行、验证到失败停止的完整工作流，不能只有注意事项。

`SPEC-MVP-003`：完整优化版完成前，必须先形成独立阶段固件 `opt-setting.bin`。该成品只允许
包含本 SPEC 第 7 节规定的系统设置一级列表旋钮功能，并且只能在恢复门禁通过后进行独立真机
验证。

`SPEC-MVP-004`：完整优化版固定命名为 `ap01-1.0.2_0031-opt.bin`。它只能组合第 5、6、7 节
规定的一级页面开关、AGENTS 看板和系统设置旋钮功能，不全面重写原厂固件。

`SPEC-MVP-005`：MVP 必须使用冻结的完整优化版在唯一确认的目标 AP01 上完成至少一次真实刷机，
并取得下载、安装、重启、重新上线和目标功能验收结果。只生成文件、只上传或只下载均不算完成。

`SPEC-MVP-006`：完成刷机后，项目必须把实际成立的制作流程、安全流程、限制、失败停止条件和
验收方法固化回对应文档。

`SPEC-MVP-007`：项目必须交付 Windows 与 macOS 通用、零基础用户可操作的 AP01 WebUI
刷机工具。

`SPEC-MVP-008`：其他用户必须能够仅根据 WebUI 的页面提示完成环境检查、目标确认、刷机和结果
确认，不需要开发者在旁解释内部实现。

`SPEC-MVP-009`：第 5、6、7 节三个功能组、第 4 节刷机工具、第 8 节文档与安全约束全部验收
通过，才允许宣布 MVP 完成。

## 3. 固件身份、产物与共同保护

### 3.1 当前官方基线

<a id="spec-firmware-baseline"></a>

`SPEC-FIRMWARE-001`：当前允许进入分析和制作的官方基线固定如下：

| 项目 | 固定值 |
| --- | --- |
| 设备型号 | `njcuk.enstor.ap01` |
| 官方版本 | `1.0.2_0031` |
| 文件名 | `ap01-1.0.2_0031.bin` |
| 文件字节数 | 6,804,520 |
| MD5 | `469a7329d496f81ae8625c4d76ccf56d` |
| SHA-256 | `8a721fc8ef25458d415b2460e4a251e0503a82f7743fdff85b12612190e5c1cb` |
| 文件头 | `BFNP` |
| 文件尾恢复校验值 | `0x7ffd605b` |

`SPEC-FIRMWARE-002`：每次制作和刷机前必须重新确认小米云最新版本。型号、版本、字节数、文件
指纹或容器结构任一不一致时，系统必须停止，不得尝试兼容、猜测地址或继续使用当前修改清单。

`SPEC-FIRMWARE-003`：原厂基线、阶段成品和完整优化版必须是三个不同身份的文件。任一成品必须
能够由文件名、完整文件指纹、构建记录和修改范围唯一识别，不能用同名覆盖掩盖成品变化。

### 3.2 阶段成品

<a id="11-设置菜单阶段固件"></a>
<a id="spec-settings-stage"></a>

`SPEC-FIRMWARE-004`：`opt-setting.bin` 的唯一新增用户功能只见 `SPEC-ROTARY-001` 至
`SPEC-ROTARY-008`。它不得包含 AGENTS 看板、一级页面开关、一级页面导航重排、页面开关状态
保存、后台刷新或二级菜单首尾循环。

`SPEC-FIRMWARE-005`：阶段成品必须保持官方型号、版本、总字节数、文件头和文件尾记录格式。
离线生成成功只证明文件成立，不自动取得上传、下载或安装资格。

### 3.3 完整优化版

`SPEC-FIRMWARE-006`：`ap01-1.0.2_0031-opt.bin` 只在官方固件上增加三个功能组，不改变原厂
启动、联网、米家通信、官方更新、恢复记录和未被目标功能涉及的页面行为。

`SPEC-FIRMWARE-007`：完整优化版必须能够从同一份经过核对的官方基线和全部已批准修改确定性
重建。构建过程可以读取身份完全匹配的冻结阶段成品，但不得读取历史实验成品，也不得叠加未
进入构建记录的修改。

`SPEC-FIRMWARE-008`：任何可安装成品都必须提供完整文件指纹、修改区间、修改区间外一致性、
文件尾校验、自动测试结果、恢复条件和允许进入的下一阶段。缺少任一项时，前端不得提供安装
操作。

## 4. WebUI 刷机全链路

### 4.1 用户入口

`SPEC-FLASH-001`：Windows 与 macOS 用户使用 Chrome 打开同一个产品入口。WebUI 必须自行检查
所需本地服务是否就绪，并把未就绪状态转换为用户可执行的页面提示。

`SPEC-FLASH-002`：零基础流程固定呈现为“准备条件 → 识别设备 → 核对固件 → 风险确认 → 执行
刷机 → 查看结果”。用户不得跳过设备身份、成品身份或风险确认。

`SPEC-FLASH-003`：设备识别结果必须至少显示可区分的设备名称、型号、当前版本、在线状态和是否
满足本次刷机条件；页面不得显示或导出设备凭据、网络地址、账号凭据等敏感原值。

`SPEC-FLASH-004`：固件核对结果必须明确区分官方基线、阶段成品和完整优化版，并显示文件名、
版本、完整性是否通过、允许执行的动作以及尚未满足的门禁。

### 4.2 执行状态与结果

`SPEC-FLASH-005`：执行刷机时，页面必须连续展示上传、设备下载、安装、暂时离线、重新上线和
验收六类状态。没有直接证据的阶段必须显示“等待确认”或“无法确认”，不能显示成功。

`SPEC-FLASH-006`：状态未知、网络中断或设备暂时离线时，系统必须停止重复写入，只允许查询
现状。用户不能通过重复点击再次下发同一安装。

`SPEC-FLASH-007`：成功结果必须同时证明目标设备接受成品、完成下载和安装、发生重启、重新
上线，并完成与本次成品相对应的功能验收。失败结果必须保留已完成阶段、停止原因和下一步安全
操作。

`SPEC-FLASH-008`：其他用户在发布环境中不得接触本项目源码、开发者本机路径、参考项目路径或
开发者账号，仍能完成 `SPEC-FLASH-001` 至 `SPEC-FLASH-007`。

## 5. 一级页面开关

<a id="21-一级页面开关"></a>
<a id="spec-primary-page-switches"></a>

### 5.1 菜单与复选行为

`SPEC-PAGE-001`：系统设置一级列表必须提供名为“开关一级页面”的入口。用户按下并松开旋钮后
进入开关页。

`SPEC-PAGE-002`：开关页必须以复选状态表示可切换页面。可切换项固定为时钟、功率、天气、
日历、萌宠和 AGENTS 看板；“返回”是操作项，不是页面开关。系统设置页始终保留。

`SPEC-PAGE-003`：左右旋转在六个复选项和“返回”之间首尾循环。焦点位于复选项时，按下并松开
旋钮切换该项；焦点位于“返回”时，按下并松开旋钮返回系统设置一级列表。

`SPEC-PAGE-004`：复选项只决定一级页面导航是否经过对应页面，不删除页面对象，也不改变原厂
页面自身的详情与返回行为。

### 5.2 生效、保存与失败

`SPEC-PAGE-005`：修改成功后，下一次一级页面旋转必须立即按新开关状态寻找目标页面；当前正在
显示的页面被关闭时，画面不立即跳走。

`SPEC-PAGE-006`：开关状态必须在设备正常重启后继续生效。保存尚未成功时，页面显示状态和实际
导航状态都不得提前变化。

`SPEC-PAGE-007`：首次没有有效保存记录时，时钟、功率和 AGENTS 看板开启，天气、日历和萌宠
关闭。

## 6. AGENTS 看板

<a id="spec-agents-dashboard"></a>

### 6.1 页面组成与刷新

`SPEC-DASHBOARD-001`：优化固件必须新增名为“AGENTS 看板”的第三方一级页面，用于展示并刷新
Codex 使用信息。

`SPEC-DASHBOARD-002`：看板由一个概览一级页面和三个详情二级页面组成，共四张页面。服务端负责
取得数据并生成设备可直接显示的完整画面，AP01 不在屏幕端重新排版数据。

`SPEC-DASHBOARD-003`：AP01 每 5 分钟尝试取得一次新数据或新画面，并把成功结果放入运行内存后
显示。一次刷新所需的数据和页面全部成功前，不得替换当前完整结果。

`SPEC-DASHBOARD-004`：设备画面优先使用 AP01 已支持且在满足画质和交互要求时体积最小的格式；
只有静态格式不能满足设备显示要求时才生成 GIF。

`SPEC-DASHBOARD-005`：断网、服务端不可达、数据不完整或新画面生成失败时，AP01 必须继续显示
最后一次成功结果，不能把错误文字画到屏幕上。

### 6.2 服务端与故障切换

`SPEC-DASHBOARD-006`：服务端必须支持 Windows 电脑、macOS 电脑、Linux NAS 和 Linux 云服务
器。四类环境提供相同字段、画面、刷新和失败表现。

`SPEC-DASHBOARD-007`：服务端必须在所在系统重启后自动运行，并继续提供最后一次有效结果；
没有有效结果时明确处于未就绪状态。

`SPEC-DASHBOARD-008`：首次刷机配置可以包含多个服务端。AP01 必须按配置顺序尝试；当前服务端
不可达时自动尝试下一个，成功后使用该服务端完成本轮刷新。

`SPEC-DASHBOARD-009`：某项数据在当前服务端无法取得时，只把该字段显示为“无法获取”；能够
取得的其他字段和页面继续正常生成。不得虚构、估算或借用其他字段填充。

### 6.3 视觉资产工作流

`SPEC-DASHBOARD-010`：首次制作看板视觉时，由 Codex 打开网页端 GPT 并调用 image2 生成效果
图；效果图必须经过用户审阅后才能成为视觉输入。

`SPEC-DASHBOARD-011`：审阅通过后，从效果图中移除会实时变化的数据文字，保留标题和视觉底图。
服务端把本轮真实数据写入预留文字槽位并生成完整成品图。

`SPEC-DASHBOARD-012`：AP01 取得并显示服务端生成的完整成品图，不得直接显示尚未填入本轮数据
的视觉底图。

`SPEC-DASHBOARD-013`：Brief 附件只用于决定 Brief 已点名字段的展示方式，不构成新增字段需求。
附件中出现但 Brief 未点名的数据，服务端不采集，前端不显示。

`SPEC-DASHBOARD-014`：字段组、布局和具体色彩方向的视觉唯一原文只见
[`AP01-AGENTS 看板效果图评审`](image/DESIGN/AP01-AGENTS看板/README.md)；本 SPEC 只规定功能
含义和可验收表现。

### 6.4 共通显示规则

<a id="41-看板数值显示合同"></a>
<a id="spec-dashboard-values"></a>

`SPEC-DASHBOARD-015`：四张页面中的数据不得显示小数点。计数保持整数；百分比、金额和来源为
小数的数值按最终显示精度取整数。

`SPEC-DASHBOARD-016`：Token 消耗按原始整数自动选择 `Token`、`万 Token` 或 `亿 Token`
单位。小于一千亿的数值必须完整放入预留位置，不能挤压、覆盖或移动其他字段。

`SPEC-DASHBOARD-017`：单位切换结果必须避免五位主体数字；数值和单位使用各自预留位置。具体
格式化边界由 DESIGN 承接，并以 `9,999 Token`、`9,999 万 Token` 和 `1,000 亿 Token` 为
三个显示上界样例。

`SPEC-DASHBOARD-018`：本周剩余额度、缓存命中率等数值越高越好的比例指示，必须在低值时表达
警告、高值时表达良好；具体色彩只引用 `SPEC-DASHBOARD-014` 指定的评审原文。

### 6.5 概览一级页面

`SPEC-DASHBOARD-019`：概览页固定包含三个区块：

| 区块 | 显示内容 | 表现 |
| --- | --- | --- |
| 本周剩余额度 | 剩余额度百分比 | 圆环 |
| 消耗数值 | 今日消耗、近 30 天消耗 | 普通数值与单位 |
| 最近趋势 | 近 7 天消耗 | 曲线 |

`SPEC-DASHBOARD-020`：圆环只用于本周剩余额度百分比。今日消耗和近 30 天消耗没有百分比总量，
不得使用圆环。

### 6.6 三个详情页面

<a id="42-看板字段口径"></a>
<a id="spec-dashboard-fields"></a>

`SPEC-DASHBOARD-021`：周剩余额度详情必须显示：

1. 本周剩余的进度条和百分比；
2. 下次重置的倒计时和重置时间；
3. 可用重置次数；
4. 每张重置卡的过期倒计时、发放时间和到期时间。

`SPEC-DASHBOARD-022`：今日消耗详情必须显示：

1. 总消耗 Token；
2. 请求数；
3. 总成本；
4. 输入、输出和缓存命中。

`SPEC-DASHBOARD-023`：近 30 天消耗详情必须显示：

1. 近 30 天累计消耗；
2. 最长任务时长；
3. 活动洞察；
4. 常用插件。

`SPEC-DASHBOARD-024`：活动洞察和常用插件各使用一个能够表达该组含义的组图标；组内数据行不
重复绘制图标或圆环。

`SPEC-DASHBOARD-025`：活动洞察和常用插件两组数据行的字段名、数值和单位使用同一种文字颜色，
不得用不同文字颜色区分具体数值。

### 6.7 数据取得与字段缺失

`SPEC-DASHBOARD-026`：字段取得方法的研究范围必须包含本机 Codex 桌面端、Codex CLI、
CC Switch App 和 Cockpit Tools App 的本地缓存。最终采用的数据来源、字段含义、读取条件和
失败表现必须在 DESIGN 中固化。

`SPEC-DASHBOARD-027`：服务端只取得 `SPEC-DASHBOARD-019`、`SPEC-DASHBOARD-021`、
`SPEC-DASHBOARD-022`、`SPEC-DASHBOARD-023` 点名的数据。数据来源不得扩大设备端或发布产物
可见的敏感信息范围。

`SPEC-DASHBOARD-028`：数据缓存、完整结果和图片不得包含提示词、回复正文、登录信息、账号
标识、设备信息或开发者本机绝对路径。

### 6.8 物理旋钮

`SPEC-DASHBOARD-029`：AGENTS 看板的旋钮反馈、按下与松开判定必须与原厂交互一致。原厂行为
的唯一参照为
[`AP01 原厂各页面物理旋钮交互实现`](../knowledge/AP01-官方固件分析/原厂各页面物理旋钮交互实现.md)。

`SPEC-DASHBOARD-030`：在概览一级页面按下并松开旋钮，进入详情；第一次进入时显示周剩余额度
详情。

`SPEC-DASHBOARD-031`：在详情中左右旋转，按“周剩余额度 → 今日消耗 → 近 30 天消耗”的顺序
双向首尾循环。

`SPEC-DASHBOARD-032`：在任一详情页面按下并松开旋钮，返回 AGENTS 看板概览一级页面。

`SPEC-DASHBOARD-033`：新增交互不得改变日历、天气、功率、时间、设置和萌宠页面的原厂确认、

## 7. 系统设置一级列表旋钮

<a id="spec-settings-rotary"></a>

`SPEC-ROTARY-001`：本节只改变系统设置一级列表。二级菜单继续保持原厂边界行为。

`SPEC-ROTARY-002`：一级列表中的有效设置项按原厂顺序首尾相接。焦点位于第一项时继续向左旋转
一格，必须直接选择最后一项。

`SPEC-ROTARY-003`：焦点位于最后一项时继续向右旋转一格，必须直接选择第一项。

`SPEC-ROTARY-004`：完成首尾切换后，继续沿同一方向旋转时，必须从目标端按照原厂相邻顺序
继续选择。

`SPEC-ROTARY-005`：每个有效旋转格必须在同一次事件中同步更新选中状态、选中样式和列表可视
位置；用户不需要再旋转一次才能看见目标项。

`SPEC-ROTARY-006`：首尾切换不播放跨越中间条目的滚动过程；一级列表内部相邻移动继续保持
原厂表现。

`SPEC-ROTARY-007`：同一个物理旋转格中尚未完成的相位变化或机械抖动不得产生相反方向的列表
移动。

`SPEC-ROTARY-008`：用户主动快速反转方向时，可以丢弃未完成的中间相位；下一格完整旋转必须
按新方向正常响应。
