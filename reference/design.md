## 2. 设计纠偏唯一流程

本节是全项目“先文档、后代码、边实现边纠偏”的唯一流程原文。各子 DESIGN 只记录自己的
当前方案和纠偏事实，并引用本节，不再另行定义流程。

### 2.1 状态

| 状态 | 判定 |
| --- | --- |
| 拟定 | 已写明技术方案、代码落点和验证方法，尚未开始对应实现 |
| 验证中 | 已按当前方案形成候选实现，尚未取得足够验证证据 |
| 已验证 | 当前方案、代码和对应证据一致，且通过本轮规定的验证 |
| 已否定 | 已取得足以证明该方案不满足目标或破坏边界的证据，不得继续作为当前方案 |
| 阻塞 | 缺少设备、材料、环境、授权或直接证据，继续实现会越过安全边界 |

“自动测试通过”只能证明自动测试覆盖的范围；“真机验收通过”必须有目标设备、成品指纹、
环境、操作和结果记录。历史成品的证据不能自动继承给新成品。

### 2.2 原厂复用先行门禁

本节是全部固件功能“先查原厂、优先复用、证据先于设计、设计先于代码”的唯一流程原文。

每条功能需求进入子 DESIGN 前，必须依次完成：

1. 从当前官方固件的实际注册点、实际调用者、数据结构和生命周期调查是否已有相关逻辑；
2. 找到相关逻辑时，先在 `knowledge/AP01-官方固件分析/` 新建或更新对应事实文档，写明固件
   身份、直接证据、调用链、可复用入口、参数、状态字段、生命周期、复查方法和能力边界；
3. 对应子 DESIGN 必须精确引用该事实文档路径，并写明本需求复用哪些原厂入口、保留哪些
   原参数与状态、失败时回到哪里、哪些原厂范围禁止修改；
4. 完成上述文档后，才允许把方案状态设为“拟定”并开始代码；
5. 没有找到相关原厂逻辑时，先把已检查的范围和“未找到”的证据写入固件分析文档，再由
   子 DESIGN 设计自有实现；
6. 认为原厂逻辑不适用时，先在子 DESIGN 写明不适用的直接证据、风险和替代方案，再实现
   替代方案；
7. 复用实现经实测失败时，先把原方案、成品身份、测试环境、失败表现和仍未知事实写入子
   DESIGN 的纠偏记录，再写下一方案；不得先改代码；
8. 代码、静态检查、自动测试和真机验收都必须能反向追溯到子 DESIGN 及其引用的固件分析
   文档。引用缺失、证据缺失或代码超出当前方案时，本轮实现不成立。

“优先复用”不等于按函数外形猜测可替换关系。只有当前官方版本中实际注册或实际调用的入口、
参数、状态字段和生命周期已经形成证据，才算可复用的原厂逻辑。相似函数在证明等价前按不同
接口处理。

“通读并掌握原厂代码”的唯一合格标准如下：有原厂源码时，逐行读完本次功能涉及的实际源码；
只有固件二进制时，逐条读完实际注册入口、全部直接调用者、全部可达分支、实际被调用函数、
返回路径和生命周期收尾范围内的反汇编指令。事实文档必须保存精确起止地址，并逐条说明指令
使用的寄存器、内存、分支目标、调用目标和前后状态；任何无法解释的间接调用、分支、数据来源
或生命周期都属于阻塞。完整文件扫描、字符串提取、资源提取、自动反编译、函数外形相似和自动
测试均不能替代该标准。对应事实文档和子 DESIGN 没有逐条覆盖矩阵时，不得编写、修改、包装
或测试相关代码。

### 2.3 一次性循环

每次新增或纠偏按以下顺序完成：

1. 在对应子 DESIGN 的“当前有效方案”中写明方案编号、承接条款、假设、模块归属、准备修改的
   代码位置、验证方法、成功条件、停止条件和回退对象；
2. DESIGN 状态改为“拟定”后，才允许开始对应代码；
3. 代码只能实现当前有效方案，不得同时夹带未进入 DESIGN 的备选方案；
4. 完成自动测试或真机验证后，立即把证据、适用范围和未覆盖范围写回同一子 DESIGN；
5. 方案成功时，把状态改为“已验证”，并补齐实际代码和测试落点；
6. 方案失败时，先在纠偏记录中把原方案标为“已否定”并写明失败证据，再把下一方案写成
   “拟定”，随后才能修改代码；
7. 同一轮结束前执行文档与代码一致性检查，再形成可单独回滚的版本记录并同步远端。

如果一次验证只能排除方案、不能证明根因，纠偏记录只写“已否定的方案”和“仍未知的事实”，
不得把猜测写成原因。

### 2.4 子 DESIGN 固定结构

每份子 DESIGN 至少维护：

1. 当前有效方案：只保留接下来允许实现或正在验证的唯一方案；
2. 纠偏记录：按时间追加，保留已否定方案、证据和替代关系，不覆盖历史；
3. 实现落点：记录模块公开入口、专属文件和依赖方向；
4. 验证门槛：区分静态检查、自动测试、页面验收、真机验收和恢复验收；
5. 阻塞项：记录缺少的直接证据及解除后先更新的文档位置。

## 3. 一致性门禁

- Brief 逐句到 SPEC 的落点只见
  [`Brief 逐句覆盖矩阵`](SPEC/Brief逐句覆盖矩阵.md)；
- 全部 SPEC 到 DESIGN、代码和验证的落点只见
  [`SPEC 到 DESIGN 实现矩阵`](DESIGN/SPEC到DESIGN实现矩阵.md)；
- 写代码前必须通读 [`Architecture.md`](Architecture.md)，并按其中要求声明模块归属；
- 每个固件功能的 DESIGN 落点必须引用对应的
  `knowledge/AP01-官方固件分析/` 事实文档；没有原厂实现时也必须引用调查范围与结果；
- 每次改动结束时，自动核对 SPEC 条款是否全部出现在 DESIGN 系列、文档引用是否存在、当前
  方案记录的代码路径是否存在；
- 尚未实现的落点必须明确标为“拟定”或“阻塞”，不能因为已经有 DESIGN 就标为完成。
