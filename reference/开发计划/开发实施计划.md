# AP01 第三方固件制作与刷机工具实施计划

本文档只记录实施顺序、阶段入口和阶段完成条件，不定义产品功能。产品目标与最小可用版本
范围见 [`brief.md`](../brief.md)，交互规则写入后续 Design（交互与视觉设计文档），技术合同
见 [`SPEC.md`](../SPEC.md)。

## 1. 顺序原则

实施严格分成三个闭环，前一个闭环没有完成时，不开始依赖它的下一个闭环。三个闭环全部
通过后，最小可用版本才完成。静态效果图审阅属于设计准备，可以在固件与恢复闭环期间提前
进行，但不得据此启动数据服务、设备页面实现、固件资源写入或刷机。

```mermaid
flowchart LR
    V["静态效果图审阅"] -. "批准后固定视觉方向" .-> B
    A["固件与恢复闭环"] --> B["数据与画面闭环"]
    B --> C["普通用户工具闭环"]
```

### 1.1 提前效果图审阅

提前审阅只制作 [`brief.md`](../brief.md) 已声明的四个页面效果图，使用示例数据展示完整
信息层级，并按 320×240 画布交付用户审阅。

完成条件是用户明确批准四个页面的布局、配色和信息层级。批准结果只作为数据与画面闭环的
视觉入口，不代表页面渲染、数据读取、固件资源、离线构建、仅下载或安装已经获准。数据与
画面闭环仍须等待固件与恢复闭环通过后才能开始。

## 2. 固件与恢复闭环

### 入口

- 已从小米云重新查询官方最新版本；
- 已下载并校验匹配型号与版本的原厂固件；
- 已通读 [`AP01 官方固件分析`](../../knowledge/AP01-官方固件分析/AP01-官方固件分析.md)；
- 固件版本与知识基线完全一致。

### 工作

1. 建立可重复的原厂固件分析和构建过程；
2. 完成最小修改；
3. 完成文件头、字节数、修改区间和恢复校验；
4. 用同一个成品完成仅下载验证；
5. 经用户本次确认后正式安装；
6. 验证重启、重新上线、米家通信和原厂基础功能；
7. 用匹配的原厂固件完成回退实测并再次验收。

### 完成条件

制作、仅下载、正式安装、重启验收和官方固件回退的证据链完整，且每一步都能按文档复现。

## 3. 数据与画面闭环

### 入口

固件与恢复闭环已通过。

### 工作

1. 复用参考项目已验证的 Codex 数据读取能力；
2. 按 `brief.md` 中声明的字段制作 320×240 画面；
3. 每 5 分钟刷新一次；
4. 刷新失败时保留最后一次成功数据和画面；
5. 验证 AP01 真机主动取得并持续显示画面；
6. 完成一级页、二级页和旋钮交互验收。

### 完成条件

数据字段、画面、刷新、断网行为和真机交互全部与批准后的需求、设计和技术合同一致。

## 4. 普通用户工具闭环

### 入口

数据与画面闭环已通过。

### 工作

1. 把设备识别、检查、制作、仅下载、安装和结果验证固化到 WebUI（浏览器中的操作界面）；
2. 在 Windows 和 macOS 上分别打包与安装；
3. 分别验证系统启动或用户登录后的自动运行；
4. 使用 Chrome 完成普通用户全流程实测；
5. 验证日志、凭据、设备信息和本机数据不进入发布物。

### 完成条件

普通用户不使用命令行，只通过 Chrome 即可完成设备识别、确认、刷机、进度查看和结果验收。

## 5. 计划变更规则

- 调整实施先后只修改本文；
- 新增或删除产品功能先修改 `brief.md` 或对应 PRD；
- 改变交互先修改 Design；
- 改变技术接口、数据合同、固件地址或验收算法先修改 SPEC；
- 计划状态不得替代验收证据。
